# Мониторинг

**Русский** · [English](MONITORING.en.md)

Экран «Мониторинг» показывает в прямом эфире, как живёт сервер и сколько трафика идёт по каждому
протоколу, а затем хранит историю для анализа по дням, месяцам и узлам. Он **только читает**: ничего
не меняет ни в протоколах, ни в менеджерах, и недоступный источник превращается в «нет данных», а не в
неверное число. Экран виден всем ролям; отдельной настройки и отдельной установки у него нет.

## Что и как измеряется

```
ядро хоста ── version-agent (root, хост) ──UDS── панель (сборщик, кольцо + SQLite, API/SSE) ── браузер
 /proc, nft, cgroup    GET /v1/metrics                     ▲ опрос только пока кто-то смотрит
                                                           └── связанные панели: /api/fleet/v2/metrics
```

**Агент хоста** (`version-agent`) раз в секунду снимает показания в отдельном потоке и держит последний
снимок в памяти; `GET /v1/metrics` отдаёт готовый снимок и ничего не считает по запросу. Сборщик
панели каждые 2 секунды (`PANEL_METRICS_INTERVAL_SECONDS`) забирает снимок, считает скорости и пишет
их в кольцо в памяти (900 точек, около 30 минут) и раз в 30 секунд — в базу.

Показатели хоста:

- **CPU** по `/proc/stat` (разница между снимками), число ядер, средняя нагрузка 1/5/15 минут;
- **память и подкачка** по `MemAvailable`: «занято» — это всё, что нельзя отдать без вытеснения;
- **диск**: занятое место корневой файловой системы, скорость чтения и записи и занятость устройства
  (`busy`) по `/proc/diskstats`;
- **сеть хоста**: сумма по физическим интерфейсам; `lo`, `veth*`, `br-*`, `docker*`, `awg*`, `tun*` и
  `wg*` в неё не входят, чтобы трафик не считался дважды;
- **контейнеры**: CPU (в процентах одного ядра, поэтому бывает больше 100) и память каждого контейнера по
  cgroup v2; имена берутся из `docker ps` раз в 30 секунд;
- **аптайм**.

### Трафик по протоколам

| Протокол | Откуда берутся байты | Живая скорость |
|---|---|---|
| MTProxy (Telemt) | счётчики ядра на порту бэкенда (`8445/tcp` за Nginx SNI) | да |
| NaiveProxy | счётчики ядра на `4443/tcp` (loopback за SNI-маршрутизатором; прямой слушатель тоже считается) | да |
| Mieru | счётчики ядра на TCP/UDP-портах из `portBindings` mita и полос Mieru | да |
| TrustTunnel | счётчики ядра на порту endpoint (`TT_LISTEN`, по умолчанию `4453/tcp`) | да |
| AmneziaWG | счётчики интерфейсов `awg15`, `awg20`, `awg31` из `/proc/net/dev` | да |

Счётчики ядра ведёт **собственная таблица nftables** `inet proxy_control_metrics`. Агент создаёт её
сам, идемпотентно, в одной транзакции и пересоздаёт при изменении набора портов. В ней две цепочки
(`input` и `output` с приоритетом `-300`, политика `accept`): правила только считают
(`counter`) и никогда не принимают решение о пакете. Остальные таблицы nftables, Docker и ufw
не затрагиваются.

- **Направление — с точки зрения клиента.** `↑` — от клиентов к серверу (порт назначения, хук `input`),
  `↓` — к клиентам (порт источника, хук `output`). Каждый loopback-переход считается один раз.
- **Это сетевой уровень (L3), байты с заголовками пакетов.** Поэтому цифры немного больше, чем
  «полезная нагрузка», и в интерфейсе они подписаны как сетевой трафик.
- **Порты находит сам агент**, спрашивать оператора не нужно. Он читает то, что записал установщик:
  список Compose-файлов, `.env` (`MTPROXY_BACKEND_PORT`), `.env.trusttunnel` (`TT_LISTEN`), конфигурацию
  mita `/var/lib/mita/server_config.json` и `MIERU_LANE_SLOTS`. Протокол, который не включён на хосте,
  просто отсутствует и показывается как «недоступен», а не как нулевой трафик. Карта портов
  перечитывается раз в минуту; на один протокол берётся не больше 64 портов.
- **Файл переопределения** `/etc/proxy-control/metrics-ports.json` нужен, только если порты
  нестандартные. Он заменяет найденные порты указанных протоколов целиком:

  ```json
  { "naive": { "tcp": [4443] }, "mieru": { "tcp": [8443], "udp": [8443] } }
  ```

  Допустимы ключи `mtproxy`, `naive`, `mieru`, `trusttunnel`; порты — числа 1–65535. Файл с ошибкой
  целиком игнорируется, в журнале агента остаётся одна строка. Правки подхватываются в течение минуты.
- **Очистка.** Агент не удаляет того, что не создавал, и при остановке оставляет таблицу (счётчики
  безвредны). Убрать её вручную: `sudo nft delete table inet proxy_control_metrics`; агент создаст её
  заново, пока работает.

### Соединения

Поле `connections` в каждой записи протокола — число **установленных TCP-соединений** (состояние
`ESTABLISHED`) на портах протокола, которые агент раз в секунду считает по `/proc/net/tcp` и
`/proc/net/tcp6` без внешних утилит. Карточка показывает его как «Соединений N». Это реальные TCP-потоки,
а не клиенты: один клиент может держать несколько. Цифра нужна потому, что у менеджеров нет живого
счёта: `sessions` у TrustTunnel остаётся 0 при идущем трафике, у NaiveProxy и Mieru его нет совсем, поэтому
`sessions` для них не используется. За SNI-роутером (NaiveProxy) считается петлевой отрезок, то есть число
туннелей к бэкенду. У Mieru считаются **только TCP-порты**, UDP не считается. У AmneziaWG TCP-порта нет:
`connections` равно `null`, а карточка показывает «Сессий» — число пиров с недавним рукопожатием.
Если файлов `/proc/net/tcp*` нет, `connections` — `null`, а не 0; карточка тогда возвращается к «Сессий».
В истории это ряд `<протокол>.connections`, в сводке — `connections_peak`.

### Что каждый протокол показывает вживую

- **TrustTunnel, AmneziaWG** — скорости ↑/↓ по ядру, клиенты от менеджера (сессии AmneziaWG — пиры; у TrustTunnel вместо сессий соединения), скорости по клиентам
  (раз в 5 секунд) с разделением на ↑ и ↓.
- **MTProxy** — скорости ↑/↓ по ядру. Путь через менеджер (Telemt) даёт **только суммарный счётчик**
  `total_octets` без разделения на ↑ и ↓: по клиентам видна общая скорость, соединения — из
  `current_connections` (опрос раз в 15 секунд).
- **NaiveProxy** — общая живая скорость по ядру. Скорости **по клиентам** даёт менеджер (опрос раз в
  15 секунд, даже когда ядро считает порт): журнал Caddy пишется, когда туннель закрывается, поэтому
  строка клиента — среднее за 60 секунд по завершённым соединениям, с `live: false` и пометкой
  «по завершённым». Это реальные объёмы, но не бегущий счётчик.
- **Mieru** — общая скорость по ядру (UDP тоже). Скорости **по клиентам** — вживую из счётчиков mita
  (`mita get metrics`, менеджер отдаёт их на `/v1/traffic`; у линий складываются работающие слоты),
  опрос раз в 5 секунд, с разделением на ↑ и ↓. Сессий по клиентам у Mieru нет. Счётчики mita
  обнуляются вместе с демоном: панель считает это сбросом.

Если `nft` недоступен или отказывает, агент отдаёт `kernel_counters: "unavailable"` и повторяет попытку
каждые 30 секунд. Панель тогда берёт суммы по менеджерам (`source: "manager"`): для TrustTunnel и
AmneziaWG и Mieru это работает как обычно, MTProxy — только общая скорость, а NaiveProxy помечается как
не-живой (`live: false`, среднее за минуту по завершённым соединениям).

## Три экрана

**Сейчас** — прямой эфир. Выбор узла (в том числе «Все узлы»); плитки CPU, RAM, диска, сети и
нагрузки с кольцами и мини-графиками; карточки протоколов со скоростями ↑↓, сессиями и мини-графиком;
график ↑/↓ за последние 5 минут; таблица «кто сейчас качает» (до 10 клиентов) и таблица контейнеров.
Индикатор состояния: «в эфире», «пауза» или «нет связи». Кнопка паузы замораживает картинку; вкладка,
скрытая дольше минуты, отключает поток и возобновляет его при возврате.

**Трафик** — история по протоколам: диаграмма с накоплением, период от 15 минут до 90 дней, переключатель
↑/↓/сумма, объёмы и доля каждого протокола.

**Узлы** — сравнение всех узлов в одной таблице (состояние, CPU, RAM, диск, сеть, объём трафика,
оповещения) и разбор выбранного узла: история ресурсов, объёмы по протоколам, средняя нагрузка по часам
суток (при периоде от 7 суток) и пики.

Периоды: 15 мин, 1 ч, 6 ч, 24 ч, 7 д, 30 д, 90 д. Пропуски в данных остаются пропусками, а не нулями.
Карточка «Ресурсы сервера» на обзоре берёт тот же живой поток (с 3.1): обновляется на месте раз в
интервал сборщика (2 с), с пометкой «в прямом эфире», и ведёт на этот экран. Если мониторинг выключен,
карточка опрашивает агента раз в 5 секунд.

## Хранение

| Разрешение | Срок хранения | Для чего |
|---|---|---|
| ядро: точки каждые 2 с в памяти (≈30 мин) | до перезапуска панели | «Сейчас», периоды 15 мин и 1 ч |
| 60 с | 3 суток | периоды до 3 суток |
| 15 мин | 35 суток | периоды до 35 суток |
| 1 ч | 400 суток | периоды до года |

Каждая точка попадает во все три разрешения (таблица `metric_rollups`, миграция 25: сумма, число
отсчётов, максимум и последнее значение за корзину). Запись идёт одной транзакцией раз в 30 секунд,
устаревшие корзины удаляются не чаще раза в час. Объём передачи за корзину хранится как сумма
(`*_bytes`), скорости — как среднее и максимум. Размер базы под рабочие таблицы метрик растёт примерно
на 40 МБ при полном наборе из пяти протоколов в конце срока хранения и меньше, если протоколов меньше
(оценка по числу строк, а не замер на живых данных). Хранится только `node_id` `local`: история связанных
узлов остаётся на самих узлах и запрашивается у них по требованию.

## Оповещения

Оповещения вычисляются из тех же рядов и показываются на экране «Узлы» и в обзоре MCP.

| Вид | Предупреждение | Критично |
|---|---|---|
| `cpu` | средняя за 5 мин выше 85 % | выше 95 % |
| `mem` | выше 90 % | выше 97 % |
| `disk` | выше 90 % | выше 95 % |
| `swap` | выше 50 % | выше 80 % |
| `stale` (нет снимка хоста) | дольше 60 с | дольше 300 с |
| `net_spike` (всплеск сети) | суммарная скорость выше 3× p95 за последние 24 ч (и не меньше 256 КиБ/с) | выше 6× |

Для `net_spike` нужен как минимум час накопленных данных. Оповещения ничего не отправляют наружу — они
только показываются.

## Транспорт: SSE и запасной опрос

Браузер получает снимки по `GET /api/metrics/stream` (Server-Sent Events): событие `snapshot` каждые
2 секунды, комментарий `: ping` каждые 15 секунд в тишине, `retry: 3000`. Ответ идёт с
`X-Accel-Buffering: no`, поэтому Nginx не накапливает поток. Если поток недоступен, интерфейс сам
переходит на опрос `GET /api/metrics/live` раз в 3 секунды (индикатор «в эфире · опрос раз в 3 с») и
переподключается с нарастающей паузой.

Ограничения потока: **4 потока на сессию, 24 в сумме** (пятый и следующие получают `429` с
`Retry-After: 5`); поток закрывается через **55 минут** событием `bye` (браузер подключается заново и
заодно проверяет, что сессия жива); закрытие вкладки освобождает место сразу. Ключ API (Bearer) может
читать `live`, `history` и `summary`; `EventSource` не умеет заголовков, поэтому скрипту проще
опрашивать `live`.

## HTTP API

Все маршруты — `GET`, доступны любой вошедшей роли (и ключам API любого уровня), отвечают с
`Cache-Control: no-store`, не содержат секретов и называют клиентов только именами учётных записей.
`PANEL_METRICS_ENABLED=0` выключает сборщик и маршруты (ответ `404 metrics_disabled`).
Параметр `node` — `local` (по умолчанию), id связанного узла или `all` (эта панель и все связанные).

| Маршрут | Параметры | Ответ |
|---|---|---|
| `/api/metrics/live` | `node` | один снимок |
| `/api/metrics/stream` | `node` | SSE: `snapshot`, `bye` |
| `/api/metrics/history` | `node` (один узел), `series` (до 40 через запятую), `range`, `points` (10–2000, по умолчанию 240) | ряды `[ts, среднее, максимум]` |
| `/api/metrics/summary` | `node`, `range` (по умолчанию `24h`) | итоги за период, оповещения, сравнение узлов |
| `/api/metrics/clients` | `protocol` | клиенты этой панели по одному протоколу с текущими скоростями (страницы протоколов показывают их как «Сейчас» / «За минуту»); только этот узел |

`range` — одно из `15m 1h 6h 24h 7d 30d 90d`; неизвестное значение даёт `422`. Идентификаторы рядов:
`host.cpu`, `host.mem`, `host.swap`, `host.disk`, `host.disk_read_bps`, `host.disk_write_bps`,
`host.load1`, `net.rx_bps`, `net.tx_bps` и для каждого протокола (`mtproxy`, `naive`, `mieru`,
`amneziawg`, `trusttunnel`) `<протокол>.up_bps`, `.down_bps`, `.sessions`, `.clients`, `.connections`, `.up_bytes`,
`.down_bytes`.

Пример `GET /api/metrics/live?node=local` (сокращён):

```json
{
  "ts": 1760780000.5, "interval": 2.0,
  "nodes": [{
    "node_id": "local", "name": "central", "status": "ok", "age_seconds": 0.0, "kernel_counters": "ok",
    "host": {
      "cpu_percent": 12.5, "cores": 4, "load": [0.5, 0.4, 0.3], "uptime_seconds": 864000,
      "mem": {"used": 1717986918, "total": 4294967296, "percent": 40.0, "available": 2576980378},
      "disk": {"used": 10737418240, "total": 53687091200, "percent": 20.0,
               "read_bps": 0.0, "write_bps": 20480.0, "busy_percent": 1.2},
      "net": {"rx_bps": 184320.0, "tx_bps": 921600.0, "interfaces": [{"name": "eth0", "rx_bps": 184320.0, "tx_bps": 921600.0}]},
      "containers": [{"name": "proxy-control-panel", "cpu_percent": 1.4, "mem_bytes": 188743680}]
    },
    "protocols": {
      "trusttunnel": {"available": true, "live": true, "source": "kernel", "up_bps": 51200.0, "down_bps": 307200.0,
                      "total_bps": 358400.0, "up_bytes": 5242880, "down_bytes": 31457280, "sessions": 3, "clients": 2, "connections": 4},
      "mieru": {"available": true, "live": true, "source": "kernel"},
      "naive": {"available": false, "reason": "disabled"}
    },
    "top_clients": [{"protocol": "trusttunnel", "username": "alice", "client_name": "Alice", "up_bps": 40960.0,
                     "down_bps": 262144.0, "total_bps": 303104.0, "live": true}],
    "alerts": []
  }]
}
```

`status` узла — `ok`, `stale` (агент не ответил, показан последний снимок с `age_seconds`),
`unavailable` (снимка ещё не было) или `unsupported` (узел без возможности `metrics.v1`).
`source` протокола — `kernel`, `interface` (AmneziaWG) или `manager`.

Пример `GET /api/metrics/history?series=host.cpu,trusttunnel.down_bytes&range=24h&points=96`:

```json
{
  "status": "ok", "node_id": "local", "range": "24h", "step": 900, "from": 1760693600, "to": 1760780000,
  "source": "rollup", "resolution": 60,
  "series": {
    "host.cpu": [[1760693400, 11.2, 40.5], [1760694300, null, null]],
    "trusttunnel.down_bytes": [[1760693400, 73400320, 20971520]]
  }
}
```

В рядах `*_bytes` второе число — объём за корзину (сумма), в остальных — среднее; третье — максимум
внутри корзины. `null` — в этом промежутке данных нет.

`GET /api/metrics/summary?range=7d` возвращает для каждого узла `host` (для CPU, памяти, диска, сети:
`avg`, `p95`, `max`, `max_at`), `protocols` (`up_bytes`, `down_bytes`, `total_bytes`, `avg_bps`,
`peak_bps`, `peak_at`, `share_percent`, `sessions_peak`, `connections_peak`), `hours_of_day` (по 24 средних на протокол,
только от 7 суток) и `alerts`. При `node=all` добавляется `compare` — по строке на узел, по убыванию
трафика.

## Узлы

Панели в парке отдают свои снимки центральной через `GET /api/fleet/v2/metrics`,
`/api/fleet/v2/metrics/history` и `/api/fleet/v2/metrics/summary` (ключ `node-sync`, возможность
`metrics.v1`). Центральная опрашивает узлы **только пока кто-то смотрит** экран (без зрителей ничего не опрашивается; статус
узла в парке по-прежнему обновляет обычный heartbeat раз в 15 секунд), не более 8 узлов одновременно, с таймаутом
3 секунды на вызов и кэшем на 2 секунды на узел; историю и итоги узла она запрашивает у самого узла в момент
просмотра (таймаут истории 10 секунд). Недоступный узел 120 секунд показывается как `stale` с последним известным
снимком и его возрастом, затем как `unavailable`; узел без `metrics.v1` (старее
2.0) — `unsupported`. Сначала обновляйте узлы, потом центр. Подробнее о парке: [FLEET.ru.md](FLEET.ru.md).

## MCP

Маршруты `live`, `history` и `summary` становятся инструментами MCP автоматически
(`get_metrics_live`, `get_metrics_history`, `get_metrics_summary`); `/api/metrics/stream` из MCP
**исключён** — вызов инструмента ждёт готового ответа, а поток бесконечен. В обзоре (`overview`) есть
компактный раздел `metrics`: по каждому узлу состояние, CPU, RAM и диск в процентах, сетевые скорости,
скорости протоколов ↑/↓ и число сессий, оповещения (`null`, если мониторинг недоступен). См.
[MCP.ru.md](docs/MCP.ru.md).

## Когда что-то недоступно

- **Агент не отвечает.** Сборщик помечает узел `stale` и показывает последний снимок с возрастом; через
  60 секунд появляется оповещение `stale`. История не обрывается без следа: в разрыве данных нет.
- **Нет `nft`.** Ряды по протоколам строятся из менеджеров (см. выше), NaiveProxy не «живой», Mieru по счётчикам mita, без
  данных; метрики хоста работают.
- **Нет Docker** или cgroup v2 — просто нет таблицы контейнеров.
- **Панель перезапущена.** Кольцо в памяти пусто, пока набирается заново; история из базы цела
  (не больше 30 секунд последних точек может не успеть записаться).

## Приватность

В метриках нет содержимого трафика, адресов назначения, IP клиентов и секретов: только скорости,
объёмы, число сессий и имена учётных записей протоколов (`runtime_username`) и клиентов. Правила nftables
считают байты по порту и не смотрят в пакеты.

## Нагрузка

Сэмплер агента — один поток, раз в секунду читает несколько файлов `/proc` и вызывает `nft` для счётчиков;
замеры на тестовом стенде — около **0,3 %** одного ядра. Тик сборщика панели укладывается в доли
секунды и ничего не блокирует; запись в SQLite — одна небольшая транзакция раз в 30 секунд. Живая проверка
сэмплера на хосте: `scripts/lab/agent-metrics-check.py` (от root, из каталога выпуска).

## Диагностика

| Симптом | Что проверить |
|---|---|
| «нет связи» на экране | `curl` до `/api/metrics/live` из браузера; Nginx/прокси перед панелью не должен буферизовать SSE (`X-Accel-Buffering: no` ставит панель сама); при отказе потока интерфейс сам переходит на опрос |
| `429` на потоке | открыто больше 4 потоков в сессии или 24 в сумме: закройте лишние вкладки |
| Все протоколы «нет данных», хост показывает | `kernel_counters` в `/api/metrics/live`; `sudo nft list table inet proxy_control_metrics`; журнал `journalctl -u version-agent` (строка «kernel counters unavailable») |
| Нулевая скорость протокола при живом трафике | порт не угадан: сверьте `sudo nft list counters table inet proxy_control_metrics` с реальным портом, при необходимости задайте `/etc/proxy-control/metrics-ports.json` |
| Узел `stale` | `sudo systemctl status version-agent`; `sudo curl --unix-socket /run/proxy-control/version-agent.sock http://version-agent/v1/metrics` (`503 metrics_warming_up` — агент только что стартовал) |
| Узел `unsupported` | узел старее 2.0 — обновите его |
| Экран отвечает `404 metrics_disabled` | `PANEL_METRICS_ENABLED=0` в окружении панели |
| Нужно убрать правила | `sudo nft delete table inet proxy_control_metrics` |
