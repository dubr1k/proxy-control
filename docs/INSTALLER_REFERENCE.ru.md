# Справочник интерактивного установщика релиза

**Русский** · [English](INSTALLER_REFERENCE.en.md)

Полный справочник по типизированному установщику релиза: какой релиз вы
проверяете, на какие вопросы отвечает мастер, какую конфигурацию он пишет, какой
план из неё выводит, какими границами владеет и какие доказательства оставляет.
Каждый блок команд, помеченный `installer-check`, выполняется через настоящий
парсер аргументов и загрузчик конфигурации в `tests/test_installer_docs.py`, так
что расхождение с кодом невозможно.

Установщик никогда не ставит систему из рабочего дерева. Он ставит её из
собранного релиза с контрольной суммой, который несёт собственную identity в
`release/release.json`.

## Проверка релиза

Скачайте архив, его `SHA256SUMS` и `release-manifest.json` со страницы релиза,
затем проверьте provenance до того, как что-либо получит привилегии.

```bash installer-check
gh attestation verify proxy-control-v0.1.0.tar.gz --repo dubr1k/proxy-control
sha256sum --check --ignore-missing SHA256SUMS
./install-bootstrap --archive proxy-control-v0.1.0.tar.gz --checksum SHA256SUMS --manifest release-manifest.json
```

`install-bootstrap` отказывается работать от root. До единственного `exec sudo`
он проверяет, что каждый вход — обычный файл, принадлежащий вам и не доступный
на запись группе или остальным, сверяет архив с опубликованной контрольной
суммой, требует, чтобы манифест называл тот же архив и тот же digest, отклоняет
prerelease-версию и проверяет архив на абсолютные и выходящие за пределы члены.
Он никогда не скачивает и не исполняет одной командой.

`release-manifest.json` фиксирует имя и digest архива, коммит, digest манифеста
внешних артефактов, число файлов и тег. `sbom.spdx.json` перечисляет каждый файл
релиза с его SHA-256 и каждый зафиксированный внешний артефакт с его лицензией.

Сборка воспроизводима: релизный workflow собирает один и тот же коммит дважды и
не продолжает, пока байты не совпадут. Эта детерминированность точна для
содержимого архива — несжатый tar побайтово одинаков на разных машинах, потому
что у каждого члена uid/gid 0, режим берётся из бита исполняемости git, а время
— из коммита. Но gzip-*обёртку* вокруг него делает локальный zlib, поэтому
пересборка на машине с другой версией zlib даст другой digest `.tar.gz` при
полностью совпадающем содержимом. Проверяйте скачанный архив по опубликованным
`SHA256SUMS` и аттестации, а не пересборкой на другой платформе.

## Интерактивный мастер

Без аргументов установщик запускает двуязычный мастер:

```bash installer-check
python3 -m installer.cli wizard --lang ru --config-output proxy-control.toml
```

Мастер спрашивает по порядку: язык, режим хоста, профиль, каждый обязательный
домен, ACME-почту, первого пользователя панели, слушатели Mieru (если профиль их
включает), режим 3x-ui и его домены, включён ли WARP и для каких доменов, и
управляет ли установщик UFW. Ответы записываются в TOML-файл, план отображается,
и до любой мутации требуется подтвердить первые двенадцать символов digest
плана. Выход на любом вопросе оставляет хост нетронутым.

## Команды

| Команда | Что делает |
| --- | --- |
| `wizard` | Задаёт вопросы, пишет конфигурацию, показывает план и применяет его после подтверждения digest |
| `plan` | Проводит аудит хоста и выводит детерминированный план; ничего не меняет |
| `install` | Применяет план, полный digest которого передан в `--accept-plan` |
| `status` | Печатает санитизированное состояние транзакции |
| `resume` | Продолжает прерванную транзакцию по её durable-журналу |
| `repair` | Перепроверяет владеемые файлы и перезапускает владеемые runtime |
| `report` | Пишет публичный отчёт приёмки и root-only передачу учётных данных |
| `uninstall` | Удаляет владеемое поколение; `--purge-data` удаляет и持persistent-состояние |

```bash installer-check
python3 -m installer.cli plan --config examples/installer/full-three-xui.toml --json
python3 -m installer.cli status --json
python3 -m installer.cli report --config examples/installer/full-three-xui.toml --output /var/lib/proxy-control/reports
```

`plan` доступен только на чтение. `install` отвергает digest, не совпадающий с
только что выведенным планом, поэтому подменить одобренный план другим нельзя.

## Файл конфигурации

```toml
schema = 1
host_mode = "fresh"        # fresh | coexist
profile = "full"           # core | core-naive | core-mieru | full
acme_email = "admin@example.com"
initial_user = "owner"

[domains]
panel = "panel.example.com"
mtproxy = "relay.example.com"
naive = "edge.example.com"     # обязателен для core-naive и full
mieru = "mieru.example.com"    # обязателен для core-mieru и full

[mieru]                        # только с профилем Mieru
tcp_ports = [46001]
udp_ports = [46001]

[three_xui]
mode = "managed-new"           # none | existing | managed-new
panel_domain = "xui.example.com"
vless_tcp_domain = "vless.example.com"
vless_xhttp_domain = "xhttp.example.com"
hysteria_domain = "hy2.example.com"
warp = false
warp_domains = []

[firewall]
manage_ufw = true
```

`schema` — целое `1`. `host_mode` выбирает свежий хост или сосуществование с
существующим Nginx-роутером на общем 443. `initial_user` — первый владелец
панели и bootstrap-пользователь Mieru, поэтому имя должно быть безопасным. В
`three_xui` режим `mode = "none"` не принимает других ключей, `existing`
принимает только домены, которые нужно маршрутизировать, а `managed-new` требует
все четыре домена плюс `warp` и `warp_domains`. `warp_domains` без `warp = true`
отклоняется. `manage_ufw` действует только на свежем хосте.

## Профили и примеры

Каждый профиль — префикс одного и того же порядка, а неподдерживаемые сочетания
отклоняются, а не молча урезаются.

```toml
profile = "core"        # Telemt/MTProto и панель
profile = "core-naive"  # плюс NaiveProxy за приватным listener Caddy
profile = "core-mieru"  # плюс Mieru/mita на собственных TCP- и UDP-слушателях
profile = "full"        # Telemt, панель, NaiveProxy и Mieru вместе
```

Готовые примеры лежат в `examples/installer/`:

```bash installer-check
python3 -m installer.cli plan --config examples/installer/core.toml --json
python3 -m installer.cli plan --config examples/installer/core-naive.toml --json
python3 -m installer.cli plan --config examples/installer/core-mieru.toml --json
python3 -m installer.cli plan --config examples/installer/existing-three-xui.toml --json
```

Управляемый 3x-ui публикует три эталонных inbound: **VLESS Reality TCP** и
**VLESS Reality XHTTP** на loopback-бэкендах за общим роутером 443 и
**Hysteria2** поверх TLS на публичном UDP/443 с собственным сертификатом. Для
каждого генерируются свежие ключи Reality, short ID и клиентские учётные данные;
ничего не копируется с эталонного сервера.

## Границы владения и порядок

План выполняет адаптеры в одном документированном порядке, и каждый владеет
ровно одной границей:

| Адаптер | Владеет |
| --- | --- |
| `packages` | Только теми пакетами, которые пришлось установить на свежем хосте |
| `nginx` | Одним владеемым блоком внутри выбранного route-файла общего 443 |
| `certificates` | Владеемыми HTTP-01 vhost и посервисными lineage Certbot |
| `firewall` | Только добавленными правилами UFW и только на управляемом свежем хосте |
| `core` | Compose-проектом `mtproxy`, его секретами и зафиксированным TDLib-probe |
| `naive` | Зафиксированной сборкой Caddy, разделёнными identity, состоянием и токеном manager, границей лога учёта и маршрутом Naive |
| `mieru` | Зафиксированным исполняемым mita, identity mita и стабильным UDS, токеном и состоянием manager, выбранными слушателями |
| `three_xui` | В режиме `existing` — ничем, кроме владеемого маршрута; в `managed-new` — одним staged-поколением |

Каждое действие применяется через durable-журнал: prepare, apply, verify.
Прерванный шаг возобновляем, а инверсия каждого адаптера восстанавливает то, что
он застал.

## Приёмка по протоколам

Живой процесс — это не протокольная проверка. Установщик принимает поколение
только по сквозным доказательствам:

- **Core**: модель Compose, все health-проверки, health панели и
  аутентифицированная HTTPS-сессия, управляющий API Telemt приватен для Compose,
  валидный `resPQ` для каждого временного MTProto-секрета, соседние SNI-маршруты
  и ограниченное сканирование на секреты.
- **NaiveProxy**: Admin API Caddy и приватный listener только на loopback,
  публичный cover HTTPS без учётных данных, один аутентифицированный `CONNECT` с
  известным payload, закрытие туннеля, дельта учёта закрытого туннеля не меньше
  отправленного payload, health manager и панели, соседние SNI и граница лога
  учёта.
- **Mieru**: оба зафиксированных digest, точный вывод
  `mita server status is "RUNNING"`, сокет управления с режимом `0770`, один
  SOCKS-запрос официального клиента на каждое включённое транспортное семейство,
  опустевшая очередь отправки, health manager и панели, нетронутые соседние
  слушатели.
- **3x-ui**: staged-бинарь сообщает зафиксированную версию, а эффективная
  сгенерированная конфигурация совпадает с шаблонами.

Каждый прогон приёмки создаёт временные учётные данные и удаляет их. Неудачная
очистка сообщается и остаётся повторяемой, а не отбрасывается молча.

## WARP и egress

WARP — это одна loopback-точка **SOCKS5** на `127.0.0.1:45000`. Установщик сам
WARP не разворачивает; он подключает к нему протоколы, когда вы его включаете.

Разделение сделано намеренно и различается по протоколам:

- **Xray / 3x-ui** пропускает через WARP **только выбранный трафик**. Правила
  привязаны к `warp_domains`, остальное идёт напрямую, а обязательная финальная
  политика добавляется после них и никогда не заменяется.
- **NaiveProxy** отправляет через WARP **весь** туннелируемый трафик.
  Разделения по доменам нет: в управляемый блок `forward_proxy` попадает
  `upstream socks5://127.0.0.1:45000`.
- **Mieru** тоже отправляет через WARP **весь** трафик — одним egress-правилом
  на все домены и все IP, называющим прокси WARP.

При `warp = false` нигде не появляется ни outbound, ни upstream, ни правило
WARP, а egress-правило Mieru остаётся `DIRECT`.

## Жёсткие остановки

Аудит отказывается планировать, а не догадывается. Жёсткая остановка сообщается,
и ничего не меняется:

- AAAA-записи, указывающие вне адресов, которые обслуживает этот хост;
- CAA-записи, не разрешающие Let's Encrypt по HTTP-01;
- неоднозначная топология общего 443 в Nginx или свежий режим на хосте, где уже
  работает stream-роутер;
- публичный слушатель, уже занятый другим сервисом;
- чужой владелец зарезервированного UID или GID (`10002`, `10003`, `10005` и
  группы `101`, `10004`, `10005`);
- существующая база, дерево бинарей, unit, служебный пользователь или слушатель
  x-ui в режиме `managed-new`;
- артефакт, digest которого не совпадает с пином.

## Восстановление, repair, откат и удаление

```bash installer-check
python3 -m installer.cli status --json
python3 -m installer.cli resume --json
python3 -m installer.cli repair --json
python3 -m installer.cli uninstall --json
```

`resume` продолжает по durable-журналу и выполняет каждую зафиксированную
мутацию ровно один раз. `repair` перепроверяет каждый владеемый файл по
записанному digest и отказывается продолжать, если один из них изменился.
`uninstall` удаляет только владеемое поколение и сохраняет учётные данные,
состояние manager и named volumes; `--purge-data` — явное согласие удалить и их,
а для Naive и Mieru — также identity, созданные самим установщиком.

## Отчёты и передача учётных данных

`report` пишет два документа с непересекающимися схемами:

- `report.json`, режим `0644`, содержит только именованные факты приёмки из
  allowlist: состояние health, статус ответа, счётчики байтов, версии и digest,
  владельцев слушателей, SAN сертификатов и результаты маршрутов. Он вообще
  отказывается называть или описывать учётные данные, а факт вне allowlist
  отбрасывается, а не пересказывается.
- `credentials/handoff.json`, режим `0600` внутри каталога `0700`, содержит
  учётные данные, созданные установкой. Публичный отчёт на него не ссылается, не
  цитирует и не пересказывает.

## Обновление существующего 3x-ui

Существующий 3x-ui никогда не обновляется в рамках обычной установки. Это
отдельная, явно вызываемая транзакция: она требует полную записанную byte
identity установки, снимает базу, дерево бинарей и unit как одно поколение,
репетирует миграцию нового бинаря на приватной копии базы до того, как будет
затронута живая база, и восстанавливает всё поколение при любом позднем сбое,
завершаясь отказом, если восстановленная установка не побайтово идентична.

## Лаборатория приёмки релиза

Релиз-кандидат проверяют две одноразовые лаборатории. Ни одна не использует
боевые учётные данные, DNS или SSH-ключи.

```bash
make lab-release RELEASE_ARCHIVE=dist/proxy-control-v0.1.0.tar.gz RELEASE_SHA256=<sha256> LAB_ARCH=amd64
make lab-container RELEASE_ARCHIVE=dist/proxy-control-v0.1.0.tar.gz RELEASE_SHA256=<sha256>
```

Лаборатория QEMU загружает Ubuntu-образ с зафиксированной контрольной суммой и
прогоняет полную матрицу релиза. Контейнерная лаборатория прогоняет ту часть,
которую может доказать одноразовый systemd-контейнер, и записывает, какие
сценарии выполнялись, поэтому частичный прогон никогда не заменяет полный отчёт
релиза. Подробности: [tests/lab/README.md](../tests/lab/README.md).

## Ограничения

- Fleet v1 работает только с Telemt. Он не объявляет и не принимает lifecycle-
  операции Naive, Mieru или 3x-ui.
- Пер-пользовательский учёт Mieru намеренно сообщается как недоступный; квота —
  это скользящая проверка допуска, а не платёжный счётчик.
- MSS clamp для Mieru — диагностическое изменение host firewall. Установщик
  никогда не включает его сам.
- Установщик не разворачивает WARP и не управляет DNS.
