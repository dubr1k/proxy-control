# Proxy Control v0.4.0-beta.1

> **Статус / Status:** Beta — гейт v0.4 в работе (стенд `ams-test`); таблица гейта и живая проверка ниже заполняются по факту. Маршрутизация: egress-политики по узлам и сервисам с честным предпросмотром под backend узла — только то, что spike доказал на стенде. Xray-роутер (v0.5) остаётся дорожной картой. / Beta — the v0.4 gate is in progress on the lab host; the gate table and the live check below are filled in as they pass. Routing: per-node, per-service egress policies with a preview that tells the truth about the node's backend — only what the spike proved on the stand. The Xray router (v0.5) stays roadmap.

## Русский

### Что нового

- **Политика egress на (узел, сервис)** для NaiveProxy и Mieru: «по умолчанию — напрямую | через WARP», «при недоступности WARP — отказать | напрямую», упорядоченные first-match правила (домены, CIDR, порты; блокировать / напрямую / через WARP), оптимистичные ревизии. MTProxy — вне области (`protocol_out_of_scope`). ADR 006 принят.
- **Компилятор и предпросмотр.** Политика компилируется под backend узла — `naive_native` (Caddy forwardproxy `upstream` + `acl`) или `mieru_native` (mita `egress`) — против возможностей, которые объявляет менеджер. Всё, что backend не может выполнить, — `unsupported` с именем правила: у NaiveProxy один upstream на сервис и нет выборочных правил, а forwardproxy не применяет ACL рядом с upstream, поэтому блокировка при WARP по умолчанию не держится; блокировка по порту — ни у кого; loopback и приватные сети можно только блокировать. Недоступный WARP — fail-closed, если политика не выбрала `approved_direct` (тогда это предупреждение в предпросмотре).
- **Egress API менеджеров** (`/v1/egress`, `plan | apply | rollback` на тех же UDS): naive-manager владеет размеченным блоком в `forward_proxy` (рукописный `upstream` перенимается как `custom` и возвращается откатом байт в байт), mieru-manager — секцией `egress` mita (применяется перезапуском — `mita reload` её не подхватывает). CAS по revision, проба доступности провайдера перед применением, readback после reload, журнал последних десяти записей. mieru-manager переходит в сеть хоста ради пробы (по-прежнему `read_only`, `cap_drop: ALL`, без слушателя). ADR 007 принят для нативных backend.
- **Установщик `[egress]`** (`warp`, `warp_port`, `naive`, `mieru`): WARP вынесен из `[three_xui]` (старые ключи читаются с одним предупреждением); `NAIVE_EGRESS_WARP` / `MIERU_EGRESS_WARP` доходят до менеджеров через `.env` и Compose; начальный egress сеется один раз, upgrade и repair его не трогают.
- **Маршрутизация через Fleet v2.** Узел объявляет `egress.v1` и свои egress-цели в `identity`; поколение несёт необязательную секцию `egress` (опускается из проводной формы и digest при отсутствии — узел и центр v0.3 и v0.4 сходятся на любом документе без неё); узел применяет её после ресурсов, идемпотентно по digest, и отчитывается `converged | failed | unsupported`; центр переводит политику в `applied` / `failed` по отчёту. Локальное применение отклоняется, пока узлом управляет центр (`managed_by_central`).
- **`/api/routing/*`** (targets, политика, preview черновика, apply, rollback, history) и аудит `routing.policy.update | apply | rollback | delete`; **экран «Маршрутизация»** с живым предпросмотром, «Применить» только для сохранённой поддерживаемой политики, историей и строкой «Маршрутизация: …» на карточке узла.
- **Стенд.** Tier `routing` (`remote-gate.sh routing`, `fleet-acceptance.py --routing`, `socks5-stub.py`): WARP на весь сервис через журналирующий SOCKS5-stub, блокировки по домену и CIDR при живом cover-сайте, выборочное правило Mieru, откат байт в байт, недоступный провайдер → fail-closed, nginx и nftables не тронуты.
- **Фикс-волна v0.3** (отложенные замечания post-merge): 429/5xx узла не переводят связь в `offline`, эскроу только из отчёта о текущем поколении, `capture` с `purpose: escrow | import`, `DELETE /api/nodes/{id}?force=1`, «применено, ожидает учётные данные», tmpfs `/tmp` менеджеров и агента, единые имена событий аудита.

### Обновление

Обычное обновление, но пересобираются панель **и оба менеджера** (`up -d --build --wait panel naive-manager mieru-manager`; `upgrade` установщика делает это сам); миграция 14 аддитивна; сначала узлы, затем центр; хост, собранный вручную, задаёт `NAIVE_EGRESS_WARP` / `MIERU_EGRESS_WARP` в `.env` сам. Откат — полная предыдущая генерация вместе с базой (образ v0.3 не стартует на схеме 14); откат панели не отменяет применённую политику — сначала «Сбросить» + «Применить». Подробно: `docs/UPGRADING.ru.md`.

## English

### What's new

- **An egress policy per (node, service)** for NaiveProxy and Mieru: «default — direct | through WARP», «when WARP is down — refuse | direct», ordered first-match rules (domains, CIDRs, ports; block / direct / through WARP), optimistic revisions. MTProxy is out of scope (`protocol_out_of_scope`). ADR 006 accepted.
- **Compiler and preview.** The policy is compiled for the node's backend — `naive_native` (Caddy forwardproxy `upstream` + `acl`) or `mieru_native` (mita `egress`) — against the capabilities the manager declares. Whatever a backend cannot enforce is `unsupported` with the rule named: NaiveProxy has one upstream per service and no selective rules, and forwardproxy skips its ACL beside an upstream, so a block cannot hold with a WARP default; block by port — nowhere; loopback and private networks may only be blocked. A WARP that is down fails closed unless the policy chose `approved_direct` (then a preview warning).
- **Egress API of the managers** (`/v1/egress`, `plan | apply | rollback` on the same UDS): the naive-manager owns a marked block inside `forward_proxy` (a hand-written `upstream` is adopted as `custom` and restored verbatim on rollback), the mieru-manager owns mita's `egress` section (applied by a restart — `mita reload` does not pick it up). Revision CAS, a provider reachability probe before apply, a readback after reload, a journal of the last ten entries. The mieru-manager moves to the host network for the probe (still `read_only`, `cap_drop: ALL`, no listener). ADR 007 accepted for the native backends.
- **Installer `[egress]`** (`warp`, `warp_port`, `naive`, `mieru`): WARP moves out of `[three_xui]` (the old keys are still read, with one warning); `NAIVE_EGRESS_WARP` / `MIERU_EGRESS_WARP` reach the managers through `.env` and Compose; the initial egress is seeded once, upgrade and repair leave it alone.
- **Routing over Fleet v2.** A node declares `egress.v1` and its egress targets in `identity`; a generation carries an optional `egress` section (left out of the wire form and the digest when absent — a v0.3 and a v0.4 panel agree on every document without one); the node applies it after the resources, idempotently by digest, and reports `converged | failed | unsupported`; the central moves the policy to `applied` / `failed` from the report. A local apply is refused while a central manages the node (`managed_by_central`).
- **`/api/routing/*`** (targets, the policy, preview of a draft, apply, rollback, history) and the audit events `routing.policy.update | apply | rollback | delete`; **the «Маршрутизация» screen** with a live preview, «Применить» only for a saved supported policy, history, and the line «Маршрутизация: …» on the node card.
- **Lab.** The tier `routing` (`remote-gate.sh routing`, `fleet-acceptance.py --routing`, `socks5-stub.py`): whole-service WARP through a logging SOCKS5 stub, block by domain and CIDR with the cover site alive, Mieru's selective rule, rollback byte for byte, a provider down → fail-closed, nginx and nftables untouched.
- **v0.3 fix wave** (the deferred post-merge findings): a node's 429/5xx no longer turns the link `offline`, escrow only from a report about the current generation, `capture` with `purpose: escrow | import`, `DELETE /api/nodes/{id}?force=1`, «применено, ожидает учётные данные», tmpfs `/tmp` for the managers and the agent, unified audit event names.

### Upgrading

The ordinary upgrade, but the panel **and both managers** are rebuilt (`up -d --build --wait panel naive-manager mieru-manager`; the installer's `upgrade` does it); migration 14 is additive; nodes first, then the central; a host assembled by hand sets `NAIVE_EGRESS_WARP` / `MIERU_EGRESS_WARP` in `.env` itself. Rollback — the complete previous generation, database included (a v0.3 image refuses schema 14); rolling the panel back does not undo an applied policy — «Сбросить» + «Применить» first. Details: `docs/UPGRADING.md`.
