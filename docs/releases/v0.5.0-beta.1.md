## Русский

### Что нового

- **Xray-router.** Один выделенный процесс Xray-core 26.3.27 в контейнере `proxy-control-xray-router` (сеть хоста, identity 10006, read-only, `cap_drop: ALL`) с двумя аутентифицированными SOCKS5-ingress на loopback — `naive` 45101, `mieru` 45102 — и менеджером-супервизором: поколения, посервисный журнал, типизированный egress API на своём UDS. Применение = рендер из intent'ов обоих сервисов → `xray run -test` → swap (≈ 50 мс) → readback → commit; сбой возвращает последнее хорошее поколение, умерший процесс поднимает watchdog, чужой бинарь или geodata держат роутер выключенным (`artifact_mismatch`). `geoip:private → block` первым правилом каждого ingress и `IPOnDemand`: перепривязанное имя не достаёт хост. UDP не ретранслируется. ADR 007 принят для роутера; каждая ячейка возможностей доказана spike'ом на стенде.
- **Подключение и отключение** сервиса — явные действия owner (`POST …/targets/{node}/{protocol}/attach | detach`): сначала секция роутера pass-through, затем `upstream socks5://…@127.0.0.1:45101` у Caddy / `egress` с `socks5Authentication` у mita; отключение — в обратном порядке. Политика никогда не переключает сервис сама; ключ ingress — идентичность сервиса, и он не появляется ни в одном API, аудите, поколении или отчёте.
- **Политика с новыми селекторами.** `geosites`, `geoips`, порты и блокировка рядом с WARP по умолчанию применяются роутером; на нативном backend'е предпросмотр честно называет роутер (`rule_kind_unsupported`). Backend `xray_router` в модели (миграция 15), `compiler_version` 2, новые причины отказа (`router_unavailable`, `not_attached`, `node_lacks_router`, `artifact_mismatch`, `geosite_unknown`, `geoip_unknown`) и предупреждение `router_credential_stale`.
- **Fleet v2.** Узел объявляет `egress.router.v1` и `identity.router`; секция `egress` поколения может нести `backend: xray_router`, `companion` и `passthrough` — всё опускается при отсутствии, узел и центр v0.4 сохраняют свои дайджесты.
- **Установщик.** `[egress] router = true` и выбор `router` для `naive`/`mieru`; адаптер `xray_router` между `warp` и сервисами: архив `Xray-linux-64.zip` из `/var/lib/proxy-control/` (ничего не скачивается), три члена по своим дайджестам, identity 10006, `/var/lib/xray-router`, секреты `secrets/xray-router-*` (root:10006 0440), `.env.xray-router`; проверка — статус менеджера, loopback-only ingress, аутентифицированный CONNECT. Ротация ключей — `rotate-xray-router-ingress`.
- **Экран «Маршрутизация».** Бейдж backend (Caddy / mita / Xray-router), строка роутера с «Подключить к Xray-router» / «Отключить от Xray-router», поля geosite / geoip / порты.
- **Лаборатория.** Tier `router` (`remote-gate.sh router`, `fleet-acceptance.py --router`): router-01…14 — подключение, WARP и блокировка рядом через роутер, порт / geosite / geoip, неизвестный код geodata, Mieru с выборочным правилом, отказ ingress без ключа и с чужим, откат при нетронутом Caddyfile, watchdog после SIGKILL, fail-closed без провайдера, secret-scan API/аудита/базы/логов, ротация, отключение и нетронутый хост. `lab-host` ставит роутер по умолчанию.
- **Фаза 8.** `docs/SECURITY_TEST_MATRIX.md` (каждая строка матрицы Task 39 → тест или сценарий), `BACKUP_RESTORE` с состоянием роутера, замороженные идентификаторы в `tests/test_deploy.py` и `docs/COMPATIBILITY.md`.
- **Фикс-волна v0.4.** Userinfo рукописного `upstream` маскируется в egress-представлениях naive-manager; мёртвый `profile_environment` удалён.

### Обновление

Обычное обновление, роутер оно **не ставит**: `panel/`, `naive_manager/`, `mieru_manager/`, `xray_router_manager/`, `compose*.yaml`, `scripts/`, `VERSION` → `docker compose up -d --build --wait panel naive-manager mieru-manager`; миграция 15 сохраняет каждую строку v0.4; узлы раньше центра. Роутер добавляется установщиком (`[egress] router = true` + архив в `/var/lib/proxy-control/`) или шагами из `INSTALLER_REFERENCE` на хосте, собранном вручную; сервисы подключаются потом, на экране маршрутизации. Откат — предыдущее поколение вместе с базой (образ v0.4 не стартует на схеме 15); перед откатом отключите сервисы от роутера. Подробно: `docs/UPGRADING.ru.md`.

### Установка

**Что нужно.** VPS **x86-64** на **Ubuntu 24.04** с `systemd`, вход обычным пользователем с `sudo`; публичный IPv4 без NAT; свободные TCP/443 и TCP/80 (режим `fresh`) либо свой Nginx `stream` на 443 с одной картой `$ssl_preread_server_name` (режим `coexist`); домены панели и MTProxy (всегда), NaiveProxy и Mieru (по профилю), необязательный домен подписки — с A-записями на этот сервер, без чужих AAAA и без CDN перед MTProxy (сертификаты — Let's Encrypt HTTP-01); для профилей с Mieru — заранее положенные `mita_3.36.0_amd64.deb` и `mieru_3.36.0_amd64.deb`, для роутера — `Xray-linux-64.zip`, всё в `/var/lib/proxy-control/` (URL и SHA-256 — `release/external-artifacts.json`); Python 3.11+ (в Ubuntu 24.04 — 3.12), `curl`, `tar`, `sha256sum`. WARP и роутер необязательны: секция `[egress]` в `install.toml` или вопросы мастера (про роутер мастер спрашивает, только если архив положен).

**Что устанавливается.** Недостающие пакеты Ubuntu (`ca-certificates certbot curl docker-compose-v2 docker.io nginx-full openssl python3` — только они попадают под владение установщика); сертификаты Let's Encrypt с проверкой продления сразу; блок SNI-маршрутов Nginx на общем 443 и TLS-vhost панели; Compose-проект `mtproxy` в `/opt/mtproxy-shared443` (контейнеры `proxy-control-panel`, `-mtproxy` (Telemt), `-mask`, по профилю `-naive-manager`, `-mieru-manager` и `-xray-router`; тома, `secrets/`, мастер-ключ панели); host-службы `caddy-naive.service` (NaiveProxy) и `mita.service` (Mieru) по профилю; бинари роутера в `/usr/local/lib/proxy-control/xray-router` и состояние в `/var/lib/xray-router`; правила UFW — только с вашего разрешения и только на свежем хосте; журнал транзакции, владение и отчёты — `/var/lib/proxy-control/`. Каждый шаг журналируется и откатывается; ничего не меняется до подтверждения digest плана. Полный список — `scripts/install-release.sh --requirements` и [INSTALLER_REFERENCE.ru.md](../INSTALLER_REFERENCE.ru.md).

**Как.** `install-bootstrap` отказывает предрелизным версиям, поэтому бета ставится четырьмя шагами без него (см. [INSTALL.ru.md](../../INSTALL.ru.md)); скрипт [`scripts/install-release.sh`](../../scripts/install-release.sh) делает их сам — без root до проверки байтов, без «скачать и выполнить одной командой»:

## English

### What's new

- **The Xray-router.** One dedicated Xray-core 26.3.27 process in the container `proxy-control-xray-router` (host network, identity 10006, read-only, `cap_drop: ALL`) with two authenticated SOCKS5 ingresses on the loopback — `naive` 45101, `mieru` 45102 — and a supervising manager: generations, a per-service journal, a typed egress API on its own UDS. An apply is render from both services' intents → `xray run -test` → swap (≈ 50 ms) → readback → commit; a failure restores the last known good generation, a dead child is restarted by the watchdog, a foreign binary or geodata keeps the router down (`artifact_mismatch`). `geoip:private → block` first on every ingress and `IPOnDemand`: a rebinding name cannot reach the host. UDP is not relayed. ADR 007 is accepted for the router; every capability cell was proved by the spike on the stand.
- **Attach and detach** are explicit owner actions (`POST …/targets/{node}/{protocol}/attach | detach`): the router's pass-through section first, then Caddy's `upstream socks5://…@127.0.0.1:45101` / mita's `egress` with `socks5Authentication`; detach in the reverse order. A policy never moves a service by itself; the ingress credential is the service's identity and appears in no API, audit, generation or report.
- **Policies with new selectors.** `geosites`, `geoips`, ports and a block beside a WARP default are enforced by the router; on a native backend the preview names the router (`rule_kind_unsupported`). Backend `xray_router` in the model (migration 15), `compiler_version` 2, new reasons (`router_unavailable`, `not_attached`, `node_lacks_router`, `artifact_mismatch`, `geosite_unknown`, `geoip_unknown`) and the warning `router_credential_stale`.
- **Fleet v2.** The node declares `egress.router.v1` and `identity.router`; a generation's `egress` section may carry `backend: xray_router`, `companion` and `passthrough` — all omitted when absent; a v0.4 node and central keep their digests.
- **Installer.** `[egress] router = true` and the choice `router` for `naive`/`mieru`; the adapter `xray_router` between `warp` and the services: `Xray-linux-64.zip` from `/var/lib/proxy-control/` (nothing is downloaded), three members against their own digests, identity 10006, `/var/lib/xray-router`, secrets `secrets/xray-router-*` (root:10006 0440), `.env.xray-router`; verify reads the manager's status, checks loopback-only ingresses and one authenticated CONNECT. Key rotation: `rotate-xray-router-ingress`.
- **The «Routing» screen.** The backend badge (Caddy / mita / Xray-router), the router line with attach/detach, the geosite / geoip / ports fields.
- **The lab.** Tier `router` (`remote-gate.sh router`, `fleet-acceptance.py --router`): router-01…14 — attach, WARP and a block beside it through the router, port / geosite / geoip, an unknown geodata code, Mieru with a selective rule, the ingress refusing a missing or a cross-service key, rollback with the Caddyfile untouched, the watchdog after a SIGKILL, fail-closed without the provider, the secret scan of API/audit/database/logs, rotation, detach and the untouched host. `lab-host` installs the router by default.
- **Phase 8.** `docs/SECURITY_TEST_MATRIX.md` (every row of the Task 39 matrix → a test or a scenario), `BACKUP_RESTORE` with the router's state, frozen identifiers in `tests/test_deploy.py` and `docs/COMPATIBILITY.md`.
- **The v0.4 fix-wave.** The userinfo of a hand-written `upstream` is redacted in the naive-manager's egress views; the dead `profile_environment` is gone.

### Upgrading

The ordinary upgrade, which **does not** install a router: `panel/`, `naive_manager/`, `mieru_manager/`, `xray_router_manager/`, `compose*.yaml`, `scripts/`, `VERSION` → `docker compose up -d --build --wait panel naive-manager mieru-manager`; migration 15 keeps every v0.4 row; nodes before the central. The router is added by the installer (`[egress] router = true` plus the archive in `/var/lib/proxy-control/`) or by the steps in `INSTALLER_REFERENCE` on a hand-assembled host; services are attached afterwards on the routing screen. Rollback: the previous generation together with the database (a v0.4 image does not start on schema 15); detach the services from the router first. Details: `docs/UPGRADING.md`.

### Installing

**Requirements.** An **x86-64** VPS on **Ubuntu 24.04** with `systemd`, a regular user with `sudo`; a public IPv4 without NAT; free TCP/443 and TCP/80 (`fresh`) or your own Nginx `stream` on 443 with one `$ssl_preread_server_name` map (`coexist`); the panel and MTProxy domains (always), NaiveProxy and Mieru (per profile), an optional subscription domain — with A records at this server, no foreign AAAA and no CDN in front of MTProxy (Let's Encrypt HTTP-01); for the Mieru profiles `mita_3.36.0_amd64.deb` and `mieru_3.36.0_amd64.deb`, for the router `Xray-linux-64.zip`, all staged in `/var/lib/proxy-control/` in advance (URLs and SHA-256 in `release/external-artifacts.json`); Python 3.11+ (3.12 on Ubuntu 24.04), `curl`, `tar`, `sha256sum`. WARP and the router are optional: the `[egress]` section of `install.toml` or the wizard's questions (the wizard asks about the router only when the archive is staged).

**What gets installed.** Missing Ubuntu packages (`ca-certificates certbot curl docker-compose-v2 docker.io nginx-full openssl python3` — only those come under the installer's ownership); Let's Encrypt certificates with a renewal dry-run; the SNI route block on the shared 443 and the panel's TLS vhost; the Compose project `mtproxy` in `/opt/mtproxy-shared443` (containers `proxy-control-panel`, `-mtproxy` (Telemt), `-mask`, per profile `-naive-manager`, `-mieru-manager` and `-xray-router`; volumes, `secrets/`, the panel master key); the host services `caddy-naive.service` (NaiveProxy) and `mita.service` (Mieru) per profile; the router's binaries in `/usr/local/lib/proxy-control/xray-router` and its state in `/var/lib/xray-router`; UFW rules only with your consent and only on a fresh host; the transaction journal, ownership and reports in `/var/lib/proxy-control/`. Every step is journaled and reversible; nothing changes before the plan digest is confirmed. The full list: `scripts/install-release.sh --requirements` and [INSTALLER_REFERENCE.en.md](../INSTALLER_REFERENCE.en.md).

**How.** `install-bootstrap` refuses pre-releases, so a beta is installed in four steps without it (see [INSTALL.en.md](../../INSTALL.en.md)); [`scripts/install-release.sh`](../../scripts/install-release.sh) does them for you — no root before the bytes are verified, no «download and run in one line»:

```bash
# by hand: the four files from the release page, then
sha256sum --check SHA256SUMS
tar -xzf proxy-control-v0.5.0-beta.1.tar.gz
cd proxy-control
sudo python3 -m installer.cli wizard

# or with the script (from a clone, or downloaded and read separately):
scripts/install-release.sh --requirements                      # what is needed and what gets installed
scripts/install-release.sh --version 0.5.0-beta.1 --sha256 <lab-sha256 from the gate table>
# --check-only — download and verify only; --no-wizard — extract without running; -- plan --config … --json — a plan without changes
```
