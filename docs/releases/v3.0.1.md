# v3.0.1 — надёжный перевод стека в proxy_panel_by_dubr1k

[English](#english) · **Русский**

Дата: 2026-10-20. Предыдущий выпуск: [v3.0.0](https://github.com/dubr1k/proxy-control/releases/tag/v3.0.0).

## Русский

### Что исправлено

- **Перевод стека больше не останавливает службы, если не уверен, что поднимет их снова.** Обновление 3.0.0 переводит стек из проекта `mtproxy` в `proxy_panel_by_dubr1k` и брало набор файлов Compose из меток работающих контейнеров. На сервере, где в метках остался файл компонента, который на нём не установлен (например, Xray-router), службы после остановки не поднимались ни под новым именем, ни под старым, и их приходилось запускать вручную. Теперь перевод берёт тот же набор файлов, что и обновление и агент обновлений (`PROXY_CONTROL_COMPOSE_FILES`), и до остановки чего-либо проверяет: модель собирается, в ней есть каждая работающая служба, и все пути хоста, которые она монтирует, существуют. Если что-то не так, перевод отказывает, ничего не трогая, и сервер продолжает работать в проекте `mtproxy`.
- **Проверка без изменений.** `sudo bash scripts/migrate-compose-project.sh --check` из распакованного выпуска выполняет все проверки перевода и ничего не меняет.

### Что важно знать

- Серверы, которые уже перешли на 3.0.0 и работают как `proxy_panel_by_dubr1k`, обновляются как обычно; перевод на них ничего не делает.
- Если обновление 3.0.0 остановилось на переводе и службы не поднялись, запустите их в старом проекте так же, как их запускает обновление: `docker compose --project-name mtproxy --project-directory /opt/mtproxy-shared443` с env-файлами `.env*` и файлами из `PROXY_CONTROL_COMPOSE_FILES` (`/etc/proxy-control/version-agent.env`), затем `up -d --no-build --wait`. Данные не пострадали: тома `mtproxy_*` перевод не трогает. После этого обновитесь до 3.0.1.
- Изменились только скрипт перевода и его тесты. Установщик не менялся.

### Новая установка

Используйте Ubuntu 24.04 LTS x86-64 и обычного пользователя с `sudo`, не вход под root. Подготовьте DNS-имена и следуйте [руководству по установке](https://github.com/dubr1k/proxy-control/blob/v3.0.1/README.md#установка-человеком) и [справочнику установщика](https://github.com/dubr1k/proxy-control/blob/v3.0.1/docs/INSTALLER_REFERENCE.ru.md).

В пустом рабочем каталоге:

```bash
curl -fsSLO https://github.com/dubr1k/proxy-control/releases/download/v3.0.1/install-release.sh
curl -fsSLO https://github.com/dubr1k/proxy-control/releases/download/v3.0.1/install-release.sh.sha256
sha256sum --check install-release.sh.sha256
bash install-release.sh
```

Продолжайте только после успешной проверки контрольной суммы.

### Обновление

Сделайте [резервную копию](https://github.com/dubr1k/proxy-control/blob/v3.0.1/docs/BACKUP_RESTORE.ru.md), скачайте и проверьте те же файлы, затем выполните:

```bash
bash install-release.sh --update
```

Порядок обновления флота прежний: сначала узлы, центральная панель последней. Тома Docker, базу и секреты при обновлении не удаляйте. Подробнее: [обновление до 3.0](https://github.com/dubr1k/proxy-control/blob/v3.0.1/docs/UPGRADING.ru.md#обновление-до-30).

## English

### What's fixed

- **Moving the stack no longer stops the services unless it is sure to start them again.** The 3.0.0 update moves the stack from the `mtproxy` project to `proxy_panel_by_dubr1k` and took the set of Compose files from the running containers' labels. On a server whose labels still named a file of a component the server does not have (the Xray-router, say), the services did not come up after the stop, neither under the new name nor under the old one, and had to be started by hand. The move now takes the same set of files as the update and the version-agent (`PROXY_CONTROL_COMPOSE_FILES`) and, before anything stops, checks that the model renders, that it defines every running service and that every host path it mounts exists. If anything is wrong, the move refuses without touching anything and the server keeps running as the `mtproxy` project.
- **A check that changes nothing.** `sudo bash scripts/migrate-compose-project.sh --check` from the unpacked release runs every check of the move and changes nothing.

### Good to know

- Servers already moved by 3.0.0 and running as `proxy_panel_by_dubr1k` update as usual; the move does nothing there.
- If the 3.0.0 update stopped at the move and the services did not come up, start them in the old project the way the update starts them: `docker compose --project-name mtproxy --project-directory /opt/mtproxy-shared443` with the `.env*` files and the files of `PROXY_CONTROL_COMPOSE_FILES` (`/etc/proxy-control/version-agent.env`), then `up -d --no-build --wait`. No data was lost: the move never touches the `mtproxy_*` volumes. Then update to 3.0.1.
- Only the move script and its tests changed. The installer did not change.

### Fresh installation

Use Ubuntu 24.04 LTS x86-64 and a regular user with `sudo`, not a root login. Prepare your DNS names and follow the [installation guide](https://github.com/dubr1k/proxy-control/blob/v3.0.1/README.en.md#installation-by-a-human) and [installer reference](https://github.com/dubr1k/proxy-control/blob/v3.0.1/docs/INSTALLER_REFERENCE.en.md).

In an empty working directory:

```bash
curl -fsSLO https://github.com/dubr1k/proxy-control/releases/download/v3.0.1/install-release.sh
curl -fsSLO https://github.com/dubr1k/proxy-control/releases/download/v3.0.1/install-release.sh.sha256
sha256sum --check install-release.sh.sha256
bash install-release.sh
```

Continue only after checksum verification succeeds.

### Upgrading

Make a [backup](https://github.com/dubr1k/proxy-control/blob/v3.0.1/docs/BACKUP_RESTORE.en.md), download and verify the same files, then run:

```bash
bash install-release.sh --update
```

The fleet update order is unchanged: nodes first, central panel last. Do not delete Docker volumes, the database or secrets as part of an update. More: [upgrading to 3.0](https://github.com/dubr1k/proxy-control/blob/v3.0.1/docs/UPGRADING.md#upgrading-to-30).
