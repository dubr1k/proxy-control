## 1. Термины

| Термин | Что это |
| --- | --- |
| **Узел** (node) | Один хост Ubuntu 24.04 с установленным Proxy Control: панель + Telemt (MTProxy) обязательно, NaiveProxy и/или Mieru по профилю, при желании Xray-router и 3x-ui. |
| **Панель** | Web-интерфейс и API узла (`proxy-control-panel`, FastAPI). Есть на каждом узле; на центре — та же панель. |
| **Центр** (central) | Панель, которая **управляет другими панелями** через их HTTPS-адрес и API-ключ `node-sync` (Fleet v2, с v0.3). Центр — обычный узел со своими протоколами, который дополнительно держит связи. Отдельной «только центральной» сборки нет. |
| **Связанная панель** | Узел, добавленный на центре («Узлы → + Панель»). Учётные записи, которые центр на нём выдал, принадлежат центру; локальные пользователи узла остаются локальными. |
| **Менеджер** | Локальный сервис узла, который единственный пишет конфиг своего протокола: Telemt API (в контейнере `mtproxy`), `naive-manager` (Caddyfile NaiveProxy), `mieru-manager` (конфиг mita), `xray-router` (поколения Xray). Панель разговаривает с ними по Unix-сокетам/токенам и никогда не правит конфиги руками. |
| **Клиент** | Человек или устройство на экране «Клиенты». |
| **Доступ** (grant) | Учётная запись клиента в **одном протоколе на одном узле**. У клиента может быть несколько доступов на разных узлах. |
| **Подписка** | Одна ссылка `https://<домен подписки>/s/<token>`, которая отдаёт все доступы клиента (raw / sing-box / clash / manifest / html). |
| **Поколение** (generation) | Неизменяемый нумерованный документ, который центр компилирует из доступов узла и доставляет ему; узел применяет его и отчитывается. |
| **Политика egress** | Для пары (узел, протокол): весь сервис напрямую или через WARP + упорядоченные правила `block / direct / egress: warp`. Применяется менеджером; на связанном узле — едет в поколении. |
| **Xray-router** | Отдельный Xray на узле (v0.5), к которому NaiveProxy и Mieru **подключаются** явно; он применяет политику с `geosite`/`geoip`/портами. Не имеет отношения к Xray внутри 3x-ui. |

## 2. Итоговая архитектура

### 2.1 Один узел: что на нём работает

```text
                        Интернет
                           │
       TCP/80 ───────► Nginx (http): только ACME HTTP-01 (/.well-known/acme-challenge/), остальное 404
       TCP/443 ──────► Nginx stream: map $ssl_preread_server_name → loopback-бэкенд
                           │
     ┌─────────────────────┼───────────────────────────────────────────────┐
     │ relay.example.com   │ panel.example.com / sub.example.net           │ edge.example.com
     ▼                     ▼                                               ▼
 127.0.0.1:8445        127.0.0.1:8443 Nginx TLS (vhost по server_name)   127.0.0.1:4443
 Telemt (MTProxy)          │ proxy_pass                                  Caddy «caddy-naive»
 Fake-TLS = relay…         ▼                                              forward_proxy + cover-сайт
 не-Telegram → mask    127.0.0.1:8787 панель (HTTP)                          │
 (Caddy cover-сайт)        │ UDS + токены                                     │
                           ├── naive-manager  ──► Caddyfile NaiveProxy ◄──────┘
                           ├── mieru-manager  ──► конфиг mita  ◄── mita (TCP/UDP 46001 публично)
                           ├── xray-router    ──► Xray egress-router (ingress 45101/45102 loopback)
                           └── version-agent  ──► обновления компонентов (root-only агент)

 UDP/443 (только managed 3x-ui) ──► Hysteria2 (Xray 3x-ui)
 xui.example.com / vless.example.com / xhttp.example.com ──► 127.0.0.1:8451 / 8449 / 8450 (3x-ui)
 WARP: cloudflare-warp в proxy-режиме, SOCKS5 127.0.0.1:40000 (по желанию)
```

Полная таблица компонентов:

| Компонент | Где работает | Identity | Слушает | Кто владеет конфигом |
| --- | --- | --- | --- | --- |
| **Nginx** | хост (пакет `nginx-full`) | root | `:80` (http: только ACME-challenge, остальное 404), `:443` (stream, SNI), `127.0.0.1:8443` (TLS панели и подписки) | установщик — один владеемый блок в route-файле общего 443 (`/etc/nginx/stream.d/proxy-control.conf` на свежем хосте) и vhost'ы панели |
| **certbot** | хост | root | — | установщик выпускает lineage'ы Let's Encrypt (HTTP-01 через `/var/www/<домен>`) и проверяет `certbot renew --dry-run` |
| **panel** | контейнер `proxy-control-panel`, Compose-проект `mtproxy` | uid 10001 | `127.0.0.1:8787` | сама панель; данные — том `panel-data` (SQLite + WAL), секреты — `secrets/` проекта |
| **mtproxy (Telemt)** | контейнер `proxy-control-mtproxy` | — | `127.0.0.1:8445` (`MTPROXY_BACKEND_PORT`), API `9091` только внутри Compose-сети | Telemt API (панель — единственный клиент) |
| **mask** | контейнер `proxy-control-mask` (Caddy) | — | 80/443 внутри Compose-сети | cover-сайт для домена MTProxy (`/var/www/<relay-домен>`), куда Telemt отдаёт не-Telegram TLS |
| **NaiveProxy** | хост-служба `caddy-naive.service` (закреплённая сборка Caddy + forwardproxy, `/usr/local/bin/caddy`) | uid 10002 / gid 101 | `127.0.0.1:4443` | `naive-manager` (контейнер, сеть хоста) — `/var/lib/naive-manager/Caddyfile`: блок пользователей, блок учёта, блок egress |
| **Mieru** | хост-служба `mita.service` (закреплённый `/usr/bin/mita` 3.36.0) | user `mita` | публичные `tcp_ports` / `udp_ports` из конфигурации (пример `46001`) | `mieru-manager` (контейнер, сеть хоста; UDS `/run/mita/mita.sock`) |
| **Xray-router** (v0.5, опц.) | контейнер `proxy-control-xray-router` (сеть хоста) | 10006 | `127.0.0.1:45101` (ingress naive), `127.0.0.1:45102` (ingress mieru), SOCKS5 с логином/паролем | `xray_router_manager` — поколения в `/var/lib/xray-router`, бинари в `/usr/local/lib/proxy-control/xray-router` |
| **WARP** (опц.) | хост, пакет `cloudflare-warp` (закреплённая версия) в proxy-режиме | root | `127.0.0.1:40000` SOCKS5 (`warp_port`) | установщик; менеджеры знают его как провайдер `warp` через `NAIVE_EGRESS_WARP` / `MIERU_EGRESS_WARP` / `XRAY_ROUTER_EGRESS_WARP` |
| **3x-ui** (опц.) | хост-служба `x-ui.service`, `/usr/local/x-ui`, база `/etc/x-ui/x-ui.db` | root | панель `127.0.0.1:8451`, VLESS TCP `127.0.0.1:8449`, VLESS XHTTP `127.0.0.1:8450`, Hysteria2 `0.0.0.0:443/udp`, подписка `127.0.0.1:2096` (если задан домен) | 3x-ui сам; установщик — только staged-поколение, панель на loopback и три эталонных inbound (managed-new) |
| **version-agent** (опц.) | хост-служба `version-agent.service`, `/opt/proxy-control/version_agent` | root | `/run/proxy-control/version-agent.sock` | каталог `/etc/proxy-control/versions.json` (allowlist версий) |
| **UFW** (опц., только свежий хост) | хост | root | — | установщик добавляет только свои правила с комментарием и сохраняет правило SSH |

Compose-проект всегда называется `mtproxy` и живёт в `/opt/mtproxy-shared443`; overlays: `compose.yaml` (mask, mtproxy, panel) + `compose.naive.yaml` + `compose.mieru.yaml` + `compose.xray-router.yaml` по профилю. `.env` проекта — root-only, в нём `COMPOSE_FILE=…` с полным набором overlays, `MTPROXY_DOMAIN`, `MTPROXY_BACKEND_PORT`, `PANEL_ALLOWED_HOSTS`, `PANEL_SUBSCRIPTION_HOST/URL`, `NAIVE_PUBLIC_HOST`, `MIERU_PUBLIC_HOST`, `*_EGRESS_WARP`, `*_EGRESS_ROUTER`.

### 2.2 Общий 443: как один порт обслуживает всё

Публичный TCP/443 принадлежит Nginx `stream`. Он **не расшифровывает** TLS — читает SNI (`$ssl_preread_server_name`) и передаёт байты дальше по карте. Установщик пишет ровно один владеемый блок:

```nginx
map $ssl_preread_server_name $proxy_control_backend {
    default            127.0.0.1:8443;   # неизвестное имя → TLS-слушатель панели (ответит 404 / cover)
    relay.example.com  127.0.0.1:8445;   # MTProxy: Telemt сам терминирует Fake-TLS
    panel.example.com  127.0.0.1:8443;   # панель: Nginx TLS → 127.0.0.1:8787
    sub.example.net    127.0.0.1:8443;   # подписка: тот же TLS-слушатель, vhost только /s/
    edge.example.com   127.0.0.1:4443;   # NaiveProxy: Caddy сам терминирует TLS
    vless.example.com  127.0.0.1:8449;   # 3x-ui VLESS Reality TCP (managed-new / existing)
    xhttp.example.com  127.0.0.1:8450;   # 3x-ui VLESS Reality XHTTP
    xui.example.com    127.0.0.1:8451;   # панель 3x-ui (managed-new)
}
```

Следствия, которые нужно помнить:

- **Кто терминирует TLS.** Панель и подписка — Nginx (vhost на `127.0.0.1:8443` с сертификатом lineage `proxy-control`). NaiveProxy — Caddy (lineage `naive`, cover-сайт + `forward_proxy`). MTProxy — Telemt (Fake-TLS под именем `relay…`, не-Telegram трафик уходит в `mask`, где Caddy показывает cover-сайт с настоящим сертификатом). 3x-ui — Xray (Reality: сертификат не нужен; Hysteria2 — свой lineage `three-xui-hysteria`; панель 3x-ui — lineage `three-xui-panel`).
- **Mieru не участвует в 443.** mita слушает свои публичные TCP/UDP-порты напрямую; домен Mieru нужен только как адрес в `mierus://`-ссылках и в подписке (A-запись, без сертификата).
- **На домене панели путь `/s/` всегда 404**, на домене подписки всё, кроме `/s/`, — 404, `access_log off`. Подписчик не узнаёт, где живёт панель; поэтому домен подписки лучше держать **в другой зоне**.
- `host_mode = "coexist"` — тот же блок добавляется в **чужой** уже работающий stream-роутер (на нём должна быть ровно одна понятная `$ssl_preread_server_name`-map); соседние SNI не трогаются и проверяются после установки.

### 2.3 Панель: роли, ключи, секреты, аудит

- **Роли**: `owner` (всё: администраторы, API-ключи, узлы, маршрутизация-apply, reveal), `admin` (пользователи протоколов, клиенты, журнал — без администраторов/ключей), `viewer` (только чтение, без reveal). Сессия — серверная, CSRF на каждую мутацию.
- **API-ключи** (`Администраторы → API-ключи`): scope `admin` (= владелец без сессии, храните как пароль владельца), `monitor` (только чтение), `node-sync` (**только** `/api/fleet/v2/*` — именно его выдают центру). Ключ показывается один раз (`pc_<prefix>_<secret>`), хранится хешем, 120 запросов/мин.
- **Мастер-ключ панели** (`secrets/panel-master-key`, v0.2): шифрует все секреты доступов и ключи узлов в `secret_versions`. Без него узел не может принять поколение центра (`secret_store_disabled`). Резервируется отдельно от базы ([BACKUP_RESTORE](../BACKUP_RESTORE.ru.md)).
- **Аудит**: каждая мутация пишет строку в той же транзакции (actor, действие, цель, request id) — без секретов, ссылок и QR. Экран «Журнал» с фильтрами по исполнителю/действию/цели.
- **Пароли** нигде не печатаются: первый владелец создаётся через stdin; пароль, который вы ввели в мастере, лежит только в приватном файле рядом с конфигурацией и в `credentials/handoff.json` отчёта (0600 в каталоге 0700); сгенерированный bootstrap-пароль — `secrets/panel-bootstrap-password` проекта (root, 0600).

### 2.4 Центр и узлы: общая картина

```text
   Центр (panel.example.com)                        Узел A (panel.node-a.example.org)
   ┌──────────────────────────┐   HTTPS + Bearer     ┌──────────────────────────┐
   │ клиенты, доступы,        │  pc_… (node-sync)    │ /api/fleet/v2/*          │
   │ политики, подписки       │ ───────────────────► │ identity/status/inventory│
   │ node_links, поколения    │  PUT generation      │ PUT generation → reconcile│
   │ heartbeat каждые 15 с    │ ◄─────────────────── │ observed (отчёт)         │
   └──────────────────────────┘                      └──────────────────────────┘
          │ свои протоколы: Telemt/Naive/Mieru как у любого узла
          ▼
   Подписка клиента https://sub.example.net/s/<token> отдаёт доступы на ВСЕХ узлах,
   где у клиента они выданы (рендер из хранилища центра, менеджеры узлов не вызываются).
```

- По связи ходят только типизированные документы: поколение (ресурсы `grant:<id>` с `desired_state`, `credential_ref`, опциями, при v0.4+ секция `egress`), отчёт `observed`, операции `capture`, `versions/update`, `unlink`. Никаких shell/URL/YAML/конфигов.
- Секреты доступов едут **рядом** с документом в том же TLS-запросе (`secrets: {credential_ref: plaintext}`), узел эскроуит их под своим мастер-ключом до применения.
- Один мастер на узел: узел запоминает GUID первого центра, чьё поколение принял, и отвечает `foreign_master` любому другому до отвязки.
- Ключ едет в одну сторону: центр хранит ключ узла зашифрованным; узел не хранит ничего от центра. Компрометация узла не открывает остальных.

### 2.5 Чего в v0.6 нет (чтобы не искать)

- Панель **не управляет клиентами 3x-ui**: доступы (grant) есть только для MTProxy, NaiveProxy и Mieru. 3x-ui ставится, маршрутизируется на 443 и настраивается через его API один раз при установке; его пользователей ведут в самой панели 3x-ui.
- MTProxy вне маршрутизации egress (`protocol_out_of_scope`).
- UDP через Xray-router не ретранслируется (UDP mita остаётся напрямую); правил per-grant нет; регулярных выражений в правилах нет.
- Установщик не управляет DNS и не трогает чужие контейнеры, маршруты и WARP.
- Панель как «чистый центр» без собственного Telemt не заявлена: обзор такого центра отвечает 502 на MTProxy-метрики.

## 3. Домены и DNS

### 3.1 Какие имена нужны одному узлу

| Имя (конфигурация) | Обязательно | Как используется | Сертификат | Куда указывает DNS |
| --- | --- | --- | --- | --- |
| `domains.panel` | да | вход в панель, API узла для центра | lineage `proxy-control` (общий с MTProxy и подпиской) | A (и AAAA только если хост реально слушает IPv6) на IP узла |
| `domains.mtproxy` | да | Fake-TLS-имя MTProxy в `tg://`-ссылках, cover-сайт `mask` | lineage `proxy-control` | A на IP узла, **DNS-only** (CDN-прокси выключен) |
| `domains.subscription` | нет, но рекомендуется | `https://<sub>/s/<token>` | SAN в lineage `proxy-control` | A на IP узла; желательно другая зона |
| `domains.naive` | при `core-naive`/`full` | публичный хост NaiveProxy (`https://edge…`), cover-сайт | lineage `naive` | A на IP узла |
| `domains.mieru` | при `core-mieru`/`full` | адрес в `mierus://`-ссылках (`MIERU_PUBLIC_HOST`) | не нужен | A на IP узла |
| `three_xui.panel_domain` | managed-new | панель 3x-ui через 443 → `127.0.0.1:8451` | lineage `three-xui-panel` | A на IP узла |
| `three_xui.vless_tcp_domain` | managed-new / existing | SNI VLESS Reality TCP → `8449` | не нужен (Reality) | A на IP узла |
| `three_xui.vless_xhttp_domain` | managed-new / existing | SNI VLESS Reality XHTTP → `8450` | не нужен (Reality) | A на IP узла |
| `three_xui.hysteria_domain` | managed-new | Hysteria2 на UDP/443 с TLS | lineage `three-xui-hysteria` | A на IP узла |
| `three_xui.subscription_domain` | нет | подписка 3x-ui → `2096` | lineage `three-xui-subscription` | A на IP узла |

Требования, которые аудит проверяет до плана (жёсткие остановки): A/AAAA указывают именно на этот хост; CAA не запрещает Let's Encrypt; TCP/80 доступен снаружи для HTTP-01; порт 443 свободен (`fresh`) или принадлежит понятному stream-роутеру (`coexist`); все домены **разные**.

### 3.2 Пример распределения имён по парку из трёх хостов

Схема: у каждого хоста своя «витрина» (панель, relay, edge, connect) в своей зоне, чтобы имена узлов не выводились одно из другого; домены подписки — в отдельной зоне, общей для всех клиентов; 3x-ui — только там, где нужен.

| Роль | Хост 1 — **центр** (`example.com`) | Хост 2 — узел A (`node-a.example.org`) | Хост 3 — узел B (`node-b.example.org`) |
| --- | --- | --- | --- |
| профиль | `full` + `router` + `warp` | `full` + `router` + `warp` | `core-naive` + managed 3x-ui |
| панель | `panel.example.com` | `panel.node-a.example.org` | `panel.node-b.example.org` |
| MTProxy (Fake-TLS) | `relay.example.com` | `relay.node-a.example.org` | `relay.node-b.example.org` |
| NaiveProxy | `edge.example.com` | `edge.node-a.example.org` | `edge.node-b.example.org` |
| Mieru | `connect.example.com` (TCP/UDP 46001) | `connect.node-a.example.org` (46001) | — |
| подписка | `sub.example.net` | `sub-a.example.net` (или без: доступы узла A видны в подписке центра) | `sub-b.example.net` (или без) |
| 3x-ui | — | — | `xui.node-b.example.org`, `vless.node-b.example.org`, `xhttp.node-b.example.org`, `hy2.node-b.example.org` |
| WARP | `127.0.0.1:40000` | `127.0.0.1:40000` | — |

Правила распределения:

1. **Одна панель — один набор имён.** Имена не переиспользуются между хостами: сертификаты и `PANEL_ALLOWED_HOSTS` привязаны к хосту.
2. **Домен подписки нужен только там, откуда вы раздаёте ссылки.** Если все клиенты заводятся на центре, достаточно `sub.example.net` на центре: подписка центра рендерит доступы на всех узлах. Подписка узла нужна, если на узле заводят локальных клиентов.
3. **Домен панели узла = адрес узла для центра** (`https://panel.node-a.example.org`). Он должен резолвиться с центра и иметь WebPKI-сертификат (`verify`), либо вы используете `pin` по отпечатку.
4. **Все имена одного хоста → один IP.** Не смешивайте CDN: MTProxy и Reality работают только при прямом соединении.
5. **Порты, которые должны быть открыты снаружи:** `80/tcp`, `443/tcp`, Mieru `tcp_ports`/`udp_ports`, `443/udp` только при managed 3x-ui (Hysteria2), SSH. Именно этот набор (плюс сохранение правила SSH) добавляет установщик в UFW при `manage_ufw = true` на свежем хосте.

## 4. Автоматическое развёртывание узла

Установка транзакционна: `plan` ничего не меняет, `install` применяет только план с подтверждённым digest, каждая мутация журналируется и обратима, приёмка — по настоящим протокольным пробам. Одна и та же процедура — для центра и для узлов.

### 4.1 Требования к хосту

- Ubuntu 24.04 с systemd, root/sudo, доступ в Интернет (пакеты, Let's Encrypt, закреплённые артефакты mita/mieru/Xray/WARP/3x-ui).
- DNS из §3 уже указывает на хост; TCP/80 и TCP/443 достижимы снаружи.
- `fresh`: порт 443 свободен, Nginx поставит установщик. `coexist`: на 443 уже работает Nginx `stream` с одной `$ssl_preread_server_name`-map.
- Свободны loopback-порты 8787, 8443, 8445, 4443, 40000, 45101, 45102 (и 8449–8451, 2096 для managed 3x-ui), UID/GID 10001–10006, 101, 10004 не заняты чужими.
- `managed-new` для 3x-ui — только на хосте **без** существующего x-ui (база, бинарь, unit, пользователь, слушатель — любой из них = отказ).

### 4.3 Мастер: вопросы по порядку

Мастер двуязычный (`--lang ru`), пишет TOML (`--config-output proxy-control.toml`, по умолчанию рядом), показывает план и ждёт подтверждения **первых двенадцати символов digest плана**. Выход на любом вопросе оставляет хост нетронутым. Порядок вопросов:

1. Язык.
2. Режим хоста: `fresh` | `coexist`.
3. Профиль: `core` | `core-naive` | `core-mieru` | `full`.
4. Режим 3x-ui: `none` | `existing` | `managed-new`.
5. Домен панели, домен MTProxy, домен подписки (пусто = публичная подписка выключена).
6. Домен NaiveProxy (если в профиле); домен Mieru и его TCP/UDP-порты (если в профиле).
7. Домены 3x-ui (по режиму): панель, VLESS TCP, VLESS XHTTP, Hysteria2; для `managed-new` ещё логин/пароль панели 3x-ui.
8. WARP: ставить ли (для профилей с Naive/Mieru, кроме managed 3x-ui, где вопрос про WARP-домены).
9. Xray-router: ставить ли; для каждого сервиса — подключить ли его к роутеру сразу (по умолчанию да); для сервисов без роутера — стартовать ли через WARP.
10. ACME-почта.
11. Имя первого владельца панели (оно же bootstrap-пользователь Mieru) и его пароль дважды (пусто = сгенерировать).
12. Управлять ли UFW (только `fresh`, по умолчанию да).

### 4.4 План и digest

План — детерминированный список действий адаптеров с наблюдаемыми фактами: владелец 443 и топология Nginx, DNS/CAA по доменам, свободные порты, коллизии UID/GID, пакеты, lineage'ы сертификатов, маршруты SNI. В плане нет ни одного секрета. `install --accept-plan <digest>` отвергает digest, не совпадающий с только что выведенным планом: подменить одобренный план нельзя.

### 4.5 Что именно ставится, по порядку адаптеров

Адаптеры выполняются в фиксированном порядке; каждый владеет одной границей, каждая мутация — `prepare → apply → verify` в durable-журнале `/var/lib/proxy-control/installer/state.json`; инверсия адаптера восстанавливает то, что он застал.

| # | Адаптер | Что делает | Что появляется на хосте |
| --- | --- | --- | --- |
| 1 | `packages` | ставит **только отсутствующие** из `ca-certificates certbot curl docker-compose-v2 docker.io nginx-full openssl python3`; только они попадают под владение (и удаляются при `uninstall`) | пакеты APT |
| 2 | `nginx` | `fresh`: создаёт `stream`-контекст и `/etc/nginx/stream.d/proxy-control.conf`; `coexist`: добавляет владеемый блок в существующий route-файл; http-vhost'ы на :80 для ACME (`/var/www/<домен>/.well-known/acme-challenge/`, всё остальное 404) | map SNI из §2.2, `nginx -t`, reload |
| 3 | `certificates` | `certbot certonly` HTTP-01 по группам: `proxy-control` (panel + mtproxy + subscription), `naive`, `three-xui-panel`, `three-xui-hysteria`, `three-xui-subscription`; затем `certbot renew --dry-run` | `/etc/letsencrypt/live/<lineage>/` |
| 4 | `firewall` (если `manage_ufw`, только `fresh`) | правила `allow` для 80/tcp, 443/tcp, Mieru tcp/udp-портов, 443/udp при managed 3x-ui, с сохранением правила SSH; правила помечены комментарием и удаляются точечно | UFW включён |

### 4.6 Приёмка, отчёты, где пароли

После `install` выполните:

```bash
cd /opt/mtproxy-shared443 && sudo docker compose ps          # все healthy
curl -fsS -H 'Host: panel.example.com' http://127.0.0.1:8787/healthz
sudo nginx -t && ss -lntup                                    # 443 у nginx, бэкенды на loopback
sudo systemctl is-active caddy-naive mita                     # по профилю
sudo python3 -m installer.cli status --json                   # фаза transaction = done
sudo python3 -m installer.cli report --config proxy-control.toml --output /var/lib/proxy-control/reports
```

`report` пишет публичный `report.json` (0644, только факты приёмки из allowlist — health, версии, digest, SAN, маршруты; **никогда** учётные данные). Где лежат учётные данные:

- пароль владельца панели, введённый в мастере, — в приватном файле `<конфиг>.credentials` рядом с TOML (0600; мастер просит удалить его после установки); сгенерированный (пустой ответ) — в `secrets/panel-bootstrap-password` проекта (root, 0600);
- панель 3x-ui (`managed-new`): адрес с её случайным base path, логин и пароль (введённый в мастере или сгенерированный) — в root-only файле `/var/lib/proxy-control/three-xui/panel-access` (0600, пишется только после того, как панель реально настроена; до этой правки сгенерированный пароль не сохранялся нигде). Штатная утилита 3x-ui на хосте (`/usr/local/x-ui/x-ui setting -show`, `-username`/`-password`) остаётся запасным путём;
- bootstrap-пользователь Mieru (= `initial_user`) — его ссылку выдаёт панель через экран Mieru (одноразовый reveal).

Обязательная ручная приёмка: реальный клиент Telegram через `tg://`-ссылку; вход в панель по HTTPS; соседние SNI (в `coexist`); проверка, что Telemt API (`9091`) не опубликован на хосте.

### 4.7 Первые действия в панели

1. `https://panel.example.com/login` → владелец (`initial_user`).
2. «Администраторы»: создать администраторов ролей `admin`/`viewer` для ежедневной работы; владельца — не для рутины.
3. «Узлы» → карточка «Этот сервер»: здоровье трёх менеджеров, GUID и URL панели — их нужно будет ввести на центре (§6).
4. «Клиенты» → «Импорт существующих», если на хосте уже были пользователи (только чтение, безопасно повторять).
5. «Маршрутизация»: у каждого сервиса виден backend (Caddy / mita / Xray-router), провайдер `warp: доступен` при установленном WARP, `Xray-router: подключён` при `[egress] … = "router"`.

### 4.8 Повторный запуск, resume, repair, uninstall

- Повторный `install` того же плана идемпотентен (наблюдает свой же роутер и поколение).
- Прерванная установка: `sudo python3 -m installer.cli resume --json` (по журналу, каждая мутация ровно один раз). Обрыв SSH (`255`) — не повод запускать вслепую: сначала `status --json`.
- `repair --json`: перепроверяет каждый владеемый файл по digest, отказывает при чужом изменении, перезапускает только свои службы; egress, применённый панелью позже, не переписывает.
- `uninstall --json`: убирает только своё (маршруты, файлы, пакеты, службы), сохраняет тома, мастер-ключ, учётные данные, сертификаты; `--purge-data` — и их (после независимой копии). `managed-new` 3x-ui после `uninstall` без `--purge-data` не переустановится, пока жива `/etc/x-ui/x-ui.db`.

## 5. 3x-ui

Proxy Control относится к 3x-ui как к **соседу на общем 443**: он либо ставит его сам один раз («managed-new»), либо только маршрутизирует SNI на уже стоящий («existing»). Пользователей 3x-ui панель Proxy Control не ведёт.

### 5.1 `managed-new`: что ставится и настраивается

Только на чистом хосте (нет `/usr/local/x-ui`, `/etc/x-ui/x-ui.db`, `x-ui.service`, пользователя/слушателя x-ui).

1. **Артефакт**: закреплённый 3x-ui **3.7.0** (amd64) по пину из `release/external-artifacts.json`, SHA-256 сверяется; staged-поколение хранится в `/var/lib/proxy-control/three-xui`, маркер владения — `/etc/proxy-control/three-xui-owned`.
2. **Файлы**: `/usr/local/x-ui/x-ui`, `/usr/local/x-ui/bin/config.json`, база `/etc/x-ui/x-ui.db`, unit `/etc/systemd/system/x-ui.service`.
3. **Bootstrap в сетевом namespace** (`proxy-control-x-ui`, unit `x-ui-bootstrap`): свежая панель 3x-ui слушает `*:2053`/`*:2096`, но внутри namespace без маршрута наружу. Диалог через API 3x-ui (все учётные данные — через stdin): вход дефолтным `admin`, ротация на ваш логин/пароль, проверка, что дефолтный больше не работает, затем `configure_panel`: web base path (случайный), порт **8451**, `listen 127.0.0.1`, сертификат lineage `three-xui-panel`. Только после этого панель выпускается в обычную сеть — на дефолтном порту она снаружи никогда не была.
4. **Три эталонных inbound** (свежие ключи Reality, short ID и клиентские учётные данные; ничего не копируется с других серверов):
   - `managed-vless-reality-tcp` — VLESS, `tcp`, `reality`, `127.0.0.1:8449`, `serverNames = [vless_tcp_domain]`, Reality `dest = 127.0.0.1:8443` (cover — TLS-слушатель панели Proxy Control, которым владеет установщик и который всегда работает: сторонний сайт может сменить сертификат или пропасть, и Reality сломается у всех сразу), `externalProxy = {vless_tcp_domain:443}` (чтобы подписка 3x-ui не рекламировала loopback-порт), sniffing `routeOnly`;
   - `managed-vless-reality-xhttp` — то же на `127.0.0.1:8450`, `xhttpSettings.path = "/assets/"`, `mode = auto`;
   - `managed-hysteria2-tls` — `hysteria` v2 на `0.0.0.0:443/udp`, TLS lineage `three-xui-hysteria`, ALPN `h3`, `externalProxy = {hysteria_domain:443}`.
5. **Маршруты** на общем 443: `vless_tcp_domain → 8449`, `vless_xhttp_domain → 8450`, `panel_domain → 8451`, при `subscription_domain` → `2096`.
6. **WARP** (`warp = true`): в Xray 3x-ui добавляется SOCKS-outbound на `127.0.0.1:40000` и правила `routing` для `warp_domains` (`geosite:<код>` или `domain:<имя>`); всё остальное — напрямую; финальная политика добавляется после и не заменяется. Это **доменный** WARP, в отличие от NaiveProxy/Mieru, где WARP — весь сервис.
7. **Приёмка**: staged-бинарь сообщает закреплённую версию; эффективная конфигурация совпадает с шаблонами; панель слушает только `127.0.0.1:8451`; все обещанные inbound слушают (8449, 8450, 443/udp). Тест-прогон гейта v0.6 (`managed-xui`) ставит настоящий 3x-ui 3.7.0 и проверяет это на стенде.
8. **Клиенты 3x-ui**: заходите по адресу из `/var/lib/proxy-control/three-xui/panel-access` (`https://xui.node-b.example.org/<случайный base path>/`, там же логин и пароль) и ведёте пользователей там; подписка 3x-ui — по своему домену/2096, если задан.

### 5.2 `existing`: только маршруты

Установщик читает базу существующего 3x-ui **только для аудита**, находит VLESS-inbound'ы по сети (`tcp`, `xhttp`), требует, чтобы они слушали **loopback** (иначе делить 443 невозможно), и добавляет маршруты `vless_tcp_domain → 127.0.0.1:<порт inbound>` и т. д. Файлы, база, inbound'ы 3x-ui не трогаются; обновление существующего 3x-ui — отдельная явная транзакция с репетицией миграции на копии базы ([INSTALLER_REFERENCE](../INSTALLER_REFERENCE.ru.md)).

### 5.3 Два разных Xray

| | Xray внутри 3x-ui | Xray-router Proxy Control |
| --- | --- | --- |
| зачем | inbound'ы VLESS/Hysteria2 для клиентов 3x-ui | egress-роутер для NaiveProxy и Mieru |
| где | `/usr/local/x-ui/bin/`, процесс `x-ui.service` | `/usr/local/lib/proxy-control/xray-router`, контейнер `proxy-control-xray-router`, identity 10006 |
| версия | та, что в 3x-ui 3.7.0 (Xray 26.7.28) | закреплённый Xray-core 26.3.27 |

| пересекаются | нет: разные бинари, каталоги, identity, порты | |

## 6. Центр и узлы: привязка панелей

### 6.1 Порядок раскатки парка

1. Все панели парка — **одна сборка** (узел строго проверяет документ поколения: узел на старой сборке отвечает 422 незнакомому полю, панель v0.2 не имеет `/api/fleet/v2/*` вообще). При обновлении: **сначала узлы, потом центр** ([UPGRADING](../UPGRADING.ru.md)).
2. Ставьте узлы по §4; центр — так же (он тоже узел). Совместимость по версиям — [COMPATIBILITY](../COMPATIBILITY.md).
3. Если хост обновляли rsync'ом, а не установщиком, файл `VERSION` должен лежать в каталоге проекта — иначе узел сообщает центру `dev`.

### 6.2 Подготовка узла

**Обязательно** — ключ `node-sync`:

1. На панели узла (владелец): «Администраторы» → «API-ключи» → «Создать ключ»: имя (например, `central`), scope **`node-sync`**, срок действия по желанию.
2. Ключ `pc_<8 hex>_<43 символа>` показывается **один раз** — скопируйте сразу; в базе остаётся только префикс и SHA-256.
3. «Узлы» → карточка «Этот сервер» показывает GUID панели и URL для ввода на центре (`https://panel.node-a.example.org`).

**По желанию** — `version-agent`, чтобы вкладка «Обновления» карточки узла на центре умела обновлять Telemt/Caddy/mita:

```bash
# из распакованного релиза на узле
sudo install -d -m 0755 /opt/proxy-control && sudo cp -r version_agent /opt/proxy-control/version_agent
sudo install -d -m 0750 /etc/proxy-control
sudo install -o root -g root -m 0644 deploy/version-agent.service /etc/systemd/system/version-agent.service
sudo install -o root -g root -m 0644 deploy/proxy-control-version-agent.tmpfiles.conf /etc/tmpfiles.d/proxy-control-version-agent.conf
sudo install -o root -g root -m 0600 deploy/version-agent.env.example /etc/proxy-control/version-agent.env
sudo install -o root -g root -m 0600 deploy/version-catalog.example.json /etc/proxy-control/versions.json
# в version-agent.env: путь проекта и ПОЛНЫЙ список overlays; в versions.json — только проверенные вами версии
sudo systemd-tmpfiles --create /etc/tmpfiles.d/proxy-control-version-agent.conf && sudo systemctl daemon-reload
sudo systemctl enable --now version-agent && sudo systemctl is-active version-agent
sudo curl --fail --unix-socket /run/proxy-control/version-agent.sock http://version-agent/v1/health
```

Каталог версий — allowlist (Telemt только `@sha256:` образы, Caddy/mita только HTTPS + SHA-256), панель его расширить не может.

### 6.3 Привязка: три действия на центре

«Узлы» → **«+ Панель»**:

1. **Имя** (как узел будет называться на центре), **URL** (`https://panel.node-a.example.org`; только `https://`, можно порт и базовый путь, без query), **API-ключ** (тот `pc_…`), **проверка TLS**:
   - `verify` (по умолчанию) — сертификат узла строится до системного хранилища, как в браузере (Let's Encrypt подходит);
   - `pin` — SHA-256 листового сертификата; «Получить отпечаток» покажет digest по URL — сверьте его с тем, что показывает сама панель узла. Для самоподписанных/лабораторных. Режима «не проверять» нет.
   - Частный/loopback/`*.local` адрес — только с «Разрешить приватный адрес».
2. **«Проверить»** — центр вызывает `identity`, `status`, `inventory` узла этим ключом, ничего не сохраняя, и показывает: GUID, версию панели, протоколы и здоровье демонов, latency, список учётных записей узла с чекбоксами для импорта. Отказы явные: «панель не говорит на Fleet API v2» (404 — старая сборка), «уже управляется другим центром» (`master_guid` чужой), «уже подключена здесь», «это та же панель», «узел отверг ключ» (401/403), «недоступна».
3. **«Добавить»** — одна транзакция: `fleet_nodes` (node_id = GUID узла, `transport = panel`), `node_links` (URL, режим TLS, отпечаток, флаг приватного адреса), ключ зашифрован под мастер-ключом центра (`purpose = node-api-key`). Ключ больше никогда не показывается (`has_api_key: true`). Отмеченные пользователи импортируются сразу (§6.4).

Связь стартует в `unknown` и становится **online** на первом heartbeat (≤ `PANEL_FLEET_HEARTBEAT_SECONDS`, по умолчанию 15 с; событие `node.up` в `GET /api/events`). Узел запомнит центр как мастера при **первом принятом поколении**, а не при добавлении — подключённая панель, которой ещё ничего не прислали, никем не управляется.

То же по API (только владелец):

```bash
# отпечаток (для режима pin)
curl -sS -X POST https://panel.example.com/api/nodes/fingerprint -H "Authorization: Bearer $ADMIN_KEY" \
  -H 'Content-Type: application/json' -d '{"url":"https://panel.node-a.example.org"}'
# проверка без записи
curl -sS -X POST https://panel.example.com/api/nodes/test -H "Authorization: Bearer $ADMIN_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"display_name":"node-a","url":"https://panel.node-a.example.org","api_key":"pc_…","tls_verify":"verify","allow_private_address":false}'
# добавление → 201 {"node_id": "<guid>"}
curl -sS -X POST https://panel.example.com/api/nodes/link -H "Authorization: Bearer $ADMIN_KEY" -H 'Content-Type: application/json' -d '{…то же тело…}'
```

(`$ADMIN_KEY` — ключ scope `admin` центра; через браузерную сессию тот же диалог делает это с CSRF.)

### 6.4 Импорт существующих пользователей узла

Из диалога добавления или позже: карточка узла → вкладка **«Пользователи»** → отметить → **«Импортировать выбранных»**.

1. Центр читает `inventory` узла; пользователи, у которых здесь уже есть доступ, помечены `already_linked` и пропускаются; пользователь, которым владеет **другой** центр, отклоняется (двух мастеров у учётной записи не бывает).
2. Центр запрашивает у узла текущие учётные данные (`credentials/capture`) **до записи**: MTProxy и NaiveProxy отдают секрет; **Mieru хранит только хеш** — такие возвращаются `unsupported`.
3. Одна транзакция: клиент на каждого пользователя (или привязка к выбранному существующему клиенту в колонке «Куда»), доступ с `origin = imported`, наблюдаемым состоянием и опциями runtime (у MTProxy — host/port ссылки Telemt), версия секрета там, где он вернулся, строка аудита `node.import` (имена, никогда секреты), поколение.
4. При следующем push узел **присваивает** этих пользователей (`managed_resources`) без единого вызова адаптера: ничего не создаётся, не ротируется, не удаляется.

Импортированный Mieru-доступ без секрета в подписке показывается как `unsupported: no stored credential`; подписку клиенту с таким доступом нельзя создать/ротировать, пока вы не нажмёте **«Ротация»** — узел выпустит новый пароль (старая `mierus://`-ссылка перестанет работать).

Одинаковое имя в разных протоколах — только подсказка: три `alice` в трёх менеджерах по умолчанию становятся тремя клиентами; объединяйте вручную.

### 6.5 Карточка узла и ежедневная проверка

Карточка связанной панели: **транспорт** (online/offline, latency, последний heartbeat, `last_error` — класс и код, никогда тело ответа), **демоны** (`ok | down | off` по протоколам из health узла), версия панели узла, пользователи (центр против локальных), best-effort трафик, поколение `desired` против `applied` с пометкой, пока есть недоставленные изменения. Вкладки **Обзор / Пользователи / Обновления** (версии от version-agent узла, обновление компонента → `POST /api/nodes/{id}/versions/{component}`; отказ узла возвращается как 502 `node_rejected`).

Действия владельца: **Пауза / Возобновить** (heartbeat и доставка пропускают узел; абоненты работают), **Проверить** (heartbeat + доставка сейчас), **Изменить** (имя, URL, ключ, TLS — новый ключ становится новой строкой секрета, старая отзывается), **Удалить**.

Цикл центра каждые 15 с: `identity` + `status` → при `config_dirty` — `PUT generation` с секретами только этого узла → `202` опрашивается через `observed`. Backoff после `failed`/непоправимого отказа: 30 с → 60 с → … → 10 мин, сбрасывается новым поколением или `converged`. Норма на экране «Узлы»: все карточки `online`, `desired = applied`, `last_error` пуст.

### 6.6 Отвязка, удаление, ротация ключа

- **Удалить на центре** (`DELETE /api/nodes/{id}`): отказ 409, пока на узле остаётся хоть один *выданный* доступ (включая ещё не подтверждённые удаления) — сначала удалите доступы клиентов и дождитесь отчёта `missing`. *Импортированные* доступы удалению не мешают и **освобождаются** (остаются на узле локальными). Затем центр говорит узлу забыть мастера (best effort, аудит `node.unlink` с `node_released`), удаляет ключ, связь и поколения.
- **Отвязать на узле** («Этот сервер» → «Отвязать», `POST /api/nodes/local/unlink`): узел забывает мастера, учётные записи центра становятся локальными, runtime не меняется. Центр об этом не узнаёт — удалите узел и там, иначе следующее поколение снова сделает его мастером.
- **Ротация ключа**: новый `node-sync` на узле → «Изменить» на центре → выключить/удалить старый на узле. Если выключить старый без обновления центра — узел уйдёт в `offline` (`node.down`) на следующем heartbeat, больше ничего не изменится.

## 7. Клиенты, доступы и подписки из центра

### 7.1 Модель

- **Клиент** заводится на центре («Клиенты» → «Новый клиент»: имя; состояние активен / приостановлен / в архиве меняется кнопками карточки).
- **Доступ** = (клиент, узел, протокол, `runtime_username`, опции). Узел — «Этот сервер» или любая связанная панель. Опции: MTProxy — лимиты/квота; NaiveProxy — квота; Mieru — квоты (`quotas: []` = без квоты).
- Секрет доступа хранится в `secret_versions` центра (шифрование мастер-ключом) с версиями `pending → active → retiring → revoked`.
- **Операция** выдачи журналируется и заканчивается ровно одним из: `succeeded`, `compensated` (созданное этой операцией удалено; существовавшее до неё не трогается), `manual_intervention_required` (продолжить: `python -m panel.cli operations-resume <id>` внутри контейнера панели). Для связанных панелей есть промежуточное `pending_remote`.

### 7.2 Выдать доступ на узел из центра (пошагово)

1. «Клиенты» → карточка клиента → **«Выдать доступы»**.
2. Выбрать **узел** (этот сервер или связанная панель), отметить **протоколы** (MTProxy / NaiveProxy / Mieru — только те, что на узле включены и `ok`), ввести **имя учётной записи** (общее для всех выбранных протоколов на этом узле; менеджеры NaiveProxy и Mieru выводят удалённые имена из оборота навсегда — не переиспользуйте имена).
3. **Локальный узел**: панель вызывает менеджеры, один результат на все протоколы, затем **одноразовый** диалог «Доступы выданы» со всеми ссылками/QR (по той же ссылке больше не откроется). Позже ссылку отдаёт подписка клиента (§7.3) или ротация доступа («Ротировать» на чипе — новый секрет, старая ссылка перестаёт работать); на экранах протоколов узла MTProxy и NaiveProxy умеют аудитируемый повторный показ, Mieru — только новую ссылку через ротацию.
4. **Связанная панель**: доступ, его секрет `pending` и новое поколение пишутся одной транзакцией; операция ждёт `pending_remote`, чип доступа показывает **«ожидает узел»**. Pusher доставляет поколение на ближайшем heartbeat (или нажмите «Проверить» на карточке узла); узел создаёт учётную запись через свой менеджер и отчитывается `enabled`; тогда операция завершается и одноразовый набор ссылок становится доступен. Telemt возвращает свою Fake-TLS-форму секрета (`ee…`) и публичные host/port — центр эскроуит именно их, поэтому `tg://`-ссылка совпадает с той, что отдаёт сам узел.
5. Проверить: чип доступа `enabled`, в карточке узла `desired = applied`, в «Журнале» центра — `grant.provision.start` и `client.*`/`grant.*`; на узле в его собственной панели этот пользователь помечен «управляется центром» и локально не редактируется (409 `managed_by_central`).

### 7.3 Подписка клиента

- Включить на панели, откуда раздаются ссылки: `domains.subscription` при установке (→ `PANEL_SUBSCRIPTION_URL`). Без него endpoint выключен.
- Карточка клиента → **«Подписка»** → «Создать URL»: ссылка `https://sub.example.net/s/<token>` и QR показываются один раз; в базе — только хеш токена. «Ротировать URL» выпускает новый токен, старый отвечает 404 в той же транзакции; «Отозвать» — 404 без замены. В диалоге видно, какие доступы в подписку попадут, и вариант ссылки под клиента.
- Одна ссылка отдаёт **все** доступы клиента на всех узлах: `?format=raw` (строки-ссылки), `singbox` (outbound'ы naive + mieru; `&client=singbox` — только naive для официального sing-box ≥ 1.13), `clash` (mieru для mihomo), `manifest` (типизированный JSON), `html` (страница с QR и матрицей совместимости). Что клиент не умеет — в `unsupported` с причиной, а не сломанная ссылка.
- Кэширование: `ETag` по эффективному набору доступов, `If-None-Match` → 304, `Profile-Update-Interval: 12`, 60 запросов/мин с адреса. Ротация credential доступа ссылку подписки не меняет — клиент заберёт новую конфигурацию при обновлении.
- Ссылка — bearer-секрет: не вставляйте её в тикеты; она не попадает в логи (uvicorn без access log, `access_log off` в Nginx) и в аудит.

### 7.4 Включить / выключить / ротировать / удалить

На центре — с экрана «Клиенты», одинаково для локальных и удалённых доступов; разница только в том, что удалённое изменение **декларативно** (новое поколение, менеджер узла вызывает сам узел):

| Действие | Локальный узел | Связанная панель |
| --- | --- | --- |
| Выключить / Включить | менеджер сразу | `desired_state` в поколении → узел → `observed_state` |
| Ротация | менеджер сразу, новый секрет `active` | новая версия `pending`, текущая `retiring`; узел ротирует по изменившемуся `credential_ref`; после отчёта — `active`/`revoked` |
| Удалить | менеджер удаляет; имя выведено из оборота (Naive/Mieru) | `desired_state = deleted` → узел удаляет и отчитывается `missing` → центр вычищает строку и отзывает секреты |
| Приостановить / Возобновить клиента | все доступы клиента выключаются / включаются | то же, через поколение |
| В архив | все доступы клиента → `deleted`; клиент в архиве | то же, через поколение |

Операция, ожидавшая доступ, удалённый до применения узлом, завершается `compensated`, а не ждёт вечно. Ссылки после ротации Mieru — только новые.

### 7.5 Локальные клиенты узла

Узел остаётся полноценной панелью: на нём можно заводить своих клиентов и доступы «Этот сервер» — они локальные, центр их видит в `inventory` как `local` и может импортировать (§6.4). Один писатель на ресурс: локальная учётная запись не трогается центром, центральная — узлом.

## 8. Маршрутизация egress и Xray-router

### 8.1 Модель политики

Одна политика на (узел, протокол); экран «Маршрутизация» или `/api/routing/*`:

```text
default_action   direct | egress        default_egress   warp
fallback         fail_closed | approved_direct
rules[]          enabled, action: direct | block | egress(warp),
                 match: {domains[], geosites[], cidrs[], geoips[], ports[]}, note
backend          naive_native | mieru_native | xray_router
```

- Домены: `example.com` — хост, `*.example.com` — поддомены (у mita оба = суффикс); CIDR нормализуются; `geosite:`/`geoip:`/порты — только на backend `xray_router`; `geoip:private` не принимается (роутер блокирует приватное сам).
- ≤ 128 правил, ≤ 64 селекторов каждого вида, ≤ 32 портов, скомпилированный документ ≤ 16 КиБ.
- Приватные назначения (loopback, RFC 1918, CGNAT, link-local, `localhost`) можно только `block`.
- `revision` растёт при каждом сохранении; `applied_revision`/`applied_digest` — что стоит на узле. «Применено» = `state = applied` **и** `applied_revision = revision`.
- `fallback = approved_direct` — единственный способ обменять fail-closed на доступность: недоступный WARP компилируется в `direct` с предупреждением.

Что умеет каждый backend:

| Сервис / backend | Весь сервис direct/WARP | `block` домен/CIDR | выборочные `direct`/`egress` | порты, geosite, geoip | block рядом с WARP-умолчанием |
| --- | --- | --- | --- | --- | --- |
| NaiveProxy `naive_native` (Caddy `upstream` + `acl`) | ✓ | ✓ | ✗ (один upstream) | ✗ | ✗ (forwardproxy не применяет ACL при upstream) |
| Mieru `mieru_native` (`egress` mita) | ✓ | ✓ | ✓ по домену/CIDR | ✗ | ✓ |
| NaiveProxy/Mieru, **подключённые к Xray-router** | ✓ | ✓ | ✓ | ✓ | ✓ |
| MTProxy | — вне области | | | | |

### 8.2 WARP на узле

- Установщиком: `[egress] warp = true` → `cloudflare-warp` в proxy-режиме на `127.0.0.1:40000`, в `.env` — `NAIVE_EGRESS_WARP=socks5://127.0.0.1:40000`, `MIERU_EGRESS_WARP=…`, `XRAY_ROUTER_EGRESS_WARP=…`.
- Вручную собранный хост задаёт эти переменные в `.env` сам ([UPGRADING](../UPGRADING.ru.md) v0.4) и пересоздаёт менеджеры.
- Без них цель показывает `warp: не настроен`, любая WARP-политика в предпросмотре — `provider_unavailable`. WARP, который не отвечает на SOCKS5-приветствие, — `provider_unreachable` / `egress_unreachable`, ничего не применяется (fail-closed).
- Сам WARP отказывает loopback и RFC 1918 назначениям — поэтому компилятор их и не открывает.

### 8.3 Настроить политику: локальный узел

1. «Маршрутизация» → узел «Этот сервер» → вкладка NaiveProxy или Mieru. В карточке: backend (Caddy / mita / Xray-router), провайдер `warp: доступен`, строка роутера.
2. Умолчание: «Напрямую» или «Через WARP»; «При недоступности WARP»: отказать (fail-closed) / напрямую.
3. Правила: «Добавить правило» → домены / CIDR (и geosite / geoip / порты для роутера), действие (Блокировать / Напрямую / Через WARP), заметка; порядок ↑/↓ или перетаскиванием — правила first-match.
4. **Предпросмотр** справа обновляется на каждое изменение: скомпилированный документ, digest, diff относительно узла, нужен ли перезапуск (mita — да; Caddy — reload), причины `unsupported` с привязкой к правилу, предупреждения (`adopts_unmanaged_upstream` — рукописный `upstream` будет перенят с сохранением оригинала для отката; `policy_empty`).
5. **«Сохранить»** (revision+1) → **«Применить»** (активна только для сохранённой поддерживаемой политики; только owner): панель просит менеджер `plan` + `apply` с `operation_id = routing:<policy>:<revision>`; менеджер проверяет провайдера, пишет свой блок, перезагружает/перезапускает сервис, читает конфиг обратно и держит предыдущую запись в журнале. Бейдж → «применено (rev N)».
6. **«Откатить»** — предыдущая запись журнала менеджера; **«История»** — `routing_applies`; **«Сбросить»** = напрямую без правил; **«Удалить политику»** — только когда узел работает «напрямую, без правил».

Что менеджер пишет (NaiveProxy):

```text
# BEGIN NAIVE-MANAGER EGRESS
upstream socks5://127.0.0.1:40000
acl {
    deny example.com *.example.com 10.0.0.0/8
}
# END NAIVE-MANAGER EGRESS
```

Mieru: секция `egress` конфига mita (`proxies` с эндпоинтом WARP, `rules` с `domainNames`/`ipRanges`/`action`), применяется перезапуском mita (сессии переподключаются один раз).

### 8.4 Настроить политику: связанная панель из центра

То же самое, только узел выбирается в списке (карточка показывает версию: «узел нужно обновить до v0.4» для старых). При «Применить» скомпилированный документ становится секцией `egress` **следующего поколения** узла (`state = applying`); узел применяет её после ресурсов через свои менеджеры, отчитывается `converged | failed | unsupported`, центр переводит политику в `applied`/`failed` по отчёту (один heartbeat). Пока узлом управляет центр, его собственный экран маршрутизации отказывает в применении (`managed_by_central`) — применяйте на центре. Отвязка узла egress не трогает.

### 8.5 Xray-router: подключить сервис и применить политику

Предпосылка: узел поставлен с `[egress] router = true` (или роутер добавлен позже по [XRAY_ROUTER](../XRAY_ROUTER.ru.md)); в карточке — `Xray-router: доступен`, версия Xray.

1. **Подключить**: карточка сервиса → **«Подключить к Xray-router»** (owner; подтверждение: сессии сервиса прервутся). Порядок внутри: роутер получает секцию сервиса как pass-through (напрямую, без правил) → менеджер сервиса переводит свой блок на ingress роутера (Caddy `upstream socks5://<user>:<pass>@127.0.0.1:45101`, mita `egress` с `socks5Authentication`). Существующая нативная политика переносится на backend `xray_router` **черновиком**; нативная политика с правилами, которая всё ещё применена, подключаться отказывается (`policy_applied`) — сначала «Сбросить» + «Применить». Узел, посеянный `[egress] naive = "router"`, уже подключён.
2. Теперь у правил доступны `geosite:`, `geoip:`, порты; блокировка работает рядом с WARP по умолчанию. Роутер резолвит `IPOnDemand`, первое правило каждого ingress — `geoip:private → block` (не отключается).
3. «Сохранить» → «Применить»: менеджер роутера рендерит поколение *n+1* из intent'ов **обоих** сервисов, `xray run -test` (неизвестный код geodata — `geosite_unknown`/`geoip_unknown`), swap ~50 мс (прерывает сессии обоих сервисов), readback, commit; предыдущее поколение остаётся для отката.
4. **Отключить** — в обратном порядке (нативный блок обратно напрямую, секция роутера в pass-through). На связанной панели attach/detach едут одним поколением с companion-документом; узел без `egress.router.v1` отвечает `node_lacks_router`.

Примеры политик (как их видит `PUT /api/routing/policies/{node}/{protocol}` и экран):

```jsonc
// 1. NaiveProxy на нативном Caddy: весь сервис через WARP, локальные сети закрыты
{"backend":"naive_native","default_action":"egress","default_egress":"warp","fallback":"fail_closed",
 "rules":[{"enabled":true,"action":"block","match":{"cidrs":["10.0.0.0/8","192.168.0.0/16"]},"note":"private"}]}

// 2. Mieru на mita: напрямую, но список доменов через WARP, рекламные — заблокировать
{"backend":"mieru_native","default_action":"direct","fallback":"fail_closed",
 "rules":[{"enabled":true,"action":"egress","egress":"warp","match":{"domains":["*.example.net"]},"note":"via warp"},
          {"enabled":true,"action":"block","match":{"domains":["ads.example.com","*.ads.example.com"]}}]}

// 3. NaiveProxy, подключённый к Xray-router: по умолчанию WARP, geosite/geoip/порты, блок рядом с WARP
{"backend":"xray_router","default_action":"egress","default_egress":"warp","fallback":"approved_direct",
 "rules":[{"enabled":true,"action":"block","match":{"geosites":["category-ads-all"]},"note":"ads"},
          {"enabled":true,"action":"direct","match":{"geoips":["cloudflare"],"ports":["443"]},"note":"cdn direct"},
          {"enabled":true,"action":"block","match":{"ports":["25","465","587"]},"note":"no smtp"}]}
```

`POST /api/routing/policies/{node}/{protocol}/preview` (с черновиком в теле) показывает, что из этого backend применит; `…/apply` с `expected_revision`; `…/rollback`; `POST /api/routing/targets/{node}/{protocol}/attach|detach`.

### 8.6 Причины отказа предпросмотра (что делать)

| Причина | Что делать |
| --- | --- |
| `provider_unavailable` | на узле нет `*_EGRESS_WARP` — поставьте WARP / задайте `.env` и пересоздайте менеджеры |
| `provider_unreachable` | WARP не отвечает — `warp-cli status` на узле; либо `fallback = approved_direct` |
| `rule_kind_unsupported` / `backend_capability_missing` | нативный backend этого не умеет — подключите сервис к Xray-router |
| `not_attached` | политика для роутера, сервис не подключён — «Подключить» |
| `router_unavailable` / `artifact_mismatch` / `router_unreachable` | роутер не установлен / бинарь или geodata не совпадают с пином / ingress не отвечает — `docker logs proxy-control-xray-router`, healthcheck `--status` |
| `node_lacks_egress_v1` / `node_lacks_router` | связанная панель старше v0.4 / v0.5 без роутера — обновите узел |
| `private_destination` | правило `direct`/`egress` называет приватную сеть — только `block` |
| `policy_conflict` (409) | кто-то сохранил параллельно — перечитайте |
| `managed_by_central` (409) | egress этого узла ведёт центр — применяйте там |
| `manual_intervention_required` (503) | менеджер не смог вернуть конфиг после расхождения readback — резервные копии в `/var/lib/naive-manager/backups` / журнале mieru-manager; роутер `phase: broken` → устранить причину и `docker compose … restart xray-router` |

### 8.7 Проверка после применения

- Бейдж «применено (rev N)»; на карточке узла на «Узлах» — строка «Маршрутизация: naive → WARP, 2 блокир.; mieru → напрямую».
- `curl --proxy https://edge.example.com --proxy-user <user>:<pass> https://<заблокированная цель>` → отказ; разрешённая цель → 200; cover-сайт `https://edge.example.com/` по-прежнему 200.
- Клиент Mieru — то же; `nginx -T` и `nft list ruleset` не изменились (маршрутизация их не трогает).
- Роутер: `docker exec proxy-control-xray-router python -m xray_router_manager.healthcheck --status` → `artifacts.*.verified == true`, `phase == "idle"`; `ss -ltnp 'sport = :45101 or sport = :45102'` — только `127.0.0.1`.
- Аудит: `routing.policy.update | apply | rollback | delete`, `routing.target.attach | detach` на панели, которая применяла.

## 9. Обновления, резервные копии, откат

- **Обновление панели** узла: новый релиз тем же путём (§4.2) — установщик перерисовывает владеемые файлы, миграции базы применяются при старте панели (схема 15 в v0.6); порядок парка — узлы, затем центр; откат — полная предыдущая генерация вместе с базой (образ старой версии отказывается стартовать на новой схеме). Управляемый центром узел перед откатом отвяжите. Подробно — [UPGRADING](../UPGRADING.ru.md), [COMPATIBILITY](../COMPATIBILITY.md).
- **Обновление компонентов** (Telemt / Caddy / mita) — из панели через `version-agent` («Версии» на узле, «Обновления» в карточке узла на центре) с откатом при любой ошибке и блокировкой `rollback_failed` до вмешательства оператора.
- **Резервная копия** ([BACKUP_RESTORE](../BACKUP_RESTORE.ru.md)): online-бэкап SQLite панели (том `panel-data`), **мастер-ключ отдельно**, `secrets/` проекта и `.env*`, `/var/lib/naive-manager`, `/var/lib/mieru-manager`, `/var/lib/xray-router`, конфиги Nginx, `/etc/letsencrypt`, ownership-манифест `/var/lib/proxy-control/`; восстановление — сначала `python -m panel.cli master-key-verify`, потом старт панели. Сценарий `backup-restore` гейта v0.6 проходит этот путь целиком на стенде.
- **Ротация ключей ingress роутера**: `sudo /usr/local/libexec/rotate-xray-router-ingress [naive] [mieru]`.

## 10. Сквозные чек-листы

### 10.1 Парк с нуля (центр + два узла)

1. DNS по §3.2 для всех трёх хостов (A-записи, DNS-only, CAA разрешает Let's Encrypt).
2. Хост 1 (центр): §4.2 → мастер (`full`, `warp`, `router`, `subscription = sub.example.net`) → план → digest → приёмка → первый вход, администраторы.
3. Хосты 2 и 3: то же со своими TOML (узел B — `core-naive` + managed 3x-ui).
4. На каждом узле: ключ `node-sync` (§6.2), при желании `version-agent`.
5. На центре: «Узлы → + Панель → Проверить → Добавить» для узла A и узла B (§6.3); дождаться `online`.
6. Импорт существующих пользователей узлов, если были (§6.4).
7. Клиент на центре → «Выдать доступ» на узел A (Naive + Mieru) и на узел B (Naive) → дождаться `enabled` (§7.2) → «Подписка» → ссылка клиенту (§7.3).
8. Маршрутизация: на узле A подключить Naive и Mieru к Xray-router (если не посеяно), применить политики (§8.5); проверить (§8.7).
9. Резервная копия всех трёх хостов (§9). Записать в приватный журнал: домены, версии, digest релиза, кто где мастер.

### 10.2 Добавить узел в существующий парк

Установить узел на **той же** сборке, что центр → `node-sync` → «+ Панель» → импорт → выдать доступы → политика egress → бэкап.

### 10.3 Выдать доступ клиенту на другом узле

«Клиенты» → клиент → «Выдать доступ» → узел → протоколы → имя → дождаться «enabled» → показать ссылки один раз или отдать подписку.

### 10.4 Включить WARP для сервиса на узле

Убедиться, что на узле есть WARP (`warp: доступен`) → «Маршрутизация» → узел → сервис → «По умолчанию: Через WARP» → предпросмотр без `unsupported` → «Сохранить» → «Применить» → проверка `curl --proxy`.

### 10.5 Вывести узел из парка

Удалить/архивировать доступы клиентов на узле → дождаться `missing` → «Удалить» узел на центре (импортированные освобождаются) → при необходимости отозвать ключ `node-sync` на узле → узел продолжает работать самостоятельно со своими локальными пользователями.
