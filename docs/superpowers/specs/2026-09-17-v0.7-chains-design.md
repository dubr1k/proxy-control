# Proxy Control v0.7 — цепи выходов и маршрутизация на каждого клиента

Дата: 2026-09-17. Ветка: `feature/vnext-v0.7-chains` (от `feature/vnext-v0.6-verification`,
`55cd862`). Поручение владельца (2026-09-17): «клиент — это я: я отправляю трафик через AMS_Z,
который отправляет трафик на ams-test … я могу настраивать так, чтобы конкретно мой трафик
маршрутизировался … какой-то трафик по правилам geosite/geoip гонять на сервер, какой-то
пускать через внутренний WARP — важно удобно настраивать цепи … и для каждого созданного
клиента на сервере это должно настраиваться; приступай, проверяй, выкладывай». Решения ниже
приняты автономно по этому поручению; всё, что спека обещает, доказано спайком
[`docs/spikes/CHAINS_PER_CLIENT.md`](../../spikes/CHAINS_PER_CLIENT.md) на `ams-test`.

## 1. Цель

Оператор описывает для узла **выходы** — напрямую, WARP узла, блок, **через другой узел парка**
(и что тот узел делает дальше: напрямую, свой WARP, следующий узел) — и правила first-match по
доменам, `geosite`, CIDR, `geoip`, портам, каждое из которых ведёт в один из выходов. Политика
существует не только на сервис узла, но и **на отдельного клиента** (его доступ на этом узле):
у доступа своя «полоса» (lane) со своим умолчанием и своими правилами. Всё это — на одном
экране, с предпросмотром «куда пойдёт этот домен», применяется транзакционно менеджерами,
доставляется на связанные панели поколениями Fleet v2 и откатывается, как в v0.4–v0.5.

Релиз `v0.7.0-beta.1` включает целиком:

- **полосы (lanes)** на Xray-router: учётка SOCKS на полосу на тех же ingress-портах
  (`svc:naive`, `svc:mieru` — полоса сервиса; `grant:<id>` — полоса доступа), правила Xray по
  `user`; менеджер роутера выпускает и хранит ключи полос, панель раздаёт их менеджерам;
- **relay-inbound** на каждом узле с роутером: `vless`+`reality` на выделенном публичном порту,
  прикрытие — TLS-слушатель собственной панели; учётные записи на пару (узел-источник, выход);
- **выходы `node:<guid>`** и **цепи** из нескольких узлов (`proxySettings` Xray) — из политики
  любого узла на любой узел парка с `relay.v1`, ключи раздаёт центр поколениями;
- **NaiveProxy на полосу**: naive-manager рендерит `forward_proxy`-обработчик на полосу;
- **Mieru на полосу**: экземпляр mita на полосу из пула слотов установщика (`mita@<n>.service`);
- модель политики v3 (`lane`, `exit`, `chains`), компилятор, цели, экран «Маршрутизация и цепи»,
  переключатель полосы на «Клиентах», подписка с портом полосы для Mieru;
- Fleet v2: возможности `egress.lanes.v1`, `relay.v1`; секция `relay` поколения; отчёт;
- установщик: `[egress] relay_port`, `[mieru] lane_slots`, UFW, обновление v0.6 → v0.7;
- гейт: tier'ы `routing`/`router`/`fleet`/`ui` расширены, новый сценарий `chains` в `lab-host`
  (два узла на стенде: `lab-host` + второй роутер из дерева), матрица сверки без пробелов;
- живая проверка AMS_Z → ams-test (роутер на AMS_Z ставится по решению владельца в этом
  поручении), заметка о выпуске, публикация.

### Не входит в v0.7

- UDP через полосу/цепь (ingress `udp: false`, как в v0.5); MTProxy — вне маршрутизации.
- Полосы для клиентов, чьи протоколы живут в 3x-ui, — 3x-ui остаётся чужим.
- Балансировка между выходами, health-based failover, автоматический выбор выхода.
- Полоса на клиента в **обоих** протоколах сразу — полоса привязана к доступу (протокол + узел);
  у клиента с Naive и Mieru на одном узле две полосы, каждая настраивается отдельно (или
  копируется кнопкой «как у …»).
- Цепь длиннее 3 узлов (вход + 2 хопа) — ограничение спеки, не техники.

## 2. Словарь

| Термин | Определение |
| --- | --- |
| **Выход** (`Exit`) | Куда роутер отдаёт соединение: `direct`, `warp` (WARP этого узла), `block`, `node` (через узел парка, с указанием, что делает узел-выход: `direct` или `warp`, либо следующий узел). |
| **Цепь** (`Chain`) | Упорядоченный список хопов `[B, C]` + выход последнего (`direct`/`warp`). Цепь длины 1 — «через узел B». Рендерится как `vless`-outbound на B; для C — outbound на C с `proxySettings.tag` = outbound B (Xray набирает C через B). |
| **Полоса** (`Lane`) | Идентичность трафика на роутере: учётка SOCKS на ingress сервиса. `svc:<protocol>` — полоса сервиса (существует всегда, это сегодняшняя учётка ingress), `grant:<id>` — полоса доступа клиента. У каждой полосы своя политика. |
| **Relay** | `vless`+`reality` inbound роутера на публичном порту `relay_port`; учётные записи `relay:<source_guid>:<exit>` (`direct` \| `warp`), по паре на узел-источник. Прикрытие Reality — `127.0.0.1:8443` (TLS-vhost панели), `serverNames = [домен панели узла]`. |
| **Слот Mieru** | Один из N демонов `mita@<n>` (порт `46100+n`, UDS `/run/mita/lane-<n>.sock`, состояние `/var/lib/mita/lanes/<n>/`), которые установщик держит запущенными «вхолостую»; mieru-manager назначает слот полосе. |

## 3. Архитектурные решения

1. **Полоса = учётка ingress, не порт.** Xray различает `user` внутри одного `socks`-inbound
   (спайк S2); порты ingress не меняются (45101/45102), ключи полос живут у менеджера роутера
   (`/var/lib/xray-router/lanes.json`, 0600), панель получает ключ **один раз** при создании
   полосы и передаёт его менеджеру сервиса тем же способом, каким сегодня ключ ingress лежит в
   `upstream` Caddy / `socks5Authentication` mita. Ни один API-ответ, аудит, поколение и отчёт ключ
   не несёт (маска `***@`).
2. **Выход через узел — это relay-учётка на узле-выходе.** Узел-выход не знает политики
   источника; он знает только «учётка `relay:A:warp` выходит в мой WARP, `relay:A:direct` —
   напрямую (в том числе к следующему хопу)». Ключи выпускает **центр** (панель, у которой оба
   узла — «Этот сервер» или связанные): создаёт UUID пары, кладёт их в поколение узла-выхода
   (секция `relay`) и в `chains` intent'а узла-источника (секция `egress`). Цепь A→B→C: у A
   учётки на B и на C; B видит соединение к C как «direct» (C — публичный адрес).
3. **Reality без сертификатов и DNS.** Prикрытие — TLS-слушатель панели узла на `127.0.0.1:8443`
   (всегда работает, настоящий сертификат), `serverName` = домен панели узла-выхода. Порт —
   выделенный публичный `relay_port` (по умолчанию `45443`; UFW открывает его установщик). Пара
   ключей Reality и `shortId` — менеджер роутера при первом включении relay (`POST /v1/relay`),
   публичная часть — в `identity.router.relay`.
4. **Fail-closed, как раньше.** Умолчание или правило `node:B` при недостижимом relay B
   (TCP + Reality-рукопожатие не проходят) — `egress_unreachable` до любых изменений;
   `fallback = approved_direct` превращает это в предупреждение и `direct`. Полоса без роутера на
   узле — `lane_requires_router`; выход `node` на нативном backend'е — `rule_kind_unsupported`.
5. **Naive-полосы — обработчики в одном сайте** (спайк S1): менеджер владеет блоком
   `# BEGIN NAIVE-MANAGER ROUTE … # END` внутри `route { }` и рендерит по `forward_proxy` на
   полосу (пользователи полосы + `upstream socks5://<lane-user>:<key>@127.0.0.1:45101`), полосу
   сервиса — последней со всеми остальными пользователями. Изменение — reload Caddy, как сегодня.
   Прежние блоки USERS/EGRESS переезжают внутрь ROUTE при первом старте v0.7 (адопция с копией
   оригинала для отката).
6. **Mieru-полосы — слоты** (спайк S3): mita не различает пользователей в egress, поэтому полоса
   Mieru = свой демон. Установщик поднимает пул `mita@1..N` (`[mieru] lane_slots`, по умолчанию 4
   при `router = true`), каждый с портом `46100+n` (TCP; UDP полосы не получают), UDS и
   состоянием; mieru-manager назначает слот полосе, применяет туда конфиг (пользователи полосы,
   egress → ingress роутера с ключом полосы) и управляет им тем же кодом, что и основным
   демоном. Свободный слот — `IDLE` (порт закрыт). Ссылка `mierus://` доступа в полосе несёт порт
   слота: перенос доступа между полосами = новая ссылка (подписка обновится сама).
7. **Область политики — (узел, протокол, полоса).** Таблица `routing_policies` получает `lane`
   (`svc` по умолчанию); у доступа — `routing_lane` (`null` = полоса сервиса, `own` = своя
   полоса `grant:<id>`). Компилируется в один intent роутера на сервис со списком полос — роутер
   применяет сервис целиком (одно поколение), как в v0.5.
8. **Совместимость.** Узел v0.6 без `egress.lanes.v1` получает поколение без полос и без
   `chains` (центр отказывает политике с полосами/цепями для него: `node_lacks_lanes`,
   `node_lacks_relay`); intent схемы 1 остаётся принимаемым роутером v0.7; поколение без секции
   `relay` сохраняет digest v0.6.

## 4. Xray-router v0.7 (`xray_router_manager`)

### 4.1 Intent схемы 2

```jsonc
{"schema": 2,
 "lanes": {
   "svc:naive":  {"default": {"action": "direct", "egress": null}, "rules": [...]},
   "grant:7f3a…": {"default": {"action": "egress", "egress": "chain:c1"},
                   "rules": [{"geosites": ["category-ads-all"], "action": "block"},
                             {"geoips": ["ru"], "action": "direct"},
                             {"domains": ["*.example.net"], "action": "egress", "egress": "warp"}]}},
 "chains": {"c1": {"hops": [{"guid": "…", "address": "panel.node-b.example.org", "port": 45443,
                            "server_name": "panel.node-b.example.org", "public_key": "…",
                            "short_id": "…", "uuid": "…"}],
                   "exit": "warp"}}}
```

- Словарь полосы — словарь схемы 1 (`action` ∈ `direct | block | egress`, `egress` ∈ `warp |
  chain:<id>`; в `default` — без `block`): панель говорит `exit`, роутер — `action/egress`.
- Ровно одна полоса `svc:<сервис>`; полосы `grant:<id>`; ≤ 32 полос, ≤ 16 цепей, 1–3 хопа;
  селекторы и лимиты — как в схеме 1; документ ≤ 64 КиБ.
- `uuid` хопа — секрет; intent хранится в поколениях роутера (0600) как и ключи ingress; в
  `GET /v1/egress/{svc}` и diff'ах — `redact_intent` (маска `***`).
- Схема 1 принимается и трактуется как одна полоса `svc:<сервис>` (`lanes_of`).

### 4.2 Рендер

- На ingress сервиса — по учётке на полосу (`accounts: [{user: "svc:naive", pass}, {user:
  "grant:…", pass}]`); правила: `geoip:private → block`, `localhost → block` на inbound, затем
  для каждой полосы `{"inboundTag": [svc], "user": [lane], …селекторы…, "outboundTag": …}` по
  порядку правил и catch-all полосы; полоса сервиса — последней.
- Outbound'ы: `block`, `direct`, `warp` (если используется), на каждую цепь: хоп 1 —
  `vless`+`reality` (`tag: chain:c1:1`), хоп 2 — `tag: chain:c1:2` с `proxySettings: {"tag":
  "chain:c1:1"}`; outbound цепи — её последний хоп; выход цепи задаётся тем, какая учётка
  (`relay:A:direct`/`relay:A:warp`) использована на последнем хопе — центр кладёт в `uuid` хопа
  нужную.
- Relay-inbound (если включён): `{"tag": "relay", "listen": "0.0.0.0", "port": relay_port,
  "protocol": "vless", "settings": {"clients": [{"id": uuid, "email": "relay:<src>:<exit>"}]},
  "streamSettings": {"security": "reality", "realitySettings": {"dest": "127.0.0.1:8443",
  "serverNames": [panel_domain], "privateKey", "shortIds"}}, "sniffing": {"routeOnly": true}}`;
  правила: `inboundTag relay + ip geoip:private → block`; `user relay:*:warp → warp`;
  `user relay:*:direct → direct`.
- Проверка `xray run -test`, swap, readback, журнал, откат — без изменений (v0.5).

### 4.3 API менеджера

| Маршрут | Назначение |
| --- | --- |
| `POST /v1/lanes/{svc}` `{lane}` → `{user, password}` (один раз) | выпустить/перевыпустить ключ полосы; хранится в `lanes.json`; учётка появляется на ingress со следующим поколением |
| `DELETE /v1/lanes/{svc}/{lane}` | забыть полосу (учётка исчезает) |
| `GET /v1/lanes/{svc}` | список полос (без ключей) |
| `POST /v1/relay` `{server_name, port}` → `{public_key, short_id, port, server_name}` | включить relay (ключ Reality — один раз на узел, хранится в `relay.json` 0600) |
| `PUT /v1/relay/accounts` `{accounts: [{email, uuid}]}` | заменить набор relay-учёток (из поколения центра) |
| `GET /v1/relay` | публичная часть + счётчик учёток |
| `GET/POST /v1/egress/{svc}/plan|apply|rollback` | как в v0.5, принимает схему 1 и 2 |
| `GET /v1/status` | + `lanes`, `relay: {enabled, port, accounts}`, `capabilities` + `lanes`, `chains`, `relay` |

Проверка достижимости хопа перед `apply`: TCP-connect к `address:port` и Reality-рукопожатие
через собственный тестовый запуск (`xray run -test` не ходит в сеть; менеджер делает один
`vless`-dial к хопу с таймаутом 3 с через временный outbound — «`egress_unreachable: chain c1 hop
1`»).

## 5. Менеджеры сервисов

### 5.1 naive-manager: блок ROUTE

```text
route {
    # BEGIN NAIVE-MANAGER ROUTE
    forward_proxy {              # полоса grant:7f3a…
        basic_auth alice <pass>
        hide_ip
        hide_via
        probe_resistance
        upstream socks5://grant%3A7f3a…:<key>@127.0.0.1:45101
    }
    forward_proxy {              # полоса сервиса svc:naive — всегда последняя
        basic_auth bob <pass>
        basic_auth carol <pass>
        hide_ip
        hide_via
        probe_resistance
        upstream socks5://svc%3Anaive:<key>@127.0.0.1:45101     # или acl-блок нативной политики
    }
    # END NAIVE-MANAGER ROUTE
    file_server
}
```

- `PUT /v1/lanes` `{lanes: [{lane, users: [...], upstream: {user, password}}]}` — менеджер
  перерисовывает блок ROUTE; полоса сервиса берёт `upstream`/`acl` из своей egress-записи, как
  сегодня. Reload Caddy; readback; журнал — та же транзакция, что `egress.apply`.
- Пользователь может быть только в одной полосе; полосы с пустым списком пользователей не
  рендерятся. Нативная политика (`acl`) применяется только к полосе сервиса; полоса доступа
  всегда подключена к роутеру (сервис должен быть подключён: иначе `not_attached`).
- Учёт трафика (`log naive_accounting`) не меняется: `user_id` тот же.
- Адопция при первом старте v0.7: блоки USERS/EGRESS внутри одного `forward_proxy` переносятся в
  ROUTE как полоса сервиса; оригинал сохраняется в `backups/`.

### 5.2 mieru-manager: слоты

- Менеджер знает слоты из env `MIERU_LANE_SLOTS="1:46101:/run/mita/lane-1.sock:/var/lib/mita/lanes/1,…"`
  (пишет установщик); каждый слот — отдельный `MitaClient` с тем же кодом (`observe`, `apply`,
  `start/stop`, `status`).
- `PUT /v1/lanes` `{lanes: [{lane, users: [...], upstream: {user, password}}]}` → назначение
  слота (первый свободный; `lane_slots_exhausted` при нехватке), конфиг слота = `portBindings
  [{port, TCP}]`, `users` полосы (те же `hashedPassword` из основного конфига — пароль не
  меняется, ссылка меняется только портом), `egress` → `SOCKS5_PROXY_PROTOCOL 127.0.0.1:45102` с
  `socks5Authentication` полосы, правило `* → PROXY`; основной демон теряет этих пользователей
  (`mita reload`). Освобождение полосы — обратный перенос и `stop` слота.
- `GET /v1/lanes` → `{lanes: [{lane, slot, port, users, status}], free_slots}`.
- `share_template` доступа получает порт слота → панель перерисовывает ссылку и подписку;
  экран «Клиенты» предупреждает «ссылка Mieru изменится» при переносе.

## 6. Панель

### 6.1 Модель (`panel/routing/models.py`, схема базы 16)

```text
routing_policies + lane TEXT NOT NULL DEFAULT 'svc'      -- 'svc' | 'grant:<id>'; UNIQUE(node_id, protocol, lane)
access_grants   + routing_lane TEXT NULL                  -- NULL (полоса сервиса) | 'own'
relay_peers(node_id, source_node_id, exit, secret_id, created_at)   -- центр: учётки relay, выданные узлу-выходу
router_relays(node_id, port, public_key, short_id, server_name, enabled, updated_at)  -- что узел сообщил
```

- `Exit`: `direct | warp | block | {"node": "<guid>", "via": "direct"|"warp"} |
  {"chain": ["<guid>", "<guid>"], "via": "direct"|"warp"}` (в JSON `exit`; поле `egress` схемы
  v0.4 принимается как алиас `exit: "warp"`, `action` — как раньше).
- `RoutingRule.exit` вместо пары `action/egress` (обратная совместимость в `PolicyInput`:
  старые тела принимаются и нормализуются; API отдаёт обе формы до v0.8).
- Компилятор: для backend `xray_router` собирает **один intent на сервис** из всех полос
  (`svc` + полосы доступов этого узла/протокола, у которых `routing_lane = 'own'`), строит
  `chains` из `relay_peers`/`router_relays` (адрес = домен панели узла-выхода, порт из
  `router_relays`), проверяет: узел-выход ≠ узел-источник, нет циклов, у каждого хопа есть
  `relay.v1` и учётка, длина ≤ 3. Причины: `node_lacks_relay`, `relay_disabled`,
  `relay_credential_pending` (учётка ещё не доставлена узлу-выходу), `chain_loop`,
  `chain_too_long`, `lane_requires_router`, `lane_not_attached`.
- Для нативных backend'ов полосы и `node`-выходы — `unsupported` с причиной, называющей роутер.

### 6.2 Сервис маршрутизации и цели

- `GET /api/routing/targets` — на цель добавляются `lanes: [{lane, grant_id, client, policy}]`,
  `exits: [{kind: direct|warp|node, node_id, display_name, reachable, via: [direct, warp]}]`.
- `PUT/GET/DELETE /api/routing/policies/{node}/{protocol}` получают `?lane=` (по умолчанию
  `svc`); `POST …/preview|apply|rollback` — тоже. Apply полосы = apply сервиса (один intent);
  `routing_applies` хранит `lane`.
- `POST /api/clients/grants/{grant_id}/lane` `{mode: "service"|"own"}` — включить/выключить
  полосу доступа: панель создаёт ключ полосы у роутера (`POST /v1/lanes/{svc}`), передаёт его
  менеджеру сервиса (`PUT /v1/lanes`), создаёт политику полосы (черновик «как у сервиса») и
  публикует поколение для связанной панели. Аудит `grant.lane.enable|disable` (без ключей).
- **Relay-учётки**: `POST /api/routing/relay/{node}/enable` (owner; узел с роутером) →
  `POST /v1/relay` локально или через поколение (`relay.enable` в секции `relay`); при первом
  использовании выхода `node:B` из узла A центр создаёт пару UUID (`relay_peers`), кладёт их в
  поколение B (`relay.accounts`) и, когда B отчитался `converged`, разрешает apply на A (до тех
  пор `relay_credential_pending`).

### 6.3 Экран «Маршрутизация и цепи»

- Слева — узел и сервис (как сегодня); **сверху карточки — «Выходы узла»**: чипы `Напрямую`,
  `WARP (доступен/нет)`, `Блок` и по чипу на каждый узел парка с relay: `→ node-b (доступен,
  12 мс)` с переключателем «дальше: напрямую | WARP node-b | → node-c».
- **Полосы**: вкладки `Сервис` и по одной на доступ со своей полосой (`alice · grant 7f3a`),
  кнопка «Добавить полосу для клиента…» (выбор доступа этого узла/протокола).
- Редактор правил: колонка «Куда» — выпадающий список выходов (с цепью в подписи:
  `→ node-b → WARP`), селекторы как в v0.5.
- **Проверка домена**: поле «Куда пойдёт…» — ввод `youtube.com` (или IP/порт) → «полоса
  grant:… → правило 2 (geosite:youtube) → node-b → WARP node-b» — считает компилятор по
  сохранённой политике, без обращения к узлу.
- Предпросмотр/применить/откат/история — как в v0.5, с `lane` в бейдже.
- На «Клиентах» у чипа доступа: «Маршрут: как у сервиса ▾ / своя полоса» → переход на
  экран цепей на нужную вкладку; для Mieru — подтверждение «ссылка изменится».
- На «Узлах» в строке маршрутизации карточки: «naive: 3 полосы, выходы: WARP, → node-b».

## 7. Fleet v2

- `identity.capabilities` += `egress.lanes.v1`, `relay.v1`; `identity.router.relay =
  {enabled, port, public_key, short_id, server_name}`; `identity.router.lanes = {naive: [...],
  mieru: [...]}`.
- Поколение: `egress[p].document` — intent схемы 2 (роутер) или нативный документ; новая
  секция `relay: {enabled: bool, server_name, port, accounts: [{email, credential_ref}]}` —
  UUID едут в `secrets` push-запроса; опускается из проводной формы и digest при отсутствии.
  Узел применяет `relay` до `egress`.
- Отчёт `observed.relay = {state, accounts, public_key, port}`; `observed.egress[p].lanes`.
- Полосы доступов на связанной панели: центр при `mode: own` кладёт в поколение ресурс доступа
  с полем `lane: "own"` (поле ресурса, не `options` — модели опций строгие; опускается из
  проводной формы при отсутствии); узел сам создаёт ключ полосы у своего роутера и переносит
  пользователя (Naive: обработчик; Mieru: слот) — ключи не покидают узел. Полоса на узле
  называется по ресурсу (`grant:<id>`) — так же её называет intent центра. Центр видит порт
  слота Mieru в `learned.share_template`; при возврате в сервис узел сообщает шаблон основного
  демона (`service_share_template` из `/v1/lanes` mieru-manager).

## 8. Установщик

- `[egress] relay_port = 45443` (при `router = true`; UFW `allow 45443/tcp`); адаптер

  `46101…4610N/tcp`, `MIERU_LANE_SLOTS` в `.env.mieru`; приёмка: каждый слот `IDLE`, сокет 0770.

## 9. Безопасность

- Ключи полос и UUID relay — секреты: живут у менеджеров (0600) и в эскроу центра
  (`secret_versions`, `purpose = relay-account`), маскируются в diff/API/аудите/отчётах; secret-scan
  лаборатории знает их формы (`socks5://grant%3A…:…@`, `"id": "<uuid>"` в intent).
- Relay-inbound принимает только известные UUID; Reality отбивает чужие рукопожатия на
  прикрытие (панель) — сканер видит TLS панели. `geoip:private → block` на relay — приватные
  назначения недоступны и для узлов парка.
- Полоса доступа не может назначить выход, которого нет у узла; узел-выход не может быть самим
  собой; учётки relay ротируются `POST /api/routing/relay/{node}/rotate` (новая пара, старая
  отзывается после доставки обоим узлам).
- Порт relay — публичный; при отключении relay менеджер закрывает inbound, установщик — UFW.

## 13. Решения, принятые за владельца

1. Порт relay — выделенный `45443`, а не SNI на 443: без нового домена и сертификата, Reality с
   прикрытием панели; UFW открывает установщик.
2. Полоса — на доступ (протокол + узел), не на клиента целиком: у клиента с двумя протоколами две
   полосы (кнопка «скопировать правила из …»).
3. Mieru-полосы через пул слотов установщика (N демонов), а не динамические юниты: менеджер в
   контейнере без systemd; свободные слоты `IDLE`.
4. Цепь ≤ 3 узлов; выход последнего — `direct` или его `warp`.
5. Ключи relay выпускает центр и доставляет поколениями; узел-выход хранит только «свои» учётки.
6. Нативные backend'ы (Caddy `acl`, `egress` mita) остаются для полосы сервиса без роутера;
   полосы и `node`-выходы требуют подключения к роутеру.
