# Proxy Control v0.4 — маршрутизация исходящего трафика (capability-limited routing)

Дата: 2026-09-14. Ветка: `feature/vnext-v0.4-routing` (от `feature/vnext-v0.3-fleet-v2`,
`v0.3.0-beta.1`). Уточняет Phase 6 (Tasks 26–31A) из [спеки vNext](2026-09-10-proxy-control-vnext-design.md)
и переводит [ADR 006](../../adr/006-routing-policy-ir.md) из `proposed` в `accepted` — см. раздел 13
«Отклонения». Решения приняты автономно по поручению владельца (2026-09-14: «приступай к работе
над версией 0.4, принимай решения автономно, всё проверяешь на ssh ams-test; также можешь тестить
на AMS_Z»).

## 1. Цель

Оператор из web-интерфейса (локально или с центральной панели) задаёт, **куда уходит трафик
клиентов** каждого прокси-сервиса узла — напрямую или через WARP-туннель узла — и какие
назначения **заблокированы**, видит перед применением, что именно узел сможет исполнить, и
применяет это транзакционно с откатом. Сегодня egress фиксируется один раз установщиком
(`[three_xui].warp` → Naive/Mieru целиком через WARP) и меняется только руками.

Релиз `v0.4.0-beta.1` включает целиком:

- нейтральную модель политики (ADR 006) с UUID-ссылками, first-match порядком, явным
  действием по умолчанию и **fail-closed**;
- предпросмотр компиляции под конкретный backend узла: `supported | unsupported`, предупреждения,
  diff с применённым состоянием, необходимость перезапуска, план отката;
- **типизированный транзакционный egress API** у менеджеров Naive и Mieru
  (`get / plan / apply / rollback`, optimistic revision, точный readback, журнал);
- применение на локальном узле и на подключённых панелях (через поколения Fleet v2);
- вынос WARP из `[three_xui]` установщика в самостоятельную секцию `[egress]`;
- изолированный spike нативных возможностей Caddy forwardproxy и mita на стенде;
- закрытие отложенных замечаний v0.3 (`2026-09-14-v0.3-post-merge-issues.md`).

### Не входит в v0.4

- Xray-router (v0.5): сравнение Xray/sing-box как универсального selective-бэкенда (варианты 3–6
  Task 30) не проводится — в каталоге релиза нет изолированного Xray-рантайма, а универсальный
  адаптер по решению спеки выбирается только после его прохождения через все failure/rollback
  тесты. v0.4 честно ограничен нативными возможностями.
- Пулы egress, least-latency, fallback-цепочки, удалённые источники списков — отсутствуют в
  модели, а не «деградируют».
- Per-client / per-grant маршрутизация: ни один backend не умеет отличать клиентов на уровне
  egress; scope `access_grant` компилируется в `unsupported`.
- MTProxy/Telemt — вне области маршрутизации: не предлагается как цель, отвергается API (422
  `out_of_scope`), не получает egress API.
- Пользовательские egress-эндпоинты (свои SOCKS5): в модели есть поле `egress` с единственным
  допустимым значением `warp`; расширение — без изменения схемы.

## 2. Паритет с 3x-ui

Источник: 3x-ui v3.7.0, `frontend/src/schemas/routing.ts`, *Routing rules* в UI.

| 3x-ui | Proxy Control v0.4 |
| --- | --- |
| Правила routing = Xray JSON: `domain[]`, `ip[]`, `port`, `network`, `outboundTag` | Нейтральная политика: `match {domains, cidrs, ports}` → действие `direct | block | egress(warp)`; backend — часть политики |
| Правило выглядит включённым, даже если inbound его не исполняет | Компилятор отдаёт `unsupported` с причиной; применить нельзя, пока не `supported` |
| Порядок drag-and-drop, first-match, «default outbound» | То же: first-match, явное `default_action`; сортировка кнопками и drag |
| Outbound tags по имени | Только `direct`, `block`, `warp` (эндпоинт узла); ссылки по UUID |
| Apply = перезапись всего Xray-конфига | Apply = типизированный документ в менеджер сервиса; менеджер рендерит только свой блок |
| Нет отката, нет preview | `plan` без мутации, `rollback` к последнему известному хорошему состоянию, журнал |

## 3. Архитектурные решения

- **ADR 006 → accepted.** IR хранится в панели; backend (`naive_native`, `mieru_native`) — явное
  поле политики; компилятор никогда не подменяет backend и не «понижает» selective-правило до
  whole-service.
- **ADR 007 (новый, `proposed`): владение enforcement.** Egress-конфигурация data plane
  принадлежит менеджеру этого сервиса: naive-manager владеет блоком `# BEGIN NAIVE-MANAGER EGRESS
  … # END` внутри `forward_proxy` Caddyfile, mieru-manager — секцией `egress` конфига mita.
  Установщик **сеет** начальное состояние один раз (как сеет bootstrap-пользователя) и на
  upgrade/repair его не трогает; других писателей нет. Панель — единственный клиент egress API.
- **Capability handshake.** Узел объявляет `egress.v1` в `GET /api/fleet/v2/identity`, а по
  протоколам — `egress: {backend, capabilities: [...], providers: {warp: {...}}}`. Центр включает
  секцию `egress` в поколение только для узлов с `egress.v1`; для остальных preview отвечает
  `unsupported: node_lacks_egress_v1`.
- **Fail-closed.** Недостижимый WARP → `apply` отказывает (`egress_unreachable`), политика не
  меняется; операция «всё равно направить напрямую» = явное редактирование политики
  (`fallback=approved_direct` разрешает компилятору заменить `warp` на `direct` **только** при
  недоступности провайдера, и это отражается в preview как предупреждение).
- **Управляющий трафик не маршрутизируется.** Egress затрагивает только туннелируемые соединения
  клиентов: Caddy `forward_proxy` (`upstream`, `acl`) и mita `egress`. Панель ↔ менеджеры (UDS),
  ACME, Fleet, heartbeat никогда не проходят через эти пути. Дополнительно компилятор отвергает
  правила `direct|egress` для loopback/link-local/RFC1918 (`private_destination`): у Caddy эти
  сети запрещены по умолчанию (`aclDefaults`), у mita правило не должно давать клиентам
  доступ к loopback узла.
- **Один документ на (узел, протокол).** Политика — это egress-политика сервиса; «subject» v0.4
  всегда `service`.

## 4. Данные

Миграция 14 (`ROUTING_V14`), additive:

```text
routing_policies   id TEXT PK (uuid4), node_id TEXT NOT NULL → fleet_nodes, protocol CHECK(naive|mieru),
                   backend CHECK(naive_native|mieru_native), default_action CHECK(direct|egress),
                   default_egress TEXT NULL CHECK(default_egress IS NULL OR default_egress='warp'),
                   fallback CHECK(fail_closed|approved_direct), revision INTEGER NOT NULL DEFAULT 1,
                   state CHECK(draft|applying|applied|failed|rolled_back) DEFAULT 'draft',
                   applied_revision INTEGER NULL, applied_digest TEXT NULL, applied_at INTEGER NULL,
                   last_error TEXT NULL, created_at, updated_at, UNIQUE(node_id, protocol)
routing_rules      id TEXT PK (uuid4), policy_id → routing_policies ON DELETE CASCADE,
                   position INTEGER NOT NULL, enabled INTEGER NOT NULL DEFAULT 1,
                   match_json TEXT NOT NULL  -- {"domains": [], "cidrs": [], "ports": []}
                   action CHECK(direct|block|egress), egress TEXT NULL, note TEXT NOT NULL DEFAULT '',
                   created_at, updated_at, UNIQUE(policy_id, position)
routing_applies    id INTEGER PK, policy_id, revision, digest, backend, compiler_version,
                   runtime_version TEXT NULL, outcome CHECK(applied|failed|rolled_back),
                   detail TEXT NULL, actor TEXT, created_at
```

- `revision` растёт при каждом сохранении политики (optimistic concurrency в `PUT`: 409
  `policy_conflict`). `applied_*` фиксируют, какая ревизия и с каким digest компиляции стоит на
  узле; `state=applied` и `revision == applied_revision` → «применено», иначе «есть неприменённые
  изменения».
- Никаких секретов: политика и compiled-документ secret-free; URL WARP-эндпоинта узла — не
  секрет, но и не хранится: центр видит его в `identity`.

## 5. Модель политики и компилятор (`panel/routing/`)

```text
RoutingPolicy   id, node_id, protocol, backend, default_action, default_egress, fallback,
                rules: [RoutingRule], revision
RoutingRule     id, position, enabled, match: {domains: [str] ≤ 64, cidrs: [str] ≤ 64,
                ports: [int|"a-b"] ≤ 32}, action, egress, note ≤ 120
```

Валидация: домены — IDNA-lowercase, `*.example.com` допустим (суффикс), пустой `match` запрещён,
CIDR нормализуется (`ipaddress`), порты 1–65535; максимум 128 правил на политику; `egress` обязателен
при `action=egress` и запрещён иначе.

`compile(policy, target: NodeEgressTarget) -> Compiled`:

```text
NodeEgressTarget  node_id, protocol, backend, capabilities: set[str], providers: {warp: {url, reachable, checked_at}},
                  applied: {revision, digest, document} | None, runtime_version
Compiled          status: supported | unsupported, reasons: [ {code, rule_id?, message} ],
                  warnings: [...], document: dict | None, digest, diff: [...] против applied.document,
                  restart_required: bool, rollback: {to_revision, to_digest} | None,
                  compiler_version, backend, runtime_version
```

Матрица возможностей (то, что backend **умеет**, а не что доказано — доказательства даёт spike и
гейт, итог в `docs/spikes/VNEXT_ROUTING_ENGINE.md`; ячейки без доказательства удаляются из
`capabilities` менеджера, и компилятор отвечает `unsupported`):

| Возможность | `naive_native` (Caddy forwardproxy) | `mieru_native` (mita egress) |
| --- | --- | --- |
| whole-service `direct` | `upstream` отсутствует | `rules=[]` (default DIRECT) |
| whole-service `warp` | `upstream <url>` | `proxies=[warp]`, правило `*`/`*` → PROXY |
| `block` по домену/суффиксу | `acl { deny example.com *.example.com }` — по hostname CONNECT | правило `domainNames` → REJECT |
| `block` по CIDR | `acl { deny 1.2.3.0/24 }` — по IP, в т.ч. резолвленным | правило `ipRanges` → REJECT |
| `block` по порту | **нет** (`ports` — allow-list, а не deny; в v0.4 не компилируется) | **нет** |
| selective `direct`/`warp` по домену/CIDR | **нет** — `upstream` один на сервис | правила `domainNames`/`ipRanges` → DIRECT/PROXY |
| per-client | нет | нет |

Коды `reasons`: `backend_capability_missing`, `rule_kind_unsupported`, `private_destination`,
`provider_unavailable`, `provider_unreachable`, `node_lacks_egress_v1`, `protocol_out_of_scope`,
`protocol_disabled_on_node`, `policy_empty`. Порядок правил в compiled-документе сохраняется
(first-match у обоих backend), `enabled=0` правила пропускаются, `block`-правила Caddy собираются в
один `acl`, у mita — в отдельные REJECT-правила в исходном порядке.

Compiled-документы (то, что менеджер принимает и валидирует; секретов нет):

```text
naive_native  {"schema": 1, "upstream": {"provider": "warp"} | null,
               "acl": [{"deny": ["example.com", "*.cdn.example", "10.0.0.0/8"]}, ...]}
mieru_native  {"schema": 1, "proxies": [{"name": "warp", "provider": "warp"}],
               "rules": [{"domains": [...], "cidrs": [...], "action": "DIRECT|PROXY|REJECT", "proxy": "warp"|null}, ...]}
```

Менеджер сам подставляет URL провайдера (`NAIVE_EGRESS_WARP` / `MIERU_EGRESS_WARP`) — панель
не передаёт адресов, путей и сырых конфигов (ADR 008 остаётся в силе). `digest` = SHA-256
канонического JSON compiled-документа; тот же `revision` политики с другим digest на узле —
конфликт (`digest_conflict`), а не молчаливая перезапись.

## 6. Egress API менеджеров (Task 29)

Оба менеджера получают четыре маршрута на существующем UDS с тем же Bearer:

| Маршрут | Naive (`naive_manager`) | Mieru (`mieru_manager`) |
| --- | --- | --- |
| `GET /egress` | `{revision, mode: direct|proxy|custom, upstream: url|null, acl: [...], document: compiled|null, providers: {warp: {url, reachable: bool|null, checked_at}}, capabilities: [...], runtime_version}` | `{revision, document: compiled|null, raw: {proxies, rules} (как в mita), providers, capabilities, runtime_version}` |
| `POST /egress/plan` | `{expected_revision, document}` → `{revision, target_revision, rendered_sha256, diff: [...], warnings, reachability, restart_required: false}`; мутаций нет | то же; `restart_required: false` (`mita apply` + reload) |
| `POST /egress/apply` | `{expected_revision, document, operation_id}` → `{revision, applied: document, readback_sha256}`; идемпотентно по `operation_id` | то же через существующий `_transaction` с `mode`/журналом |
| `POST /egress/rollback` | `{expected_revision}` → восстанавливает предыдущую запись журнала egress (last-known-good) | то же |

Общие свойства:

- **Revision** — SHA-256 управляемого блока (Naive) / ревизия состояния (Mieru, уже есть);
  расхождение → 409 `egress_conflict`. Неизвестное поле, схема ≠ 1, неизвестный провайдер,
  loopback/private в `allow` → 422 `egress_invalid`.
- **Reachability.** Перед `apply` с `provider=warp` менеджер делает TCP-connect + SOCKS5
  greeting без аутентификации (для `socks5://`) или только TCP-connect (для `http://`) к
  эндпоинту; неудача → 409 `egress_unreachable`, конфиг не меняется. `mieru-manager` для этого переводится
  на `network_mode: host` (слушателей у него нет — только UDS; `read_only`, `cap_drop: ALL`
  остаются), иначе loopback хоста ему недоступен.
- **Readback.** Naive: после `reload` через Admin API читается `GET /config/` и сверяются
  `upstream` и `acl` handler'а `forward_proxy` (обёрнуто в существующий `_assert_adapted_semantics`);
  Mieru: `mita describe config` → сравнение секции `egress` с ожидаемой. Расхождение → откат к
  предыдущему файлу/конфигу + `reload`, ответ 502 `egress_readback_mismatch`; если и откат не
  сошёлся — 503 `manual_intervention_required` с сохранённой резервной копией (путь в ответе).
- **Журнал.** `state.json` Naive / journal Mieru получают `egress: {current, previous, history[≤10]}`
  с `rendered_sha256`, `operation_id`, `applied_at`; crash между записью файла и reload
  восстанавливается тем же `_recover_transaction` (Naive) / `_recover` (Mieru).
- **Соседние состояния не меняются:** Naive-блок пользователей и accounting не трогаются
  (проверяется тестом на байтовую идентичность остальных строк); у mita `users`,
  `portBindings`, `mtu`, `loggingLevel` копируются из наблюдённого конфига как есть.
- **Bounded reason codes:** `egress_conflict`, `egress_invalid`, `egress_unreachable`,
  `egress_validate_failed`, `egress_readback_mismatch`, `manual_intervention_required`,
  `egress_unsupported` (провайдер не сконфигурирован: `NAIVE_EGRESS_WARP` пуст).
- Telemt egress API **не получает** (спека vNext, Task 29).

Caddyfile Naive после Task 29 (блок сеет установщик, далее пишет только менеджер):

```text
        forward_proxy {
            # BEGIN NAIVE-MANAGER USERS
            basic_auth …
            # END NAIVE-MANAGER USERS
            hide_ip
            hide_via
            probe_resistance
            # BEGIN NAIVE-MANAGER EGRESS
            upstream socks5://127.0.0.1:45000
            acl {
                deny example.com *.example.com 10.0.0.0/8
            }
            # END NAIVE-MANAGER EGRESS
        }
```

Существующий Caddyfile без блока EGRESS (все хосты v0.1–v0.3, включая `AMS_Z` с
`upstream http://127.0.0.1:8118`): `GET /egress` отдаёт `mode: custom` и найденную строку `upstream`
как есть, `revision` считается по ней; первый `apply` переносит `upstream` внутрь блока (удаляя
незамаркированную строку) — preview показывает это как diff и предупреждение
`adopts_unmanaged_upstream`. `rollback` восстанавливает байты до первого apply.

## 7. Установщик: `[egress]` (Task 28)

`install.toml`:

```toml
[egress]
warp = true              # ставить/держать cloudflare-warp в proxy-режиме (бывшее [three_xui].warp)
warp_port = 40000        # бывшее [three_xui].warp_port
naive = "warp"           # direct | warp — начальный egress сервиса (сеется один раз)
mieru = "warp"           # direct | warp
```

- **Dual-read.** Секции `[egress]` нет → значения выводятся из `[three_xui].warp*` **ровно как
  сегодня**, включая связку «`warp_domains` непусто → Naive/Mieru direct» (старые конфиги
  рендерятся и round-trip'ятся без изменений; `render_config` не пишет `[egress]`, если её не
  было). Секция есть → она каноническая: `naive`/`mieru` выбираются явно, `[three_xui].warp`
  становится псевдонимом `[egress].warp` (оба заданы и различаются → `ConfigError`), а
  `[three_xui].warp_domains` остаётся селективным routing для managed-new Xray.
- Мастер (`wizard.py`) пишет `[egress]` для новых конфигов; вопрос «WARP» переезжает из блока 3x-ui
  в отдельный шаг с выбором egress для Naive и Mieru.
- Адаптеры Naive/Mieru берут `egress` из `config.egress.naive|mieru` (не из `three_xui`);
  планы/mutations не меняют формат (`egress=proxy|direct`, `warp-port=…`), значит `plan`-digest
  существующих установок при dual-read не меняется — это утверждает тест.
- Установщик кладёт в `.env` хоста `NAIVE_EGRESS_WARP=socks5://127.0.0.1:<port>` и
  `MIERU_EGRESS_WARP=socks5://127.0.0.1:<port>` при `warp = true` (пусто иначе); compose-оверлеи
  пробрасывают их в менеджеры. Хосты, собранные вручную, задают переменные сами
  (`docs/UPGRADING`); без них провайдер `warp` — `unsupported`.
- Рабочий WARP не переустанавливается, владение не меняется (WarpAdapter — как был).

## 8. Панель

### 8.1 API (`panel/routing/routes.py`, owner для мутаций, viewer — чтение)

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/routing/targets` | узлы × протоколы: `{node_id, node_name, kind: local|remote, protocol, backend, capabilities, providers, egress_v1: bool, policy: {id, revision, state, applied_revision} | null}`; MTProxy присутствует с `backend: null, reason: protocol_out_of_scope` |
| `GET /api/routing/policies/{node_id}/{protocol}` | политика с правилами (404, если нет) |
| `PUT /api/routing/policies/{node_id}/{protocol}` | upsert политики и полного списка правил одной транзакцией; `expected_revision` (409 `policy_conflict`); UUID правил сохраняются, новые — без `id`; `revision += 1`; audit `routing.policy.update` |
| `DELETE …/{node_id}/{protocol}` | удалить политику (409 `policy_applied`, пока `applied_revision` не откатан к `direct`-без-правил — сначала «Сбросить и применить») |
| `POST …/{node_id}/{protocol}/preview` | `compile()` против актуального target; тело — необязательная несохранённая политика (preview черновика) |
| `POST …/{node_id}/{protocol}/apply` | `expected_revision`; `unsupported` → 422 с `reasons`; local → egress API менеджера; remote → `publish()` поколения с `egress`; результат/операция; audit `routing.policy.apply` |
| `POST …/{node_id}/{protocol}/rollback` | к предыдущей записи `routing_applies` (`rolled_back`); local → `rollback` менеджера; remote → поколение с предыдущим документом |
| `GET …/{node_id}/{protocol}/history` | `routing_applies` (≤ 50) |

### 8.2 Локальный узел

`RoutingService.apply(policy)`: `compile` → `manager.egress_plan` → `manager.egress_apply(operation_id=f"routing:{policy.id}:{revision}")`
→ `routing_applies(applied)` + `applied_*` в одной транзакции **после** ответа менеджера (I/O вне
`BEGIN IMMEDIATE`, как в v0.3). Ошибка менеджера → `state=failed`, `last_error=<code>`, запись
`failed`. Панельные клиенты `NaiveClient`/`MieruClient` и `MemoryNaive`/`MemoryMieru` получают
`egress()`, `egress_plan()`, `egress_apply()`, `egress_rollback()`.

### 8.3 Подключённые панели (Fleet v2)

- `GenerationDocument.egress: dict[Literal["naive","mieru"], EgressDocument] | None = None`
  (`schema_version` остаётся 1: поле опционально и не отправляется узлам без `egress.v1`;
  `_Strict` узла v0.3 иначе ответил бы 422). `EgressDocument{backend, policy_id, policy_revision,
  document, digest}`; входит в `canonical_digest`.
- Узел: `Reconciler._apply` после ресурсов применяет `egress` по протоколам через адаптеры
  (`ProtocolAdapter.apply_egress(document) -> AppliedEgress`, `mtproxy` — `NotImplemented`);
  `ObservedGeneration.egress: dict[str, ObservedEgress{state: converged|failed|unsupported,
  revision, digest, error}]`; отсутствие секции = «оставить как есть» (узел не трогает egress).
  Ошибка egress → поколение `failed` (как ресурс), ресурсы при этом применяются.
- Центр: `compile()` поколения добавляет `egress` из политик узла со `state in (applying, applied)`
  (черновик не публикуется); pusher по observed переводит политику в `applied`/`failed`,
  `routing_applies` пополняется. `identity_json` узла хранит `egress`-таблицу протоколов —
  источник `targets` для центра.
- `unlink` узла оставляет egress как есть (данные плоскости не трогаются).

## 9. Spike (Task 30) — что проверяется на стенде

`docs/spikes/VNEXT_ROUTING_ENGINE.md`; лаборатория — установка `lab-host` на `ams-test`
(живые Caddy 2.11.4 + forwardproxy `d62c80d`, mita 3.36.0). WARP на стенде нет — вместо него
**подставной SOCKS5** (`scripts/lab/socks5-stub.py`: журналирует каждую CONNECT-цель, ничего
не фильтрует), чтобы различать «ушло через egress-прокси» и «ушло напрямую» по факту, а не по
IP.

Пробы (каждая — факт `supported | unsupported | needs_client_hostname` в таблице spike):

1. Caddy: `upstream socks5://` переключается reload'ом без обрыва cover-сайта; `caddy adapt`
   принимает `acl { deny <domain> <*.domain> <cidr> }` внутри `forward_proxy`; deny по домену
   срабатывает на hostname CONNECT; deny по CIDR срабатывает на IP и на резолвленный hostname;
   ACL проверяется **и при заданном `upstream`**; дефолтный запрет loopback/RFC1918 сохраняется
   при пользовательском `acl`; `ports` — не deny (фиксируется как `unsupported` для block-port).
2. mita: `egress.rules` с `domainNames`-суффиксом и `ipRanges` → `PROXY|DIRECT|REJECT` first-match;
   hostname vs заранее резолвленный IP (клиент mieru передаёт hostname? — проверяется обоими
   способами); поведение UDP при `PROXY` (ожидаемо: не релеится через SOCKS5 → фиксируется);
   `mita apply` + reload без обрыва существующих сессий пользователей.
3. Reachability: SOCKS5-greeting к живому/мёртвому эндпоинту с host-network контейнера.
4. Отказы: невалидный `acl` → `caddy validate` отклоняет, файл восстановлен; kill Caddy между
   записью и reload → `_recover_transaction` возвращает последнее известное хорошее; то же для
   mita (`_recover`).

**Decision gate:** ячейки со `supported` попадают в `capabilities` менеджеров; остальное —
`unsupported` в компиляторе. Никакого универсального selective-адаптера в v0.4 не выбирается.

## 10. Безопасность

- Compiled-документы и политики secret-free; URL провайдера живёт в env менеджера; ответы
  `GET /egress` не содержат учётных данных (SOCKS5-auth к WARP не поддерживается — proxy-режим
  warp-cli без аутентификации).
- Панель не передаёт менеджеру ни путей, ни адресов, ни сырых конфигов; менеджер валидирует
  документ по строгой схеме (`extra=forbid` эквивалент) и лимитам (≤ 128 правил, ≤ 64 доменов/CIDR
  на правило, ≤ 16 KiB документа).
- Fail-closed: недостижимый провайдер → отказ; `fallback=approved_direct` — явный выбор владельца,
  виден в preview и audit.
- Loopback/private как цель `direct|egress` — `private_destination`; у Caddy дефолтный deny
  этих сетей сохраняется (проверяет spike и unit-тест на рендер).
- Rate limit и body limit узла (64 KiB) не меняются: секция `egress` ≤ 16 KiB на протокол, лимит
  утверждается тестом на максимальную политику.
- Audit: `routing.policy.update|apply|rollback` с `policy_id`, `revision`, `digest`, `outcome`;
  без документа.

## 13. Отклонения от спеки vNext и решения, принятые за владельца

1. **Task 30 сужен** до нативных проб (варианты 1 и частично 2 — reachability из netns через
   host-network); варианты 3–6 (Xray/sing-box) — в v0.5 (Task 32 и далее). Основание: decision
   gate спеки допускает capability-limited v0.4, а изолированного Xray-рантайма в каталоге нет.
2. **Пулы и пользовательские egress-эндпоинты отсутствуют в схеме** (в спеке — объекты `pools`,
   `egress endpoints`): поле `egress` со значением `warp` расширяемо без миграции; лишние таблицы
   без потребителя не заводятся.
3. **Одна политика на (узел, протокол)**, scope `service`; `control_plane` и `access_grant` не
   моделируются (первый — константный bypass, второй — `unsupported` у всех backend).
4. **`mieru-manager` на host-network** ради reachability-пробы; альтернатива (проба из панели или
   naive-manager) нарушает границы сервисов.
5. **Существующие `upstream` без маркеров принимаются как `custom`** и переносятся в управляемый
   блок при первом apply с сохранением байтов для отката — иначе `AMS_Z` (privoxy `8118`) не
   управляем без ручной правки.
6. **Отложенные замечания v0.3** закрываются в этой ветке первой задачей (fix-wave), т.к. касаются
   тех же модулей Fleet v2, которые v0.4 расширяет.
7. **Тег и раскатка на `ams-server`/`AMS_P`/`AMS_R`** — за владельцем; `AMS_Z` и `ams-test`
   разрешены для живой проверки.
