# Proxy Control v0.5 — выделенный Xray egress-router и финализация vNext

Дата: 2026-09-16. Ветка: `feature/vnext-v0.5-xray-router` (от `feature/vnext-v0.4-routing`,
`v0.4.0-beta.1` + документация публикации, `eb20e8d`). Уточняет Phase 7 (Tasks 32–36) и Phase 8
(Tasks 37–41) из [спеки vNext](2026-09-10-proxy-control-vnext-design.md), переводит
[ADR 007](../../adr/007-routing-enforcement-ownership.md) целиком в `accepted` — см. раздел 15
«Отклонения». Это последняя версия программы vNext: после неё дорожная карта закрыта. Решения
приняты автономно по поручению владельца (2026-09-16: «переходим к разработке версии 0.5, это
последняя стадия; действуй как с предыдущими версиями, всё тестируй на локальных контурах»).

## 1. Цель

Оператор получает на узле **необязательный** выделенный маршрутизатор исходящего трафика
(Xray-core), к которому явно подключает NaiveProxy и/или Mieru. Подключённый сервис отдаёт
роутеру весь туннелируемый трафик через собственный аутентифицированный SOCKS5-ingress на
loopback, а политика маршрутизации (ADR 006) компилируется уже в правила Xray: домены,
`geosite`, CIDR, `geoip`, порты, `direct | warp | block` в любом сочетании, first-match, с
предпросмотром, транзакционным применением, откатом к last-known-good и той же моделью
управления с центральной панели (Fleet v2). Не подключённые сервисы и узлы без роутера
работают ровно как в v0.4.

Релиз `v0.5.0-beta.1` включает целиком:

- закреплённый артефакт Xray-core (бинарь + `geoip.dat` + `geosite.dat`) в каталоге релиза,
  выкладываемый оператором заранее как пакеты mita — установщик ничего не скачивает;
- runtime `xray-router` в собственном контейнере с менеджером-супервизором и типизированным
  egress API (`get / plan / apply / rollback`, `xray run -test`, атомарная смена поколения,
  readback, журнал, восстановление после сбоя);
- два аутентифицированных loopback-ingress (`naive`, `mieru`) с ключами-секретами установщика;
- провайдер `router` у naive-manager и mieru-manager, явные действия «подключить/отключить»;
- расширение модели политики: backend `xray_router`, селекторы `geosites`, `geoips`, правила
  только по портам; компилятор в `XrayRoutingIntent`; capability-ячейки, доказанные spike;
- применение локально и через поколения Fleet v2 (`egress.router.v1`), экран «Маршрутизация»;
- изолированный spike Xray на стенде (`docs/spikes/XRAY_EGRESS_ROUTER.md`), ADR 007 accepted;
- Phase 8: backup/restore с состоянием роутера, сводная матрица негативных/security-тестов,
  гейт репозитория и стенда, релизная последовательность;
- закрытие отложенных замечаний v0.4 из `CONTINUE-HERE-v0.4.md` (fix-wave).

### Не входит в v0.5

- **Статический bridge в 3x-ui** (спека vNext Task 35, вопрос 2 §7): не предлагается ни для
  `existing`, ни для `managed-new`. 3x-ui-owned Xray остаётся полностью чужим; ADR 007 оставляет
  за собой «не более одного явно принадлежащего bridge позже, после отдельного гейта drift/upgrade».
- **Canary rollouts (Task 38):** политики маршрутизации существуют per (узел, протокол), fleet-wide
  поколения политики в архитектуре нет — единица применения и есть один узел. Обновление
  артефактов Xray — установщик/version-agent, не центр. Отложено, см. §15.
- **Per-grant маршрутизация:** ни один ingress не различает клиентов сервиса; scope `access_grant`
  по-прежнему `unsupported`. Тег ingress — идентичность сервиса, не клиента.
- **UDP через роутер:** ingress создаются с `udp: false`; Mieru UDP через SOCKS5-egress mita не
  доказан (spike v0.4) — остаётся `unsupported`.
- **MTProxy/Telemt** — вне маршрутизации (ADR 006), роутер не имеет для него ingress.
- **Регулярные выражения в доменных правилах, балансировщики, пулы, удалённые списки** — не в
  модели. `geosite`/`geoip` — только из закреплённых файлов релиза, без скачивания.
- **Живая проверка на production-узлах (AMS_Z):** по указанию владельца весь гейт v0.5 — только
  на `ams-test`.

## 2. Паритет с 3x-ui

| 3x-ui (routing rules) | Proxy Control v0.5 |
| --- | --- |
| `domain: ["geosite:category-ads-all", "domain:example.com", "full:x.y"]` | `match.domains` (суффикс / `*.` / точное имя как в v0.4), `match.geosites: ["category-ads-all"]` |
| `ip: ["geoip:private", "geoip:cn", "1.2.3.0/24"]` | `match.cidrs`, `match.geoips: ["cn"]`; `geoip:private` — неизменяемый bypass, не правило |
| `port: "443,1000-2000"` | `match.ports` — теперь исполняется (backend `xray_router`) |
| `outboundTag: direct / blocked / warp` | `action: direct | block | egress(warp)` |
| один Xray на всё, правила без inbound → «работают для всех» | правила всегда ограничены `inboundTag` сервиса; чужой сервис не затрагивается |
| перезапись всего конфига, без отката | поколение Xray = функция от намерений сервисов; `-test` → swap → readback → LKG-откат |
| routing внутри 3x-ui не касается Naive/Mieru | это и есть цель роутера; 3x-ui не участвует |

## 3. Архитектурные решения

- **ADR 007 → accepted целиком.** Роутер — отдельный сервис (контейнер `proxy-control-xray-router`),
  свой бинарь, свой конфиг, свои поколения; никогда не исполняется из `/usr/local/x-ui/bin`, не
  делит с x-ui ни путей, ни портов, ни перезапусков. Единственный клиент его API — панель.
- **Ownership трёх писателей не появляется.** У naive-manager и mieru-manager остаётся их блок
  (v0.4); при подключении к роутеру этот блок содержит ровно один провайдер `router` (upstream /
  `* → PROXY router`) и больше не меняется политикой; вся политика живёт в секции сервиса у
  менеджера роутера. Отключение возвращает нативный блок к `direct`.
- **Ingress = идентичность сервиса.** Каждому сервису — свой loopback-порт, тег и пара
  `user:password` (32 байта энтропии), созданные установщиком как секреты и известные только
  роутеру и менеджеру этого сервиса. Без аутентификации подключение отвергается Xray на уровне
  SOCKS5 (метод `password`), кросс-сервисные ключи не подходят. Публичных слушателей нет.
- **Fail-closed сохраняется.** Недостижимый WARP → `apply` отказывает (`egress_unreachable`);
  в рантайме мёртвый WARP-outbound = отказ соединения, а не «напрямую». `fallback=approved_direct`
  действует только на этапе компиляции (как в v0.4) и виден в preview.
- **Неизменяемый bypass роутера** — не «управляющий трафик мимо», а **запрет приватных
  назначений**: первое правило каждого ingress — `geoip:private → block` плюс `localhost`;
  `domainStrategy: IPOnDemand` резолвит имя до сопоставления, поэтому имя, указывающее на
  `127.0.0.1` (DNS rebinding к Caddy Admin API `2019`, WARP `45000`, самому роутеру `45101`),
  тоже блокируется; `freedom` использует `domainStrategy: UseIP`, чтобы соединение шло на тот
  же адрес, по которому принято решение. Управляющие потоки (панель ↔ менеджеры по UDS, ACME,
  Fleet mTLS, heartbeat) через роутер физически не проходят.
- **DNS-семантика говорится вслух.** Роутер резолвит каждое имя системным резолвером узла
  (`dns.servers: ["localhost"]`) для принятия решения; в WARP-outbound имя передаётся именем
  (SOCKS5 ATYP domain). Это документируется как свойство, а не скрывается; `sniffing`
  (`routeOnly: true`) восстанавливает имя из TLS SNI/HTTP Host для клиентов, шлющих IP.
- **Одна политика на (узел, протокол), backend — часть политики** (v0.4). Backend протокола
  — то, что сообщает узел: `xray_router`, если сервис подключён, иначе нативный; политика с
  другим backend компилируется в `unsupported: backend_capability_missing`, как и раньше.
- **Артефакты закреплены независимо от 3x-ui.** Никакого «сидирования» бинаря из staged-архива
  3x-ui (спека Task 32 допускала как оптимизацию) — одна проверенная поставка, одна процедура.

## 5. Runtime и менеджер `xray_router_manager`

**Замороженные идентификаторы (v0.5, `docs/COMPATIBILITY.md`):** сервис compose `xray-router`,
контейнер `proxy-control-xray-router`, оверлей `compose.xray-router.yaml`, образ из
`xray_router_manager/Dockerfile` (`python:3.13-slim`, без Xray внутри), `network_mode: host`,
uid/gid `10006:10006` (`xray-router`), `read_only`, `cap_drop: ALL`, `no-new-privileges`,
`pids_limit: 128`, `tmpfs /tmp`. Бинарь и geodata — bind `/usr/local/lib/proxy-control/xray-router`
read-only. Состояние — bind `/var/lib/xray-router` (`10006:10006`, `0700`), подготавливается
установщиком (`scripts/prepare-xray-router-state.sh` по образцу mieru). Сокет — tmpfs-том
`xray-router-run` → `/run/xray-router/manager.sock` (`0660`). Секреты (compose `secrets`):
`secrets/xray-router-manager-token`, `secrets/xray-router-ingress-naive`,
`secrets/xray-router-ingress-mieru` (строка `user:password`, `0600`). Loopback: `127.0.0.1:45101`
(тег `naive`), `127.0.0.1:45102` (тег `mieru`). Env: `XRAY_ROUTER_BIN_DIR`,
`XRAY_ROUTER_XRAY_SHA256`, `XRAY_ROUTER_GEOIP_SHA256`, `XRAY_ROUTER_GEOSITE_SHA256`,
`XRAY_ROUTER_EGRESS_WARP` (URL провайдера, как у других менеджеров), `XRAY_ROUTER_MANAGER_TOKEN_FILE`,
`XRAY_ROUTER_INGRESS_NAIVE_FILE`, `XRAY_ROUTER_INGRESS_MIERU_FILE`.

**Граница.** Xray — дочерний процесс менеджера (тот же uid, `XRAY_LOCATION_ASSET` → каталог
geodata), без `api`, без `stats`, `log.access: none`, `log.loglevel: warning`, stderr
ограниченно ретранслируется в журнал контейнера с редактированием (ключи ingress никогда не
печатаются). Сырые Xray JSON, пути файлов, URL списков от клиентов API отвергаются на уровне
схемы (`egress_invalid`).

**Состояние** (`/var/lib/xray-router`): `generations/<n>.json` — полный конфиг Xray поколения n;
`current.json` — `{generation, digest, services: {naive: {document, digest, revision}, mieru: {...}}}`;
`journal.json` — `{naive: {current, previous, history[≤10]}, mieru: {...}}` с `operation_id`,
`applied_at`, `generation`; `state.json` — фаза транзакции для восстановления. Ключи ingress в
поколениях **есть** (Xray читает их из конфига) — поэтому `generations/` `0600`, а в API,
`GET /egress`, журнале и логах документы сервисов не содержат ключей (они не являются частью
`XrayRoutingIntent`; менеджер подставляет их при рендере).

**HTTP API на UDS (Bearer, `http.server`, как у других менеджеров):**

| Маршрут | Ответ |
| --- | --- |
| `GET /v1/status` | `{version, xray_version, artifacts: {xray, geoip, geosite: {sha256, verified}}, running: {generation, digest, since}, services: {naive: {attached_ingress: true, revision, digest}, mieru: {...}}, providers: {warp: {reachable, checked_at}}, capabilities: [...], restart_required: true}` |
| `GET /v1/egress/{service}` | `{revision, document: intent|null, mode: direct|proxy, providers, capabilities, restart_required: true, warnings, runtime_version}` — та же лексика, что у v0.4 |
| `POST /v1/egress/{service}/plan` | `{expected_revision, document}` → `{revision, target_revision, generation_digest, diff, warnings, reachability, restart_required: true}`; без мутаций (`xray run -test` во временном файле) |
| `POST /v1/egress/{service}/apply` | `{expected_revision, document, operation_id}` → `{revision, applied, readback_sha256, generation}`; идемпотентно по `operation_id` |
| `POST /v1/egress/{service}/rollback` | `{expected_revision}` → предыдущая запись журнала сервиса (LKG); `egress_no_previous` без истории |

`service ∈ {naive, mieru}`; иное → 404. `revision` сервиса = SHA-256 канонического
`{document, generation}`; `expected_revision` ≠ текущей → 409 `egress_conflict`.

**Транзакция apply** (менеджер сериализует все операции одним замком):

1. валидация `XrayRoutingIntent` (схема §6), лимиты, reachability WARP при использовании
   (`egress_unreachable`, конфиг не меняется);
2. рендер полного конфига поколения `n+1` из намерений **всех** сервисов (детерминированно,
   отсортированные ключи) + неизменяемый bypass + ingress с ключами из секретов;
3. `xray run -test -config generations/<n+1>.json` (таймаут 10 с); неуспех → 422 `egress_invalid`
   с кодом `geosite_unknown` / `geoip_unknown`, если Xray назвал неизвестный код, файл удаляется;
4. `state.json: phase=swapping`; SIGTERM текущему Xray (ожидание ≤ 5 с, затем SIGKILL), запуск
   нового с `<n+1>.json`; ожидание, пока оба ingress принимают TCP (≤ 10 с);
5. readback: SHA-256 файла, с которым запущен процесс, = digest поколения; `current.json` и
   журнал сервиса обновляются атомарно (`os.replace` + fsync каталога); `phase=idle`;
6. при неудаче шага 4 — запуск предыдущего поколения (LKG); если и он не поднялся →
   503 `manual_intervention_required` (в ответе — путь поколения), менеджер остаётся в фазе
   `broken` и отдаёт её в `/status` до ручного вмешательства.

Все сессии всех подключённых сервисов рвутся на ~1 с при каждом apply (`restart_required: true`,
preview говорит об этом). Восстановление при старте менеджера: по `state.json` — `swapping` →
запустить поколение из `current.json` (LKG), незавершённое `n+1` удалить; всегда проверить
артефакты, затем запустить Xray с текущим поколением; при первом старте — поколение 1:
оба ingress, bypass, `direct` для обоих сервисов.

**Ротация ключей ingress** (`scripts/rotate-xray-router-ingress.sh`, §8): новые секреты → перезапуск
`xray-router` (менеджер рендерит поколение с новыми ключами при старте, если файлы секретов
изменились) → перезапуск `naive-manager`/`mieru-manager` (менеджер при старте перерисовывает
управляемый блок, если его рендер от текущего документа и текущего ключа отличается от файла —
блок есть чистая функция документа + провайдера). Прерывание ≈ 2 с; старые ключи не принимаются.

## 6. Модель политики и компилятор (`panel/routing/`)

```text
Backend        naive_native | mieru_native | xray_router
RuleMatch      domains ≤ 64, cidrs ≤ 64, ports ≤ 32, geosites ≤ 64, geoips ≤ 64
               — непусто хотя бы одно из пяти (правило только по портам допустимо);
               geosite/geoip коды: ^[a-z0-9][a-z0-9@!_-]{0,63}$, lower-case; `private` в geoips запрещён
               (bypass, а не правило) → 422
```

Миграция 15 (`ROUTING_V15`), additive: `routing_policies.backend CHECK` расширяется значением
`xray_router` (SQLite не меняет CHECK на месте — таблица пересоздаётся с копированием строк
внутри одной транзакции, FK-каскады `routing_rules` сохраняются), `match_json` получает
ключи `geosites`, `geoips` (отсутствие = `[]`, старые строки читаются без изменений);
`routing_applies.backend` — без CHECK. Новых таблиц нет.

**Capability-ячейки `xray_router`** (доказываются spike §10; недоказанные удаляются из
`capabilities` менеджера, компилятор отвечает `unsupported`): `whole_direct`, `whole_warp`,
`block_domain`, `block_cidr`, `block_port`, `block_geosite`, `block_geoip`, `selective_domain`,
`selective_cidr`, `selective_port`, `selective_geosite`, `selective_geoip`. Для нативных backend
`geosites`/`geoips`/`ports` → `rule_kind_unsupported` (как порты в v0.4). Ограничение naive
«block рядом с upstream» для `xray_router` не действует.

**Compiled-документ `xray_router`** (`XrayRoutingIntent`, то, что менеджер принимает; секретов
нет; ≤ 16 KiB):

```text
{"schema": 1,
 "default": {"action": "direct" | "egress", "egress": "warp" | null},
 "rules": [{"domains": [...], "geosites": [...], "cidrs": [...], "geoips": [...], "ports": [...],
            "action": "direct" | "block" | "egress", "egress": "warp" | null}, ...]}
```

Компилятор (`panel/routing/adapters/xray_router.py`): правила в исходном порядке, `enabled=0`
пропускаются; домены `*.x` и `x` → `domain:x` (суффикс, как mita), точное имя без `*.` **тоже**
`domain:x` — семантика v0.4 сохраняется и говорится в docs; `geosite:` / `geoip:` / CIDR /
`port` — как есть; `private_destination` для `direct|egress` остаётся (компилятор), а bypass
роутера — второй рубеж. `Compiled.document` = intent; `Compiled.attach` (новое поле) = нативный
документ подключения (`{"upstream": {"provider": "router"}}` / mieru-аналог), который
`RoutingService` обеспечивает при apply. `diff` — против `applied.document` роутера.
`restart_required: true` всегда.

**Рендер в Xray** (внутри менеджера, не в панели): `inbounds` — два `socks` (`listen 127.0.0.1`,
`auth: password`, `accounts` из секретов, `udp: false`, `sniffing {enabled, destOverride
[http, tls, quic], routeOnly: true}`, `tag`); `outbounds` — `direct` (`freedom`, `domainStrategy:
UseIP`), `block` (`blackhole`), `warp` (`socks` → URL `XRAY_ROUTER_EGRESS_WARP`, только если
хоть одно намерение его использует); `routing.domainStrategy: IPOnDemand`; для каждого тега:
`[{"inboundTag": [tag], "ip": ["geoip:private"], "outboundTag": "block"}, {"inboundTag": [tag],
"domain": ["domain:localhost", "full:localhost"], "outboundTag": "block"}, …правила…,
{"inboundTag": [tag], "network": "tcp", "outboundTag": default}]`; `dns: {"servers":
["localhost"]}`; `log: {"access": "none", "loglevel": "warning"}`. Никакого `api`/`stats`.

## 7. Egress API менеджеров Naive/Mieru: провайдер `router`

- Env: `NAIVE_EGRESS_ROUTER` (`socks5://127.0.0.1:45101`), `NAIVE_EGRESS_ROUTER_CREDENTIAL_FILE`
  (`/run/secrets/xray-router-ingress-naive`); `MIERU_EGRESS_ROUTER` (`socks5://127.0.0.1:45102`),
  `MIERU_EGRESS_ROUTER_CREDENTIAL_FILE`. Пусто → провайдера `router` нет.
- `GET /egress.providers` получает `router: {reachable, checked_at}` (reachability = TCP +
  SOCKS5 greeting с методом `password` без завершения аутентификации — сервер отвечает `0x02`).
- Документы: naive `{"schema": 1, "upstream": {"provider": "router"}, "acl": []}`; mieru
  `{"schema": 1, "proxies": [{"name": "router", "provider": "router"}], "rules": [{"domains": ["*"],
  "cidrs": ["*"], "action": "PROXY", "proxy": "router"}]}`. Рендер: Caddyfile `upstream
  socks5://<user>:<pass>@127.0.0.1:45101`; mita `egress.proxies[]` с `socks5Authentication`.
  Ключ читается из файла при каждом рендере и **никогда** не попадает в `GET /egress`, `plan`,
  журнал, `raw` custom-строки (если оператор вручную вписал `upstream socks5://u:p@…`, менеджер
  при adoption редактирует userinfo в `raw` и в журнале — v0.4 хранил строку как есть, это
  исправление входит в fix-wave), логи и ответы об ошибках.
- `mode` при подключении — `proxy`. `capabilities` нативного backend не меняются: с провайдером
  `router` документ сервиса фиксирован, политика — в роутере.

## 8. Установщик: `[egress] router`

- `EgressChoice` получает `ROUTER`; `[egress]`: `router = true|false` (по умолчанию `false`),
  `naive = direct|warp|router`, `mieru = direct|warp|router` (`router` допустим только при
  `router = true`; `warp` при `router = true` по-прежнему означает нативный WARP). Мастер задаёт
  вопросы, если архив Xray найден в `/var/lib/proxy-control/`; `check` сообщает, что не найден.
- Адаптер `installer/adapters/xray_router.py`: артефакты (§4), user/group 10006, state dir,
  секреты (token + два ключа ingress; `repair` не пересоздаёт существующие), `.env.xray-router`
  (`XRAY_ROUTER_*`), `COMPOSE_FILE` += `compose.xray-router.yaml`, env `*_EGRESS_ROUTER*` в
  `.env.naive`/`.env.mieru` (адаптеры naive/mieru, как `*_EGRESS_WARP` в v0.4), `docker compose
  up --wait xray-router`. Сеяние (один раз, ADR 007): при `naive = router` — нативный блок с
  провайдером `router`; секция сервиса в роутере — `direct` без правил (пропуск). На
  `upgrade`/`repair` egress не трогается; узел v0.4 подключается уже из панели (§9).
- Ротация — root-скрипт `scripts/rotate-xray-router-ingress.sh` (§5), как другие `prepare-*`
  скрипты вне транзакции установщика; `uninstall` останавливает контейнер, удаляет
  state, секреты и бинари. `installer/planner.profile_environment` (мёртвый код v0.4) удаляется.
- `check-deployment.sh`/`proxyctl.py status`: строка роутера (поколение, digest, версия Xray).

## 9. Панель

### 9.1 API (`panel/routing/routes.py`; owner для мутаций, viewer — чтение)

- `GET /api/routing/targets`: у каждого протокола `backend` = `xray_router`, если нативный
  `GET /egress` показывает провайдер `router` в управляемом документе; `router: {available,
  attached, xray_version, restart_required} | null` на узле; в `capabilities` — ячейки backend.
- `POST /api/routing/targets/{node_id}/{protocol}/attach` → 200 `{target}`: условия — на узле
  есть роутер (`egress.router.v1` / локальный клиент), `providers.router.reachable`, у протокола
  нет применённой политики с правилами или `default_action=egress` (иначе 409 `policy_applied`
  — сначала «сбросить»). Шаги: роутер `apply(intent: direct, [])` для тега (если секция не в
  этом состоянии) → нативный `apply(attach-документ)`. Политика протокола (если есть) получает
  `backend = xray_router`, `state = draft`, `revision + 1`.
- `POST …/detach` → нативный `apply(direct)` → роутер `apply(direct, [])`; политика получает
  нативный backend, `draft`. Оба действия — audit `routing.target.attach|detach`.
- `PUT/preview/apply/rollback/history/DELETE` — как в v0.4; для `xray_router`: `apply` = роутер
  `apply(intent)` + проверка, что нативный документ = attach (иначе применить его — узел мог
  быть переустановлен); `rollback` = роутер `rollback`; «сбросить» = роутер `direct, []`.
- Коды: `router_unavailable`, `router_unreachable`, `not_attached` (apply политики
  `xray_router` на неподключённый сервис → 409), плюс коды менеджера.

### 9.2 Локальный узел

`panel/xray_router.py`: `XrayRouterClient` (UDS, Bearer, те же таймауты и лимиты тела, что у
`NaiveClient`) + `MemoryXrayRouter` для тестов; env `XRAY_ROUTER_ENABLED`,
`XRAY_ROUTER_MANAGER_SOCKET`, `XRAY_ROUTER_MANAGER_TOKEN_SOURCE` из `compose.xray-router.yaml`
(секция `panel` оверлея, как у naive/mieru). `RoutingService` получает `router: RouterAdapter |
None`. `EgressTarget.backend` расширяется; `EgressTarget.router_attached: bool`.

### 9.3 Подключённые панели (Fleet v2)

- Узел объявляет `egress.router.v1` в `CAPABILITIES` и `identity.router = {available, attached:
  {naive, mieru}, xray_version, capabilities}`; протоколы — `egress.backend = xray_router` при
  подключении.
- `EgressDocument.backend` += `xray_router`; поле `router: dict | None` — intent для роутера,
  когда `backend == xray_router` (`document` при этом — attach-документ нативного менеджера);
  в `canonical_digest`; узел v0.4 без поля отвергает документ с `router` строгой моделью —
  центр не включает `xray_router` для узлов без `egress.router.v1` (422 `node_lacks_router`).
- Reconcile узла, для каждого протокола секции `egress`: при `backend == xray_router` —
  сначала роутер (`apply(intent)`), затем нативный attach-документ; при нативном `backend` —
  сначала нативный документ, затем, если поле `router` присутствует, роутер (`apply(intent)`).
  Всё идемпотентно по digest. Так attach с центра = поколение `{backend: xray_router, document:
  attach, router: intent}`, detach = `{backend: нативный, document: direct, router: intent
  direct/[]}` — порядок «роутер → натив» и «натив → роутер» следует из backend без отдельных
  команд. `ObservedEgress` дополняется `router: {revision, digest, generation}`; pusher переносит
  в `routing_applies`. Attach/detach с центра — те же маршруты §9.1.
- Лимит тела push узла 64 KiB сохраняется (intent ≤ 16 KiB на протокол).

### 9.4 UI («Маршрутизация», `panel/static/js/routing.js`)

- Карточка цели: бейдж backend («Xray-router» / «Caddy» / «mita»); при `router.available &&
  !attached` — кнопка «Подключить к Xray-router» с подтверждением («сессии сервиса прервутся,
  политика будет применяться роутером»); при `attached` — «Отключить». Недоступный роутер —
  строка «Xray-router: не установлен».
- Форма правила: поля «geosite», «geoip», «порты» всегда видны; preview честно отвечает
  `unsupported` для нативных backend. Предпросмотр показывает intent, `restart_required`, версию
  Xray и digest артефактов.
- Строка на карточке узла (`nodes.js`): «Маршрутизация: Xray-router (naive, mieru)».

## 11. Безопасность

- Ключи ingress: секреты установщика (`0600`, root), в контейнерах — Docker secrets; никогда в
  DB, API, audit, observed/identity, логах, `raw`/журналах менеджеров, Caddyfile-бэкапах вне
  каталога менеджера (Caddyfile уже `0600` у naive-manager; `server_config.json` mita — `0600`).
  Тест-сканы: `_SECRET_SHAPES` лаборатории получают оба ключа.
- Роутер: `read_only`, `cap_drop ALL`, non-root, без публичных портов, без `api`; Xray читает
  только свой каталог поколений и geodata; поколение с ключами — `0600` в каталоге `0700`.
- Все клиенты API роутера — только панель по UDS с Bearer; сырые конфиги/пути/URL отвергаются.
- Приватные назначения блокируются двумя рубежами (компилятор + bypass с резолвом).
- Подмена backend невозможна: политика с `backend`, не равным объявленному узлом, —
  `unsupported`; узел с `router` в поколении без `egress.router.v1` — 422 на центре, strict
  model на узле.
- Digest поколения = функция намерений + ключей + версии рендера; тот же `revision` политики с
  другим digest — `digest_conflict` (v0.4).

## 15. Отклонения от спеки vNext и решения, принятые за владельца

1. **Статический bridge в 3x-ui не реализуется** (Task 35, вопрос 2 §7): спека сама рекомендует
   включать его только после отдельного гейта drift/upgrade; ADR 007 оставляет дверь открытой.
2. **Task 38 (canary rollouts) отложен:** политики per-узел, fleet-wide поколения политики нет,
   обновление артефактов — установщик; узел и есть canary. Записано в ROADMAP-части CHANGELOG.
3. **Xray в контейнере, не systemd-юнит** (`deploy/proxy-control-xray-router.service` из спеки не
   создаётся): один стек compose, те же секреты/tmpfs/ограничения, что у менеджеров; слушает
   только loopback, host network нужен ради него. Менеджер супервизирует Xray сам — у Xray нет
   управляющего сокета, как у mita.
4. **Артефакт независим от 3x-ui:** сидирование бинаря из staged 3x-ui не реализуется —
   одна поставка, `Xray-linux-64.zip` v26.3.27 (последний стабильный на дату спеки), geodata из
   того же архива, а не отдельные pin'ы v2fly.
5. **`IPOnDemand` + `geoip:private → block` как неизменяемый bypass:** роутер резолвит имена на
   узле ради защиты от rebinding — говорится вслух в ROUTING/XRAY_ROUTER docs как DNS-семантика.
6. **Подключение — явное действие, а не следствие политики:** attach/detach — отдельные маршруты
   с аудитом; политика с backend `xray_router` не применяется на неподключённый сервис.
7. **Регулярные выражения (`regexp:`) и `network: udp` не предлагаются** (спека Task 34
   допускала): нечего доказывать на стенде и нечем показать в preview.
8. **Отложенные замечания v0.4** (`CONTINUE-HERE-v0.4.md`: пустой управляемый блок naive при
   «сбросить», userinfo в `raw` custom-строк, мёртвый `profile_environment`) закрываются
   fix-wave первой задачей.
9. **Гейт только на `ams-test`, без AMS_Z** — указание владельца на v0.5; тег/публикация и
   раскатка — за владельцем.
10. **Ротация ключей ingress — root-скрипт с кратким перезапуском**, без overlap-first
    (overlap в спеке относился к bridge 3x-ui; собственные менеджеры перерисовывают блок при
    старте).
