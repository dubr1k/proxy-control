# v0.10 — клиент на нескольких узлах и подписка под рукой

Статус: **утверждено владельцем** (2026-09-20), к реализации. Решения владельца: токен подписки
хранится **зашифрованным под keyring** (не только хэш, не открытым текстом); подписка создаётся
**автоматически вместе с клиентом**; состав клиента правится **матрицей узел × протокол**.
Предыдущие выпуски: [v0.8 выходы и правила](2026-09-18-v0.8-exits-and-rules-design.md);
основа модели — [ADR 004](../../adr/004-client-access-grant-subscription.md).

## 1. Цель

Оператор 3x-ui привык: создал клиента — сразу получил ссылку подписки и QR; открыл клиента —
видит ту же ссылку и список inbound'ов, галочками добавляет и убирает. У нас клиент уже держит
гранты на любых узлах, а подписка уже собирает их все в одну ссылку (ADR 004), но:

- в диалогах «Новый клиент» и «Выдать доступ» узел выбирается **один** `select`'ом, хотя
  `POST /api/clients/{id}/grants` принимает гранты на разных узлах одной операцией;
- ссылка подписки показывается **один раз**: в базе только хэш токена;
- подписку надо создавать отдельной кнопкой, и панель отказывает, если у клиента есть грант
  без сохранённого секрета (импортированный);
- «на каких узлах живёт клиент» нигде не видно как единица: гранты — чипы на карточке,
  подписка — отдельный диалог.

v0.10 закрывает четыре разрыва, не меняя модель `Client → AccessGrant → Subscription`.

### Не входит

Массовая выдача нескольким клиентам сразу; автоматическое размещение по узлам (non-goal ADR
004); новые форматы подписки; хранение отрендеренной подписки; изменение рендереров.

## 2. Хранение токена: escrow под keyring

Сейчас `client_subscriptions.public_token_hash` — единственный след токена. Добавляется
**шифрованная копия** в `secret_versions` тем же `SecretStore`, что хранит секреты грантов:

- `purpose="subscription"`, `grant_id=None`, `permitted_node_id=None`, `secret_id` = id
  подписки, `version=1`, `state="active"`. AAD связывает шифртекст с id подписки, так что
  строку нельзя переставить другому клиенту.
- Ротация мастер-ключа (`rewrap`) и проверка (`verify_all`) покрывают токены без доработок.
- Хэш остаётся: `/s/{token}` ищет по нему, как сейчас; escrow нужен только для показа.

Миграция 20 `subscription-escrow`: `ALTER TABLE client_subscriptions ADD COLUMN secret_id TEXT`,
`ADD COLUMN secret_version INTEGER`. Обе NULL для подписок, выданных до v0.10, и для панели без
keyring. Модель `Subscription` получает `secret_ref: SecretRef | None`; API отдаёт
`escrowed: bool`.

`SubscriptionService._issue` после генерации токена: если `secret_store.enabled` — `store(...)` и
запись ссылки в строку; иначе — как сейчас. При `revoke` и `rotate` старая версия секрета
переводится в `revoked` (`transition`), чтобы отозванный токен нельзя было показать.

Документация: ADR 004 получает абзац «показ по требованию: токен хранится под keyring, показ
только owner/admin и в аудите»; OPERATIONS.ru/en, раздел «Подписки: логи и ротация» — фраза
«в базе только хэш» заменяется на «хэш и шифрованная копия под мастер-ключом; без ключа копии
нет». SECURITY-заметки о reveal остаются в силе: показ идёт через одноразовый reveal.

## 3. API

Все ручки — под `context.roles("owner","admin")`, CSRF как у остальных мутаций.

- **`POST /api/clients/{id}/subscription/reveal`** — расшифровывает токен, собирает тот же
  `reveal_payload` (URL, QR, варианты) и отдаёт `reveal_token` для `GET /api/reveal/{token}`,
  как `create`/`rotate` сегодня. Аудит `subscription.reveal` (target — id подписки, detail —
  `client_id`). Ответы: 404 — клиента или активной подписки нет; 409 `not escrowed` — подписка
  выдана до escrow или без keyring, текст экрана: «ссылка выдана до включения хранилища —
  ротируйте, новая будет доступна для показа»; 409 `secret store disabled` — нет keyring.
- **`GET /api/clients/{id}/subscription`** — добавляется `escrowed` и `secret_store: bool`
  (включён ли keyring); `grants[]` получает `node_id`, `grant_id` уже есть.
- **`POST /api/clients`** — тело `ClientCreate` получает `subscription: bool = True`. Если
  домен подписки настроен и флаг истинен, подписка выдаётся в той же транзакции, что и клиент;
  ответ — `client` плюс `subscription_reveal_token` (тот же reveal-механизм), либо `null`, если
  домен не настроен. Клиент из «Новый клиент» создаётся **до** грантов, поэтому подписка с
  первого же поколения; гранты потом бампают поколение как сейчас.
- **`SubscriptionService._renderable`** убирается: гранты без секрета не блокируют выдачу — они
  уже честно идут в `unsupported` у рендереров. Проверка «только активный клиент» и «не больше
  одной активной» остаются.
- Существующие `create`/`rotate`/`revoke` не меняются снаружи; `create` остаётся для клиентов,
  созданных до v0.10 или с `subscription=false`.

Пакетной ручки «применить матрицу» **нет**: диф считает UI (§5), сервер получает уже знакомые
`POST /grants` (несколько узлов за раз) и `POST /grants/{id}/{enable|disable|delete}`.

## 4. Реестр аудита и события

Новое действие аудита `subscription.reveal`; в `audit.js` подпись «Ссылка подписки показана».
События (`/api/events`) не меняются: показ — не событие подписчика.

## 5. Интерфейс

### 5.1 Окно клиента

`#subscription-modal` становится **окном клиента**: открывается кликом по карточке (и кнопкой
«Подписка», которая переименовывается в «Открыть»). Заголовок — имя клиента и состояние.

Сверху — блок подписки:

- если подписки нет: «Подписка не создана» и кнопка «Создать URL» (для старых клиентов);
- если есть: строка статуса как сейчас (создана, поколение, последнее обновление), поле URL с
  «Копировать», QR, выбор формата (те же четыре варианта). Поле пустое до нажатия
  **«Показать»** — показ идёт через reveal и аудит; после показа URL и QR держатся, пока окно
  открыто, при закрытии очищаются (как сейчас). Кнопки «Ротировать», «Отозвать» — на месте.
- `escrowed=false` при включённом keyring: вместо «Показать» — подсказка «ссылка выдана до
  включения хранилища, ротируйте»; `secret_store=false`: подсказка «панель без хранилища
  секретов показывает ссылку один раз — при создании и ротации».

Ниже — **матрица**: строки — узлы, столбцы — MTProxy, NaiveProxy, Mieru.

- Строки: «Этот сервер» плюс связанные панели не на паузе (как `nodeOptions`), плюс узлы, где у
  клиента уже есть гранты, даже если панель сейчас на паузе (строка серая, только чтение).
- Клетка: чекбокс и подпись состояния — пусто, «ожидает узел», «выключен», «без секрета»,
  «ошибка: …». Клетка с грантом `desired_state=deleted` рисуется как пустая.
- Над матрицей — «Имя учётной записи» (одно на все новые клетки, предзаполнено из имени
  клиента или из уже существующих грантов, если имя у них одно).
- Кнопка **«Применить»** считает диф: поставленные галочки без гранта → один `POST /grants`
  со всеми парами узел × протокол; снятые галочки с включённым грантом → `disable`;
  поставленные на выключенном → `enable`. Снятие — **выключение, не удаление**; «Удалить» —
  отдельная кнопка в клетке, с подтверждением, как сейчас на чипе.
- После применения окно перечитывает обзор; успешная выдача открывает «Доступы выданы» поверх,
  как сейчас; `compensated`/`manual_intervention_required` — тост с текстом операции и
  матрица перечитана (что реально создалось, то и видно).
- Ротация секрета гранта и полоса маршрута (`routing_lane`) остаются на чипах карточки:
  в матрице их нет, чтобы клетка оставалась чекбоксом.
- Роль viewer: матрица только чтение, кнопок нет, «Показать» нет.

### 5.2 Диалог «Новый клиент»

`select` узла заменяется той же матрицей (общий модуль `js/placement.js`: рендер строк,
чтение выбора, диф). Порядок вызовов: `POST /clients` (с подпиской) → `POST /grants` → окно
«Доступы выданы». В это окно добавляется блок «Подписка» с URL, QR и выбором формата из
`subscription_reveal_token`, так что оператор получает всё одним экраном. Без отмеченных
клеток — только карточка и подписка.

### 5.3 Диалог «Выдать доступ»

Убирается: его роль берёт матрица в окне клиента. Кнопка «Выдать доступ» на карточке
открывает окно клиента.

### 5.4 Экраны MTProxy / NaiveProxy / Mieru

Не меняются: там по-прежнему один узел (`issueOnNode`), это сервисные экраны, не клиентские.

## 6. Ошибки и крайние случаи

- Нет домена подписки: `POST /clients` создаёт клиента без подписки, `subscription_reveal_token`
  = null, окно клиента показывает подсказку про `domains.subscription` как сейчас.
- Keyring выключен: подписка выдаётся без escrow (как v0.9), показ только при создании/ротации.
- Reveal-токен одноразовый и привязан к сессии — как у бандла; повторное «Показать» делает
  новый reveal и новую запись аудита.
- Часть узлов отказала в `POST /grants`: сага компенсирует созданное ей; матрица перечитывается.
- Узел на паузе с грантами клиента: строка видна, галочки заблокированы, подпись «панель на
  паузе».
- Подписка отозвана: блок сверху — «Подписка отозвана», кнопка «Создать URL».
- Архивный клиент: окно открывается только для чтения, матрица заблокирована.

## 7. Тесты

Backend (`panel/tests`):

- `test_subscription_escrow.py`: выдача с keyring пишет `secret_versions` с
  `purpose=subscription`; `reveal` возвращает тот же токен, что `/s/{token}` принимает; аудит
  `subscription.reveal`; после `rotate` старая версия `revoked`, reveal старой невозможен;
  без keyring `secret_ref=None`, reveal → 409; подписка до v0.10 (NULL) → 409 `not escrowed`;
  `rewrap` и `verify_all` считают токены.
- `test_clients_domain.py` / `test_subscription_lifecycle.py`: `POST /clients` создаёт подписку
  в одной транзакции, при `subscription=false` — нет; без домена — `null`; гранты без секрета
  не блокируют `create`.
- `test_migrations.py`: миграция 20 на базе v0.9 — колонки NULL, старая подписка читается.

UI-контракт (`test_subscription_ui_contract.py`, `test_fleet_v2_ui_contract.py`):

- матрица рендерит «Этот сервер», связанные панели, узлы с грантами на паузе (только чтение);
- диф: набор вызовов для «две новые клетки на разных узлах + одна снята + одна включена
  обратно» ровно один `POST /grants` с двумя `node_id` и по одному `disable`/`enable`;
- клик по карточке открывает окно; «Показать» вызывает `/subscription/reveal` и заполняет
  URL/QR; закрытие очищает;
- «Новый клиент» без клеток создаёт клиента и показывает блок подписки в «Доступы выданы»;
- viewer не видит «Показать» и «Применить».

Мобильный аудит (`test_mobile_layout.py`): матрица на ширине телефона — горизонтальная
прокрутка внутри блока, не страницы.

Гейт — полный прогон на `ams-test`; живая проверка на `AMS_Z` → `ams-test`: создать клиента на
двух узлах, показать ссылку, подписка отдаёт гранты обоих узлов, снять узел — грант выключен,
подписка обновилась, ротация — старый показ отказан.
