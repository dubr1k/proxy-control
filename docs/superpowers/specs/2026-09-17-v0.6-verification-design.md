# Proxy Control v0.6 — сверка всех функций v0.2–v0.5 на бэкенде и фронте

Дата: 2026-09-17. Ветка: `feature/vnext-v0.6-verification` (от `feature/vnext-v0.5-xray-router`,
`420f742` — v0.5 с закрытым гейтом, живой проверкой на AMS_Z и smoke экрана). Поручение владельца
(2026-09-17): «версия 0.6 — результат проверки всех функций на бэкенде и фронте за 0.2–0.5,
выпустишь её после того, как подтвердишь, что всё работает». Решения приняты автономно, как для
v0.4/v0.5; публикация v0.6 — по этому поручению, после подтверждения.

## 1. Цель

v0.6 не добавляет функций. Она отвечает на один вопрос — **работает ли всё, что обещано в v0.2–v0.5,
на настоящем хосте, через настоящие API и настоящий браузер** — и отвечает не словами, а
артефактами: матрицей «функция → доказательство», лабораторными tier'ами, которые эту матрицу
исполняют, и исправлениями всего, что при этом сломалось. Релиз выходит только когда каждая
строка матрицы закрыта зелёным прогоном на финальном дереве.

Что считается «функцией»: каждая строка «Added» разделов CHANGELOG v0.2–v0.5, каждый маршрут
панели (`/api/*`, 101 маршрут + `/s/{token}`), каждый view экрана (`dashboard`, `clients`,
`users`, `naive`, `mieru`, `versions`, `fleet`, `routing`, `admins`, `audit`, `login`), каждая
команда установщика (`wizard`, `plan`, `install`, `repair`, `status`, `uninstall`, `rollback`,
`resume`) и каждый закреплённый tier лаборатории.

## 3. Что v0.6 добавляет

### 3.1 Матрица сверки — `docs/VERIFICATION_MATRIX.md` + `tests/fixtures/verification-matrix.json`

Одна строка на функцию: `id`, `since` (версия), `area` (backend / ui / installer / fleet /
routing / router / clients), `claim` (что обещано, одной фразой), `proof` (тест, сценарий или
проверка, которая это доказывает: `pytest::…`, `lab-host::…`, `fleet::sNN_…`, `ui::…`,
`live::…`), `status` (`proven` | `fixed-in-0.6` | `gap`). Тест `tests/test_verification_matrix.py`:
каждая строка ссылается на существующий тест/сценарий (имя найдено в дереве), у каждой строки
`status != gap` к релизу, у каждого маршрута панели есть строка, у каждого view — строка `ui::`.
Матрица — единственный источник для таблицы гейта релизной заметки.

### 3.2 Аудит маршрутов — `scripts/dev/route-coverage.py`

Печатает все маршруты FastAPI панели (метод + путь + зависимость роли) и для каждого ищет
упоминание пути в `panel/tests`, `tests`, `scripts/lab`; маршрут без единого упоминания —
ошибка. Запускается в `remote-gate.sh full`. Роли: каждый маршрут с мутацией защищён `owner`
или `admin` — проверяется тем же скриптом по `Depends(...)` (расширение `test_rbac_*`).

### 3.3 Tier `ui` — `scripts/lab/ui-acceptance.py` (+ `remote-gate.sh ui`)

Единый CDP-драйвер (headless Chrome на `ams-test`, как `routing-shots.py`), в дереве, а не на
хосте. Проходит **каждый view** как владелец через настоящую форму входа, и как `admin`
(ограниченная роль) там, где роль меняет экран:

- `login`: неверный пароль → ошибка без утечки; верный → `/`; выход; CSRF-cookie.
- `dashboard`: карточка хоста (CPU/память/диск), статусы сервисов, счётчики протоколов.
- `users` (MTProxy): создать → ссылки `tg://` и `https://t.me/` → лимиты → отключить/включить →
  ротация → удалить; список обновляется без перезагрузки.
- `naive`: создать с квотой → reveal (Native/Karing/NekoBox, QR где обещан) → сброс трафика →
  отключить → удалить.
- `mieru`: создать → reveal `mieru-client.json` → квоты → ротация → удалить.
- `clients`: клиент → grants на все три протокола → подписка (URL, ротация, отзыв) → импорт из
  инвентаря узла (`import/inventory`, `adopt`, `adopt-batch`) → архив клиента.
- `versions`: агент версий отвечает, компоненты и закреплённые версии видны; обновление —
  через `fleet` tier (`/api/nodes/{id}/versions/{component}`), не из UI.
- `fleet` (узел): карточка «Этот сервер», строка маршрутизации; **центр** (вторая панель
  in-process, как в `fleet-acceptance.py`): экран «Узлы» центра — link по fingerprint, import,
  grant на узле, disable/rotate/delete, pause/resume, rename, unlink.
- `routing`: сценарии `routing-shots.py` (v0.4) + `router-shots.py` (v0.5) — в дереве.
- `admins`: создать администратора, отключить/включить, scoped API-ключи (создать, показать один
  раз, выключить, удалить).
- `audit`: записи всех действий выше видны, фильтры работают, секретов в кадре нет.
- Мобильная раскладка 390 px — каждый view.
- Инвариант всего прогона: ни одной ошибки консоли, ни одного неперехваченного исключения,
  ни одного секрета/ссылки в скриншотах (регэксп из `fleet-acceptance._SECRET_SHAPES`).

Выход: `lab-results/ui/report.json`, скриншоты (≤ 150 КБ, без метаданных) для релизной
заметки, `UI_ACCEPTANCE_OK`.

### 3.4 Бэкенд: дыры в лабораторном покрытии

- `lab-host` **без** `LAB_KEEP_INSTALL`: сценарии `uninstall` и `coexistence` не гонялись с v0.3 —
  один полный прогон обязателен (и снова `LAB_KEEP_INSTALL=1` для tier'ов).
- `lab-container` (`docker_lab.py`) — полный контейнерный лаб один раз на финальном дереве.
- `managed-xui-acceptance.sh` — managed-new 3x-ui на стенде: стенд держит stub `x-ui`
  (память: скрипт отказывается работать, пока он есть) — снять stub, прогнать, вернуть.
- Backup/restore drill: новый сценарий `guest-runner.sh` `backup-restore` — снять бэкап по
  `docs/BACKUP_RESTORE` (база, секреты, state менеджеров, роутер), сломать (удалить базу и
  state), восстановить, доказать: пользователи, гранты, политики, ключ ingress роутера и
  подписки те же (digest'ы до/после).
- Обновление данных: `tests/test_migrations.py` — цепочка с базы v0.2 (фикстура) до 15 с
  сохранением каждой строки (есть с 12–15; добавить фикстуру v0.2/v0.3, если её нет).
- Подписка (`/s/{token}`, домен подписки, ETag/кэш, отзыв) — `subscription-acceptance.py`
  как самостоятельный шаг `ui`/`fleet` (`s05`), плюс негатив: отозванный токен → 404 без тела.

### 3.5 Живая проверка на AMS_Z (по разрешению владельца)

Обновление v0.5 → v0.6 на месте (тем же путём, что v0.4/v0.5: точки отката `/root/v06-live/`,
rsync, `up -d --wait --no-deps panel naive-manager mieru-manager`), затем `ui-acceptance.py`
в **режиме только чтения** (`--read-only`: вход, каждый view рендерится, ноль ошибок консоли,
списки пользователей = снимку) плюс один пробный пользователь на протокол через UI (создан →
reveal → удалён). Никаких изменений маршрутизации/роутера (доказаны в v0.5).

### 3.6 Исправления

Всё, что матрица или tier'ы находят, чинится в этой же версии с тестом-регрессией (образец
v0.5: `test_the_real_runner_sees_only_the_router_compose_service`), строка матрицы получает
`fixed-in-0.6`. Никаких новых функций; изменения API — только исправления с сохранением
wire-совместимости (COMPATIBILITY.md).

## 4. Не входит

Новые возможности (§15 спеки v0.5: 3x-ui bridge, canary, per-grant, UDP relay, regexp);
merge веток в `main` и раскатка на `ams-server`/`AMS_P`/`AMS_R` — по-прежнему владелец;
переписывание существующих тестов ради красоты.

## 5. Гейт и релиз

Гейт на `ams-test` на финальном дереве: `full` (включая `route-coverage.py` и
`test_verification_matrix.py`), `compose`, `lab-container`, `lab-host` без `LAB_KEEP_INSTALL`
(один раз) и с ним, `fleet`, `routing`, `router`, `ui`, `managed-xui` — все `*_OK`; живая
проверка AMS_Z; релизная заметка `docs/releases/v0.6.0-beta.1.md` с таблицей матрицы и
скриншотами; `CHANGELOG`, `VERSION`. Публикация — путь v0.4 (архив дважды на стенде, тег с
`lab-sha256`, workflow `Release`, тело релиза из заметки) **по поручению владельца** — после
того, как все `*_OK` и живая проверка подтверждены в заметке.
