# v0.11 — обновления из upstream и обзор в одну строку

Статус: **утверждено владельцем** (2026-09-21), к реализации. Решения владельца: источник
версий — **прямой опрос upstream** (GitHub Releases и реестр образов), а не каталог проекта;
NaiveProxy **обновляется пересборкой Caddy из UI**, не только проверяется; Xray-router
получает выбор версии Xray-core и обновление через UI. Предыдущий выпуск:
[v0.10 клиент на нескольких узлах](2026-09-20-v0.10-client-subscription-nodes-design.md).

## 1. Цель

Оператор хочет нажать «Проверить обновления» и увидеть, что вышло новее, чем стоит на хосте;
нажать «Обновить» и получить новую версию с откатом при неудаче — без ручного редактирования
`versions.json`. Сегодня version-agent (v0.3) применяет только записи root-owned каталога
`/etc/proxy-control/versions.json`, компонентов ровно три (`telemt`, `naive`, `mita`), Xray-core
роутера прибит константой установщика, а обновление `mita` отказывает, пока существует
контейнер `proxy-control-mieru-manager` (он закрепляет бинарник по digest'у).

Второй блок — обзор: карточка ресурсов сервера занимает одну строку на всю ширину, три
протокола идут под ней тремя карточками, у Mieru исчезает «Application bytes», навигация
показывает общее число клиентов, всё это работает на телефоне.

### Не входит

Автоматическая установка обновлений по расписанию (только проверка по кнопке и кэш её
результата); обновление панели Proxy Control (см. `docs/UPGRADING.md`); обновление 3x-ui;
подпись каталога проекта (вариант А); обновление `mieru`-клиента внутри probe-образа;
обновление geodata иначе, чем уже умеет роутер (v0.8).

## 2. Обзор и навигация (панель, только фронт)

- `panel/static/js/dashboard.js`: из карточки Mieru удаляется блок `protocol-metrics` с
  «Application bytes». Карточка ресурсов (`hostCard`) получает класс `host-row`.
- `panel/static/style.css`: `.protocol-overview` остаётся grid'ом, но `.host-card` занимает
  `grid-column: 1 / -1`, а сетка становится `repeat(3, minmax(0, 1fr))`. Внутри карточки ресурсов
  метрики в один ряд (три ячейки). Точки: `≤1040px` — протоколы в две колонки, третья карточка
  на всю ширину; `≤900px` — одна колонка, метрики ресурсов 2 + 1; `≤560px` — метрики по одной,
  ячейки `protocol-access`/`protocol-metrics` по две в ряд, без горизонтальной прокрутки.

  `paintNavCounts` в `dashboard.js` берёт `items.length` из `GET /api/clients` (тот же вызов,
  что делает экран клиентов) и красит бейдж; `clients.js` после создания/удаления клиента
  обновляет бейдж тем же helper'ом (`paintClientsCount(context, n)` в `common.js`).
- Проверка: контракт `panel/tests/test_dashboard_ui_contract.py` (нет «Application bytes», есть
  `host-row`, `#clients-count` красится); `scripts/lab/ui-acceptance.py` получает шаг «обзор на
  ширине 390px»: карточки не перекрываются (`cells_do_not_overlap`), `document.documentElement.scrollWidth
  <= innerWidth`, бейдж клиентов равен числу карточек на экране клиентов.

## 3. Источники upstream (version-agent)

Новый модуль `version_agent/upstream.py`. Источники описаны **в коде**, не в конфиге: набор
хостов фиксирован, произвольный URL по-прежнему невозможен. Оператор может выключить опрос
переменной `PROXY_CONTROL_UPSTREAM_CHECK=off` в `version-agent.env`.

| Компонент | Источник | Артефакт (linux/amd64) | Хэш |
|---|---|---|---|
| `xray` | GitHub Releases `XTLS/Xray-core` | `Xray-linux-64.zip` | `Xray-linux-64.zip.dgst` (строка `SHA2-256=`) |
| `mita` | GitHub Releases `enfein/mieru` | `mita_<v>_linux_amd64.tar.gz` | `<asset>.sha256.txt` |
| `telemt` | реестр `ghcr.io/samnet-dev/mtproxymax-telemt` | тег `<v>` | digest манифеста (`Docker-Content-Digest`) |
| `naive` | GitHub Releases `caddyserver/caddy` + коммит `klzgrad/forwardproxy` (ветка `caddy2`) | сборка на хосте | pin `vX.Y.Z h1:…` после сборки |

Правила опроса:

- Только `https://api.github.com/repos/<owner>/<repo>/releases?per_page=10` (без pre-release и
  draft), `https://github.com/<owner>/<repo>/releases/download/…` для ассетов и `.dgst`, реестр
  `https://ghcr.io/v2/<repo>/tags/list` и `…/manifests/<tag>` с анонимным токеном. Редирект,
  покинувший хост из этого списка, — отказ (как в `_download` сейчас).
- Ответы ограничены: JSON релизов ≤ 1 МБ, файл хэша ≤ 4 КБ, архив ≤ 256 МБ.
- Версия из тега проходит `_VERSION` каталога; ассет без файла хэша — «недоступно для
  установки» с причиной `no_published_digest`, кнопки нет.
- Результат проверки сохраняется в `state.json` (`upstream: {checked_at, components: {…}}`) и
  отдаётся в `GET /v1/versions` до следующей проверки; при ошибке источника — предыдущий
  результат плюс `last_error`. Повторная проверка чаще, чем раз в 60 с, возвращает кэш
  (GitHub без токена — 60 запросов в час).

Запись каталога получает новое поле `source`: `catalog` (как сейчас, «проверено оператором»)
или `upstream` («из upstream, проектом не проверялась»). В UI и `docs/UPGRADING` это
проговаривается прямо: хэш из релиза подтверждает целостность скачивания и авторство файла,
но не заменяет проверку на стенде.

### 3.1. Артефакты внутри архивов

`CatalogEntry` расширяется полем `archive: {"format": "zip" | "tar.gz", "member": "<path>"} | None`.
Агент скачивает архив, сверяет SHA-256 **архива** с опубликованным, извлекает только
названный member (без symlink'ов, без `..`, размер ≤ 256 МБ) во временный файл и дальше идёт
обычный путь `_update_binary`. Для `xray` member'ов три (`xray`, `geoip.dat`, `geosite.dat`),
см. §5. Локальный `versions.json` тоже может использовать `archive`: оператор перестаёт
перепаковывать релизы.

## 4. Кнопки «Проверить обновления» и «Обновить»

Агент: `POST /v1/upstream/check` (тело пустое) — опрос всех источников, ответ тот же, что у
`GET /v1/versions`. Панель: `POST /api/versions/check` (owner), audit `runtime.version.check`.
Управляемый узел: `POST /api/fleet/v2/versions/check` по relay, центральная —
`POST /api/nodes/{id}/versions/check`.

`GET /v1/versions` теперь отдаёт для каждого компонента:

```json
{"current": "3.36.0", "status": "ready",
 "available": [{"version": "3.37.0", "kind": "binary", "source": "upstream", "url": "…", "sha256": "…", "published_at": "…"}],
 "upstream": {"checked_at": 1758460000, "latest": "3.37.0", "installable": true, "reason": null, "last_error": null}}
```

Установка версии из upstream идёт тем же `POST /v1/update {component, version, expected_current}`:
агент ищет версию сначала в каталоге, затем в кэше upstream. Кэш живёт в `state.json`, т.е. в
root-owned файле; из браузера по-прежнему приходит только номер версии.

Экран версий (`management.js`): сверху строка «Проверено <дата> · Проверить обновления»; карточки
Telemt, NaiveProxy, Mieru и, если роутер установлен, «Xray-router / Xray-core». В карточке:
текущая версия, `select` доступных с пометкой источника («каталог» / «upstream»), кнопка
«Обновить <компонент>», подпись о риске для upstream. Без агента экран, как сейчас, говорит
«Агент обновлений недоступен».

## 5. Компонент `xray`

- `_COMPONENTS` каталога и агента: `("telemt", "naive", "mita", "xray")`; panel `Literal` и
  relay-маршруты принимают `xray`. Компонент показывается, только если роутер установлен
  (`PROXY_CONTROL_XRAY_ROUTER=on` в `version-agent.env`, пишет установщик).
- Обновление: скачать `Xray-linux-64.zip`, сверить с `.dgst`, извлечь `xray`, `geoip.dat`,
  `geosite.dat` в `bin-dir` (`/usr/local/lib/proxy-control/xray-router`) через staging и
  `os.replace`, сохранить прежние три файла в `backups/xray.previous/`; переписать в
  `.env.xray-router` три строки `XRAY_ROUTER_*_SHA256`; `docker compose … up -d --wait xray-router`;
  через сокет менеджера (`/run/xray-router/manager.sock`, токен из compose secret) прочитать
  `status.xray_version` и убедиться, что он равен новой версии и `phase == idle`. Любая ошибка —
  откат файлов, overlay и контейнера с той же проверкой (`RolledBackError`/`RollbackFailedError`).
- Geodata: если источник списков роутера — «пин» (`source.kind == "xray"`), менеджер после
  рестарта сам переседает на новую пару (seed = `bin-dir`); иначе списки не трогаются.
- Установщик: `_XRAY_VERSION` и member-пины остаются **версией по умолчанию для чистой
  установки**. Новый модуль `installer/runtime_state.py` читает `state.json` version-agent'а;
  `_selection`/`verify`/`repair` Xray-router, Mieru и Naive принимают либо пин установщика, либо
  версию и хэши из `state.json`. Так `verify` после обновления через UI не ломается, а
  переустановка с нуля ставит проверенный проектом пин.
- `ReadWritePaths` unit'а агента получают `/usr/local/lib/proxy-control`.

## 6. Компонент `mita` и закреплённый потребитель

`_assert_no_pinned_consumer` заменяется на обновление потребителя: агент переписывает
`MIERU_MITA_SHA256` в `.env.mieru`, ставит бинарник, перезапускает `mita` (и `mita@<n>` слоты,
если есть), затем `docker compose … up -d --wait mieru-manager`; менеджер при старте сверяет
digest бинарника (как сейчас) и здоровье подтверждает успех. Откат — в обратном порядке. Из
`tar.gz` релиза берётся member `mita` (проверить путь внутри архива на стенде; для `.deb`
поддержка не добавляется).

## 7. Компонент `naive` — пересборка Caddy

- Проверка: последний релиз `caddyserver/caddy` (тег `vX.Y.Z`, не pre-release) и последний
  коммит ветки `caddy2` в `klzgrad/forwardproxy` (`GET …/commits/caddy2`, SHA). Версия
  показывается как `2.12.0` с пометкой «сборка на хосте».
- Установка: агент пишет `Dockerfile.caddy-naive` с новой версией builder-образа
  (`caddy:<v>-builder` **по digest'у**, полученному из реестра Docker Hub `registry-1.docker.io`,
  анонимный токен), `xcaddy build v<v>` и коммитом forwardproxy; `docker build` под root
  (агент уже требует docker); извлечение `/caddy` через `docker create`/`cp` как в
  `installer/adapters/naive.py:225`; дальше обычный `_update_binary`: checker
  (`EXPECTED_CADDY_VERSION` = вывод `caddy version` новой сборки), `caddy adapt --validate`,
  замена, pin `caddy-naive.pin`, рестарт `caddy-naive`, откат.
- `runtime_version` для такой записи агент вычисляет сам после сборки (строка `vX.Y.Z h1:…`),
  поэтому запись upstream для `naive` имеет `kind: "build"` с полями `caddy_version`,
  `builder_image` (с digest'ом), `forwardproxy_commit`.
- Сборка идёт до 15 минут; `POST /v1/update` для `naive` отвечает после сборки (панель ждёт
  через `timeout=1200`), UI показывает «Собираем…».
- `docker/Dockerfile.caddy-naive` в репозитории остаётся пином для чистой установки.

## 8. API и данные

- Агент: `GET /v1/versions` (расширен), `POST /v1/upstream/check`, `POST /v1/update` (компонент
  `xray`, версии из upstream). `state.json` схема 1 → 2: добавлены `upstream` и, для `xray`,
  `members` с хэшами.
- Панель: `POST /api/versions/check`; `Literal` компонентов + `xray`; `MemoryVersions` для тестов
  умеет `check()` и `xray`.
- Fleet: `POST /api/fleet/v2/versions/check` на узле, `POST /api/nodes/{id}/versions/check` на
  центральной; capability `versions.check` в `CAPABILITIES` узла — центральная прячет кнопку у
  узла без неё.
- Audit: `runtime.version.check`, `node.version.check`.

## 9. Ошибки

| Ситуация | Поведение |
|---|---|
| GitHub недоступен / 403 rate limit | `last_error` в ответе, предыдущий кэш остаётся, тост «Не удалось проверить: …» |
| Ассет без файла хэша | версия видна, `installable: false`, `reason: no_published_digest` |
| Хэш из `.dgst` не совпал со скачанным | `UpdateError`, ничего не тронуто |
| Роутер после замены не вышел в `idle` с новой версией | откат файлов и overlay, `RolledBackError` |
| `mieru-manager` не здоров после рестарта | откат `mita` и overlay, `RolledBackError` |
| `docker build` Caddy упал | `UpdateError` до замены бинарника, старая сборка не тронута |
| Опрос выключен (`PROXY_CONTROL_UPSTREAM_CHECK=off`) | кнопка «Проверить» скрыта, только каталог |
