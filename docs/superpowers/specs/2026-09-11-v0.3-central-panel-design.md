# Proxy Control v0.3 — центральная панель и подключённые панели

Дата: 2026-09-11. Ветка: `feature/vnext-v0.3-fleet-v2` (от `feature/vnext-v0.2-local-control-plane`,
`v0.2.0-beta.1`). Заменяет Phase 5 (Tasks 20–25A) из
[спеки vNext](2026-09-10-proxy-control-vnext-design.md) — см. раздел 12 «Отклонения».

## 1. Цель

Одна панель управляет собой и всеми подключёнными к ней панелями: `ams-server` становится
центром для `AMS_P`, `AMS_R`, `AMS_Z`. Всё настраивается из web-интерфейса, как в 3x-ui:

- на панели-узле владелец создаёт **API-ключ**;
- на центральной панели кнопка **«Узлы → Добавить панель»** принимает URL панели и ключ;
- дальше центр сам держит связь (heartbeat), показывает состояние узла, его пользователей
  и версии, выдаёт/отзывает доступы клиентам на любом узле и обновляет компоненты узла.

Релиз `v0.3.0` обязан включать это целиком; ничего кроме образа панели на хостах не
появляется (ни ingress, ни агента, ни CA, ни CSR). Все проверки — на стенде `ams-test`;
после зелёного гейта разрешена живая проверка на `AMS_Z` (узел) ↔ `ams-test` (центр).

### Не входит в v0.3

- транзитивные узлы (узел узла), история метрик, mTLS-режим панель↔панель
  (Fleet v1 mTLS остаётся как есть и не трогается);
- маршрутизация (v0.4), Xray-router (v0.5);
- удалённое обновление самой панели узла (version-agent умеет только `telemt|naive|mita`).

## 2. Паритет с 3x-ui

Источник: docs.sanaei.dev — *Operations → Multi-node*, *Reference → API Tokens*, *Nodes*.

| 3x-ui | Proxy Control v0.3 |

| Selective import of remote inbounds при добавлении | Шаг «Импорт существующих пользователей»: список пользователей узла по протоколам с чекбоксами → клиенты + adopted-гранты |

| Push-синк inbounds+clients, `configDirty`, adopt matching, orphan-защита | Push **DesiredGeneration** (ADR 002), `config_dirty`, adoption без удаления, orphan = ресурс центра вне текущего поколения → удаляется; локальные пользователи узла не трогаются |
| Stable per-panel GUID | `panel_guid` (uuid4) в `panel_settings`, создаётся при первом старте; на центре `node_id` = GUID узла |
| `allowPrivateAddress` | То же: приватные адреса узла запрещены без явного флага |
| Pause sync / probe / delete / `updatePanel` | Пауза / Проверить сейчас / Удалить (отказ при активных грантах) / вкладка «Обновления» через version-agent узла |

## 3. Архитектурные решения

- **ADR 008 (новый, supersedes ADR 001 в части направления):** транспорт панель→панель по
  HTTPS-домену панели узла со scoped Bearer-ключом. Узел не получает shell, URL, HTTP
  method/path, YAML или готовых конфигов — только типизированные документы.
- **ADR 002 применяется:** desired state узла — неизменяемое нумерованное поколение с
  digest; узел отвергает меньший номер и тот же номер с другим digest; откат = новое
  поколение с центра.
- **ADR 003 применяется:** ресурс на узле принадлежит либо центру (`central`), либо узлу
  (`local`). Ресурсы центра защищены от локальных мутаций (409 `managed_by_central`);
  ресурсы узла центр видит как `foreign` и никогда не удаляет.
- **Один центр на узел:** узел запоминает GUID центра при первом принятом поколении и
  отвергает поколения другого центра (409 `foreign_master`) до «Отвязать от центра».
- **Секреты выдаёт центр.** Naive/Mieru уже caller-supplied. Telemt: `POST /v1/users`,
  `rotate-secret` и `PATCH` upstream принимают `secret` (32 hex); узел пробует передать
  секрет, при отказе пиннутого форка (`ghcr.io/samnet-dev/mtproxymax-telemt@sha256:ab27…`)
  генерирует сам и возвращает креды в ответе на push (как 3x-ui возвращает клиентов).
  Probe 2026-09-11: TELEMT_CALLER_SECRET = supported (`create: 202 {"ok": true, ...}`).
  Первый шаг плана — живой probe форка на `ams-test`.

## 4. Данные

Все миграции additive, номера продолжают `MIGRATIONS` (v9+). Таблицы существуют на каждой
панели; какие из них заполнены, зависит от роли панели в конкретной связи.

```text
panel_settings        key TEXT PK, value TEXT               -- panel_guid, fleet_master_guid
api_keys              id, name, scope CHECK(admin|monitor|node-sync), prefix, key_hash UNIQUE,
                      enabled, expires_at NULL, created_at, created_by, last_used_at
node_links            node_id PK → fleet_nodes, panel_url, tls_verify CHECK(verify|pin),
                      pinned_cert_sha256, api_key_secret_id, allow_private_address,
                      enabled, status CHECK(unknown|online|offline), latency_ms,
                      panel_version, identity_json, status_json, last_heartbeat_at,
                      last_error, config_dirty, desired_generation, acknowledged_generation,
                      created_at, updated_at
desired_generations   node_id, generation, digest, document_json, previous_generation,
                      created_at, created_by, pushed_at, acknowledged_at
                      PK(node_id, generation)
observed_generations  node_id PK, applied_generation, digest, reconcile_state,
                      resources_json, reported_at
managed_generations   generation PK, digest, master_guid, document_json, received_at,
                      applied_at, state CHECK(received|applying|converged|failed)
managed_resources     protocol, runtime_username, ref, generation, state, last_error,
                      revision, updated_at   PK(protocol, runtime_username)
```

- Секреты узла для ресурсов центра лежат в `secret_versions` с `purpose='fleet-managed'`,
  `secret_id=ref`, `permitted_node_id='local'`.
- Ключ узла на центре — `secret_versions` с `purpose='node-api-key'`,
  `permitted_node_id=<guid>`; в ответах API только `has_api_key`.
- `fleet_nodes` для панели-узла: `node_id=<guid>`, `kind='remote'`, `auth_state='linked'`;
  колонка `transport CHECK(v1|panel)` добавляется миграцией, v1-узлы получают `v1`.

Документ поколения (secret-free, канонический JSON → SHA-256 digest):

```text
GenerationDocument
  schema_version: 1
  node_guid, master_guid, generation, previous_generation, created_at, created_by
  resources: [
    { ref: "grant:<id>", protocol, runtime_username, desired_state: enabled|disabled|deleted,
      credential_ref: "grant:<id>:<version>", credential_origin: caller|manager,
      options: {...}, valid_from, valid_until }
  ]
```

Ссылка `credential_ref` включает версию: смена версии на центре = ротация на узле.

## 5. Узел: API-ключи и Fleet API v2

### 5.1 API-ключи

- Формат: `pc_<prefix8>_<43 url-safe>`; в БД `prefix` для поиска и SHA-256 всего ключа;
  сравнение константное по времени. Плейнтекст возвращается один раз при создании.
- Аутентификация: `RequestContext.current` принимает `Authorization: Bearer` до cookie.
  Ключ превращается в псевдо-пользователя `{username: "key:<name>", role, via: "api-key"}`;
  CSRF для bearer не проверяется (cookie нет). `admin` → owner, `monitor` → viewer,
  `node-sync` → отдельная зависимость `context.fleet_key`, остальные маршруты отвечают 403.
- Просрочка и `enabled=0` → 401. Каждый вызов обновляет `last_used_at` (не чаще раза в
  минуту). Rate limit на ключ: 120/мин (429).
- Audit: `actor_username="key:<name>"`; тела запросов/ответов в audit и логи не попадают.

### 5.2 Эндпоинты `/api/fleet/v2/*` (scope `node-sync` или `admin`)

| Метод и путь | Назначение |
| --- | --- |
| `GET identity` | `{guid, panel_version, api_version: 2, master_guid, protocols: {mtproxy|naive|mieru: {enabled, public_host, public_port, daemon: ok|down|off}}, capabilities: [...]}` |
| `GET status` | версии и host из version-agent, трафик и число пользователей по протоколам, счётчики managed/local |
| `GET inventory` | пользователи по протоколам: `{runtime_username, enabled, options, ownership: central|local, ref?}` — без секретов |
| `PUT generation` | тело `{expected_guid, generation: GenerationDocument, secrets: {credential_ref: plaintext}}`. Проверки: guid (409 `guid_mismatch`), чужой центр (409 `foreign_master`), номер ниже (409 `stale_generation`), тот же номер/другой digest (409 `digest_conflict`), digest не сходится (422), лимит 64 KiB, неизвестный протокол/поле (422), секреты только для refs документа (422). Сохраняет поколение и секреты, запускает reconcile с дедлайном 25 с; `200 {observed, credentials: {ref: plaintext}}` (`credentials` — только для ресурсов, которые узел сгенерировал сам; `Cache-Control: no-store`) или `202` — reconcile продолжается в фоне |
| `GET observed` | `{applied_generation, digest, reconcile_state: idle|applying|converged|failed, resources: [{ref, protocol, runtime_username, state: enabled|disabled|missing|failed, error?, revision?}], reported_at}` |
| `POST credentials/capture` | `{resources: [{protocol, runtime_username}]}` → `{credentials: {"<protocol>:<user>": plaintext|null}, unsupported: [...]}`, `no-store`. Используется при импорте и при повторной эскроу-выдаче после потерянного ответа |
| `POST versions/update` | `{component: telemt|naive|mita, version, expected_current}` → version-agent узла |
| `POST unlink` | «Отвязать от центра»: `fleet_master_guid` очищается, ресурсы центра становятся `local`, runtime не трогается. Та же операция доступна владельцу узла из UI (сессия), а центр вызывает её при «Удалить узел» |

Повторный `PUT` того же поколения идемпотентен: reconcile проходит по факту (no-op, если
сошлось), ответ той же формы, креды manager-ресурсов повторно берутся из runtime через
`capture`.

### 5.3 Reconcile на узле (`panel/fleet_v2/reconcile.py`)

```text
load latest managed_generation (received|applying|failed)
discover через адаптеры включённых протоколов
для каждого ресурса документа:
  deleted   → если есть в runtime и ownership=central → adapter.delete → state=missing
  отсутствует в runtime → preflight → create(operation_id=f"{guid}:{gen}:{ref}", intent,
                         CredentialPlan(caller, secret) | manager) → state=enabled
  есть в runtime → credential_ref сменился → rotate; enabled≠desired → enable/disable;
                   options≠desired → update_options, где адаптер умеет, иначе drifted
                   (набор изменяемых полей на адаптер фиксирует план по API менеджеров)
ресурсы центра из прошлого поколения, отсутствующие в документе → delete (orphan)
ресурсы ownership=local → не трогаются
verify повторным discover → observed; converged → config_dirty=0
```

- Ошибка одного ресурса не останавливает остальные; поколение `failed` с постатусной
  раскладкой; фоновый ретрай с backoff 30 с → 10 мин до сходимости или до нового поколения.
- Поколение и секреты записаны до apply; при старте панели незавершённое поколение
  применяется заново (идемпотентно по discover). Компенсации нет — откат делает центр.
- Локальные писатели (`/api/users*`, `/api/naive/users*`, `/api/mieru/users*`,
  `DomainFacade`, `ProvisioningService`) перед мутацией проверяют `managed_resources`
  → 409 `managed_by_central`. Локальный discover домена узла считает их `foreign`.

## 6. Центр

- `panel/fleet_v2/client.py` — `NodeClient` (httpx): Bearer, таймауты (connect 5 с, read
  30 с), TLS `verify` через системный trust store или `pin` через SSL-контекст без
  проверки цепочки + сравнение SHA-256 листа; ошибки маппятся в `NodeUnreachable`,
  `NodeRejected(code)`, `NodeAuthFailed`. Тела ответов не логируются. Для тестов
  принимает `transport=` (httpx `ASGITransport` ко второму приложению).
- `panel/fleet_v2/links.py` — `NodeLinkService`: `fingerprint(url)`, `test(url, key,
  tls)` → identity+status без сохранения, `add(...)` (одна транзакция: `fleet_nodes`,
  `node_links`, ключ в `secret_versions`, audit), `update`, `set_enabled`, `probe`,
  `delete` (отказ, пока есть гранты с `desired_state<>'deleted'`), SSRF-проверка адреса.
- `panel/fleet_v2/generations.py` — `compile(db, node_id) -> GenerationDocument` (чистая
  функция от `access_grants` узла с `origin in (provisioned, imported)`), `publish(db,
  node_id, actor)` в транзакции вызывающего: одинаковый digest → новой строки нет; иначе
  `generation = last + 1`, `config_dirty = 1`. Подключается к `ClientService.notify`
  рядом с `bump_generation` — все мутации грантов уже проходят через него.
- `panel/fleet_v2/pusher.py` — lifespan-задача: по каждому включённому `node_link`
  heartbeat раз в 15 с (`identity` + `status`) → статус, latency, версия, демоны,
  счётчики; переходы → события `node.up`/`node.down`; при `config_dirty` или
  `desired_generation > acknowledged_generation` → `PUT generation` с секретами,
  раскрытыми через `SecretStore.reveal(permitted_node_id=node_id)`; ответ → статусы в
  `access_grants.observed_state`, `observed_generations`, эскроу вернувшихся кредов
  (новая активная версия секрета); `202` → `GET observed` на следующем тике. Ошибки →
  `last_error`, backoff.
- Provisioning удалённых грантов: в `ProvisioningService.start` для узлов с
  `transport='panel'` шаг `publish` вместо `preflight/create`: грант, секрет `pending` и
  поколение записываются в одной транзакции, операция `pending_remote`; pusher завершает
  её, когда observed сообщает `enabled`. `bundle()` для удалённого гранта доступен после
  активации; UI показывает «ожидает узел».
- Импорт: `POST /api/nodes/{id}/import {resources: [{protocol, runtime_username,
  client: new|<client_id>}]}` → клиент (display_name = username) или привязка, грант
  `origin=imported` с наблюдаемым состоянием, `credentials/capture` → активный секрет;
  если capture не поддержан — грант без секрета, подписка показывает «нужна ротация»,
  кнопка «Ротация» создаёт поколение с новой версией. Затем `publish` — узел помечает
  ресурсы `central` (apply = no-op).
- Подписки: публичные хосты протоколов для узла берутся из `identity_json`; рендереры
  получают `public_hosts_for(node_id)` вместо единственного значения настроек.

## 7. UI

- **«Доступ»** (owner-only): секция «API-ключи» — таблица (имя, scope, срок, статус,
  последнее использование), «Создать ключ» (диалог: имя, scope, срок; плейнтекст показан
  один раз с кнопкой копирования), вкл/выкл, удалить.
- **«Узлы»**: карточка «Этот сервер» дополняется GUID, URL для добавления на центре и
  подсказкой «создайте ключ node-sync»; если панель привязана к центру — бейдж
  «управляется центром <имя/GUID>» и кнопка «Отвязать». Кнопка **«Добавить панель»** →
  диалог: Имя, URL, API-ключ, Проверка TLS (`verify`/`pin` + «Получить отпечаток»),
  «Проверить» (identity + status + inventory), шаг «Импорт существующих пользователей»
  с чекбоксами, «Добавить». Карточка узла: статус, версия, демоны, счётчики, трафик,
  latency, heartbeat, `last_error`, `desired/applied generation`; действия: Пауза /
  Возобновить, Проверить сейчас, Изменить, Удалить; вкладки **Обзор** / **Пользователи**
  (гранты узла по протоколам + локальные пользователи с «Импортировать») /
  **Обновления** (версии компонентов узла, кнопка обновить). Карточки v1-узлов и
  локального узла остаются.
- **«Клиенты»**: выбор узла при выдаче доступа включает подключённые панели; статус
  гранта `pending` отображается как «ожидает узел».
- Мобильная навигация и `check-js-syntax.sh` — как для остальных экранов.

## 8. Безопасность

- Ключи: только хеш в БД, константное сравнение, scope, срок, отзыв — мгновенно.
- Ключ узла на центре зашифрован master-key (v0.2 уже требует его при наличии секретов).
- TLS: `verify` по умолчанию; `pin` — для самоподписанных/лабораторных сертификатов;
  `skip` не существует. Приватные адреса — только с `allow_private_address`.
- На узле: `no-store` на всех ответах с секретами, лимит тела 64 KiB, rate limit на ключ,
  audit без тел, поколения только от одного центра.
- Payload по-прежнему типизирован: ни shell, ни URL, ни путей, ни конфигов.
- Компрометация центра = компрометация секретов всех узлов — принимаемая граница, та же,
  что у 3x-ui; компрометация одного узла не даёт доступа к другим (ключ односторонний).

## 9. Установка, обновление, раскатка

- Новых компонентов нет. Обновление панели = существующая процедура (`compose up -d
  --build --wait panel`), миграции additive, `panel_guid` создаётся сам.
- Порядок для владельца после релиза: обновить все четыре хоста → на `AMS_P/R/Z` создать
  ключ `node-sync` → на `ams-server` добавить три панели и импортировать пользователей.
- Откат узла: предыдущий образ панели; `managed_resources` пуст, пока центр ничего не
  прислал, так что откат до первого поколения не оставляет следов.
- Документация: `FLEET.en/ru.md` переписываются под v2 (v1 переносится в раздел
  «Legacy mTLS transport»), `PANEL.*` — API-ключи, `docs/OPERATIONS.*` и `UPGRADING.*`,
  `CHANGELOG.md`, `docs/VNEXT_ARCHITECTURE.md` (ADR 008).

## 11. Критерии приёмки v0.3

- владелец подключает панель из UI за три действия (ключ → добавить → импорт) без CLI;
- транспортное здоровье и здоровье демонов различимы; heartbeat даёт online/offline
  и события;
- гранты на удалённом узле создаются/выключаются/ротируются/удаляются и сходятся после
  офлайна узла без участия оператора;
- узел отвергает меньшее поколение, конфликт digest и чужой центр;
- ресурсы центра защищены от локальных мутаций; локальные пользователи узла не удаляются;
- потеря ответа на push не создаёт второй аккаунт и не теряет единственный секрет;
- подписка клиента объединяет гранты всех узлов с правильными публичными хостами;
- v1-узлы продолжают работать; миграции additive; откат узла не оставляет следов.

## 12. Отклонения от Phase 5 спеки vNext

| Было в Phase 5 | Стало | Почему |
| --- | --- | --- |
| Pull-only mTLS ingress v2 + отдельный агент + CA/CSR | Панель→панель по HTTPS-домену панели с API-ключом | Требование владельца: всё из web-UI, «как в 3x-ui»; узлы уже публикуют панель по HTTPS с WebPKI |
| Асимметричный канал `secret-results` (X25519+HKDF, ingress keyring, ротация) | Центр генерирует секреты; Telemt принимает `secret`; fallback — креды в ответе на push | Upstream Telemt поддерживает caller-supplied secret; канал стал избыточен |
| Node-local compensate → verify previous generation | Постатусный `failed` + ретрай; откат = новое поколение центра | Пользователи независимы; частичный apply безопасен; ADR 002 anti-entropy |
| Capability handshake до отправки | Узел объявляет `capabilities` в identity; неподдержанное → `unsupported` в статусе ресурса | Достаточно для трёх известных адаптеров |
