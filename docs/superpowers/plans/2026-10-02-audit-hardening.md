### Незавершённые проверки и ограничения

- Полный QEMU `release-amd64` (19 сценариев) ещё не прошёл; отдельная fresh-установка с реальной перезагрузкой (17 шагов) и дополнительная изолированная Fleet-приёмка подготовлены к последующему запуску. Первый запуск VM завершился OOM на подготовке окружения; его отчёт сохранён отдельно и не считается успешной проверкой. Повторный запуск с ограниченным TCG cache и фиксированным лимитом памяти дошёл до установки probe, превысил штатный таймаут 900 секунд и выполнил rollback. Обнаружен дополнительный дефект: образ probe с совпадающим идентификатором владельца создан через 278,56 секунды после завершения rollback; остановка родительского shell не остановила всю работу сборки. Исправление и регрессионный тест готовятся отдельно. Увеличения таймаута ради зелёного результата не было; после исправления требуется новый кандидат и полный повтор проверки.
- Первая локальная приёмка AMS_Z не проверила роль панели до создания данных. Внешний центр автоматически импортировал 9 тестовых runtime-доступов; их локальная очистка корректно получила `409`. В сценарий добавлен отказ до любых изменений, если узел управляется центром. Временные ключи отозваны, точный журнал оставлен для штатной очистки через владельца.
- По разрешённой проверке `ams-server` подтверждён как владеющий центр: 9 импортированных тестовых grants в 9 клиентах, чужих grants в этих клиентах нет. Пользователь отказался от предложенной точечной очистки («Не нужно делать»). Изменения центра и связанная очистка AMS_Z не выполняются; девять тестовых доступов остаются, журнал их происхождения сохранён, временные административные ключи отозваны.
- Существующая исходящая Fleet-связь AMS_Z относится к другому GUID и vhost, а не к текущей панели ams-test. TLS возвращает `verify_code=20`; сервер отдаёт один сертификат. Сохранённый старый образ и кандидат отказывают одинаково. Связь, сертификаты и truststore не менялись.
- Оба рабочих ingress относятся к coexist/foreign-конфигурации. Обновление вернуло `coexist_manual`, `client_ip=not_verified`; чужие SNI-маршруты не менялись. ### Дополнение для кандидата 1.1.1-rc.2

Ошибка поздних действий после таймаута исправлена в Core runner: команда запускается
в отдельной сессии, при прерывании её группа получает SIGKILL; затем проверяются
завершение лидера и отсутствие выполняющихся процессов группы. Неопределённость
останавливает автоматический rollback и оставляет журнал `applying` с требованием
проверки процессов оператором. Очистка временного доступа не маскирует это прерывание.
Отдельно запущенные службы и Docker daemon не считаются частью этой группы.

Регрессии на ams-test: исходный runner дал **2 failed / 2 passed** в коротком
shell→child воспроизведении. Исправление прошло **386 passed, 1 skipped** в целевом
наборе; независимая проверка timeout/transaction — **63 passed**. Единственный skip
целевого набора — проверка отказа непривилегированному пользователю при запуске root.
Общий gate нового кандидата ещё предстоит; результат rc.1 не переносится на rc.2.

Прямая проверка Docker на ams-test воспроизвела позднее действие старого runner:
таймаут примерно на пятой секунде, callback сборки после двадцатой. Исправленный
runner остановил работу без позднего callback и без итогового образа; тестовые
ресурсы удалены, рабочий образ probe не менялся. Итоговые метаданные находятся в
`/root/dev/proxy-control-native-cancel-proof/report.json`.

### Следующие улучшения за пределами исправлений

1. Измерить работу парка на реалистичном числе узлов: длительность цикла, долю повторов, задержку применения и предел очереди. Текущие 8 параллельных отправок — ограничение ресурсов, а не доказанная оптимальная настройка для любого парка.
2. Добавить отдельную readiness-диагностику с состоянием БД, возрастом последнего reconcile и незавершёнными операциями. HTTP health и Docker healthy сами по себе не подтверждают применение всех доступов.
3. Постепенно разделить крупные installer/core и routing/service по существующим границам ownership, journal и rollback; сначала сохранить контрактные тесты. Для этого не требуется переписывать установщик целиком.
4. Расширить реальные клиентские проверки 3x-ui: установка и проверка слушателей не доказывают работу VLESS TCP, XHTTP и Hysteria2. Отдельно остаётся ручная приёмка Telegram реальным пользовательским клиентом.
5. Для рабочих coexist-конфигураций отдельно спроектировать доверенную передачу исходного IP с владельцем фронтенда. Автоматическое изменение чужих SNI ради этого исправления не выполнялось.
